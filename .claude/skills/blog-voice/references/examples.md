출처는 `~/.blog-work/overnight/voice-pairs.md` 1–4절과 저장소의 `src/content/posts/virtualized-document-list/index.mdx`입니다. 「수정 전」은 따라 쓰지 않을 인용입니다. 이스타의 중간 수정과 완성한 1편을 구별하며, 새 글의 표기와 용어는 blog-voice 본문 규칙을 따릅니다.

## 1. 서비스 안쪽 설명에서 사용자와 계기로

수정 전(`voice-pairs.md` 1절, 첫 문장)

이스타가 고친 문장(`voice-pairs.md` 1절)

> Knot는 제가 우아한테크코스에서 팀 프로젝트로 만든 서비스입니다. 사용자가 녹음버튼만 누르면 녹음 전체 전사본과 요약 문서를 자동으로 만들고, 해당 문서를 주제별로 쪼개 가독성 높은 문서로 관리합니다.

완성한 1편에서는 아래처럼 다듬었습니다.

> Knot는 제가 우아한테크코스에서 팀 프로젝트로 만든 서비스입니다. 사용자가 녹음 버튼만 누르면 녹음 전체 전사본과 요약 문서를 자동으로 만들고, 그 문서를 주제별로 쪼개 읽기 쉬운 문서로 관리합니다.

서비스 화면을 보여 준 뒤, 기존 문서 가져오기를 준비하며 팀 문서가 2,000개 가까이 늘었다는 계기와 느려진 증상을 이었습니다. 탭과 저장소 설명보다 사용자가 하는 일을 먼저 알 수 있게 했습니다.

## 2. 지금 설명에 필요 없는 구현 세부 빼기

수정 전(`voice-pairs.md` 2절)

> Knot 문서 목록도 문서를 100개씩 최대 20번 이어 받아 1,939개를 모두 JavaScript 배열로 들고 있고, 가상화한 뒤에도 받는 양은 같습니다.

이스타가 고친 문장(`voice-pairs.md` 2절)

> 가상화를 적용한 Knot 문서 목록도 서버에서 받아온 1,939개의 데이터를 모두 JavaScript 배열로 들고 있습니다.

가상화가 서버에서 받는 데이터의 양을 줄이지 않는다는 설명에, 몇 번에 나눠 받았는지까지 넣을 필요는 없었습니다. 완성한 글은 「받아 온」으로 띄었습니다.

## 3. 정의 나열에서 문제와 숫자 예로

수정 전(`1편-before.mdx`)

> 전체 높이는 그리지 않은 행의 높이까지 더한 높이로, 목록에 전체 높이를 주면 행을 몇 개만 그려도 스크롤바의 길이와 위치가 행을 모두 그린 목록과 같아집니다.

이스타가 고친 문장(`voice-pairs.md` 3절)

> 첫째, 스크롤바가 짧아집니다. 2,000개를 모두 그리면 목록 높이는 2,000 × 40 = 80,000px인데요, 화면에 보이는 것만 그린다면 스크롤 할 수 있는 공간이 없어지겠죠? 그래서 실제 데이터는 10개 행만 그린다고 해도, 스크롤 할 수 있는 높이를 확보하기 위해 80,000px의 공간이 있도록 만들어둡니다. 그러면 스크롤바는 2,000개가 모두 있을 때와 똑같아져요.

완성한 1편에서는 「실제로는 행을 10개만 그리더라도」로 다듬었습니다. 값의 이름을 외우게 하기보다, 공간을 두지 않으면 스크롤바가 어떻게 바뀌는지 먼저 설명하고 숫자로 따라가게 했습니다.

같은 수정에서 이스타는 「데모에서 overscan을 0으로 두고 확! 스크롤 해보시겠어요?」라고 독자에게 물었습니다. 완성한 글은 이 조작을 화면이 잠깐 비어 보이는 문제와 연결해 설명합니다.
