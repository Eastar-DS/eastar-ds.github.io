# 이스타의 블로그 글 문체

Knot를 모르는 프론트엔드 개발자에게 제가 어떤 문제를 만나 어떻게 풀었는지 들려주듯 씁니다. 기준 글은 이스타와 함께 완성한 `src/content/posts/virtualized-document-list/index.mdx`(리스트 가상화 1편)입니다. 아래 규칙은 이스타의 `voice-notes.md`, `voice-pairs.md`와 1편 수정 전후에서 뽑았습니다.

## 함께 읽을 것과 규칙의 순서

- 문장 금지 표현은 [writing-style](../writing-style/SKILL.md), 글 형식은 `docs/content-guide.md`를 읽습니다.
- 사용자가 이번 작업에서 명시한 규칙을 먼저 따릅니다. 정본의 첫 문단 결론 규칙과 아래 이야기 순서가 부딪히면, 1편처럼 서비스 소개에서 시작해 첫머리 안에 해결과 결과까지 잇습니다.
- 이번 리스트 가상화 시리즈는 `updatedAt`, 「고친 내용」 절, 「배운 점」 절을 넣지 않습니다. `slug`, `publishedAt`, 시리즈 순서를 지키고 공개한 글에 `draft`를 더하지 않습니다. 정본과 다른 지시는 정본을 고쳐 맞추지 않습니다.
- [예시 모음](references/examples.md)은 첫머리를 쓰거나 정의 문단을 고칠 때 읽습니다. 인용한 옛 문장의 표현을 새 글에 되살리지 않습니다.

## 1. 배경에서 결과까지 잇기

첫머리는 배경 → 계기 → 증상 → 측정 → 해결 → 결과로 이어 갑니다.

1. 배경: 서비스가 사용자에게 무엇을 해 주는지 쉬운 말로 소개합니다. 탭 이름, 저장소 위치, 팀 안에서만 쓰는 말로 시작하지 않습니다.
2. 계기: 왜 문제가 생겼는지 씁니다. 1편에서는 기존 문서를 가져오는 기능을 준비하며 팀 문서 2,000개 가까이를 넣었습니다.
3. 증상: 사용자가 느낀 일을 씁니다. 문서 목록 화면이 느려졌다는 말부터 하고 원인을 설명합니다.
4. 측정: 이스타가 잰 숫자로 얼마나 느렸는지 보여 줍니다. 장비나 횟수 설명으로 이야기를 끊지 않습니다.
5. 해결과 결과: 무엇을 바꿨고, 같은 조건에서 값이 어떻게 달라졌는지 씁니다.

첫머리에서 결과까지 알려 준 뒤 본문에서 원인과 해결을 풀어 갑니다. 모든 글에 1편의 절 제목이나 절 수를 복사하지는 않습니다. 2편부터는 서비스 소개를 길게 반복하지 않고 앞 편에서 한 일을 짧게 이은 뒤, 이번 편이 풀 문제를 씁니다. 그 편만 읽어도 문제를 알 수 있어야 합니다.

첫머리에는 「100개씩 20번 받기」 같은 구현 세부, 「가운데값」 같은 통계 설명, 장비와 녹화 조건을 늘어놓지 않습니다. 정확한 값은 결과 표에 두고 첫머리에서는 자료가 뒷받침하는 「2,000개 가까이」 같은 어림도 씁니다.

## 2. 1인칭으로 말하듯 쓰기

- 「제가」, 「저희 팀이」로 주체를 밝힙니다. 이스타가 실제로 한 일과 자료에 있는 판단만 쓰며, 생각이나 대화를 지어내지 않습니다.
- 습니다체를 바탕으로 「~예요」, 「~해요」 같은 해요체를 섞습니다. 문장마다 같은 끝맺음을 기계적으로 반복하지 않습니다.
- 배경과 다음 일을 이을 때 「~는데요,」를 씁니다. 「원래 Knot는 사용자가 직접 녹음한 내용만 문서로 정리해 줬는데요」처럼 이어 말합니다.
- 한 문장에 서로 다른 정보를 몰아넣지 않습니다. 같은 맥락의 원인과 결과는 자연스럽게 잇고, 뜻 없이 짧게 잘라 쓰지도 않습니다(writing-style).
- 독자가 확인할 수 있는 데모가 있으면 「overscan을 0으로 두고 빠르게 스크롤해 보시겠어요?」처럼 조작과 볼 것을 함께 말합니다. 데모 없이 해 보라고 묻지 않습니다.
- 「스크롤할 수 있는 공간이 거의 없어지겠죠?」, 「어떻게 풀었을까요?」처럼 독자가 다음 설명을 생각해 볼 질문도 씁니다.
- 느낌표는 정말 강조할 때 쓰며 글 하나에 세 곳을 넘기지 않습니다. 범위는 「–」(U+2013), 짧은 인용과 화면 문구는 「」로 씁니다.

## 3. 절마다 답할 질문을 나누기

| 절의 역할 | 담을 내용 |
| --- | --- |
| 개념 | 쉬운 풀이, 그 방법을 쓰면 새로 생기는 문제, 숫자 예와 데모 |
| 원인 찾기 | 증상, 측정, 원인 짐작과 그 짐작을 확인한 시험 |
| 방법 고르기 | 실제로 살펴본 방법과 우리 구조에 맞는지 따진 내용 |
| 동작 설명 | 앞에서 낸 문제를 하나씩 어떻게 풀었는지 |
| 결과 | 같은 조건의 전후 값과 표, 그림 |
| 포기한 것 | 해결 뒤에도 생기는 구체적인 제약 |
| 정리 | 본문에서 설명한 문제, 선택, 결과를 짧게 되짚기 |

`content-visibility`를 넣어 보거나 행 30개만 그려 본 시험은 원인을 확인하는 일이라 원인 절에 둡니다. 구현 방법을 고르는 절에서 다시 설명하지 않습니다. 첫 렌더링 문제에 맞지 않는 `memo`를 「먼저 떠올렸다」고 꾸미지도 않습니다.

마감 조건이나 팀 운영 이야기가 글의 문제와 관계없으면 뺍니다. 측정의 세부 조건은 마지막 접는 칸에 두고, 포기한 것과 섞지 않습니다.

## 4. 처음 나온 말은 먼저 보여 주기

화면의 대상을 부를 말은 실제 화면 그림이나 쉬운 풀이로 무엇을 가리키는지 정한 뒤 씁니다. 1편은 이름표가 붙은 화면을 보여 주며 「폴더 이름」, 「카드」, 「행」을 정했습니다. 코드 이름을 바로 내놓고 독자가 화면과 연결할 거라고 가정하지 않습니다.

| 시리즈에서 쓰는 말 | 처음 보여 줄 뜻 |
| --- | --- |
| 리스트 가상화 | 보이는 행과 overscan 안의 행을 DOM에 그리는 방법. Knot에서는 문서 데이터를 모두 받아 둔 채 그리는 행 수를 줄임 |
| 문서 목록 | Knot의 「주제별」 탭에서 폴더마다 문서를 모아 보여 주는 목록 |
| 폴더 이름 | 폴더마다 카드 위에 있는 제목 |
| 카드 | 폴더 이름 아래에서 문서 행들을 감싼 상자(`ul`) |
| 행 | 카드 안의 문서 한 줄(`li`) |
| 그리는 행 | 지금 보이는 행과 overscan 안의 행 |
| 그리지 않은 행의 자리 | 카드 안에서 DOM으로 만들지 않은 행이 차지할 공간 |
| overscan | 스크롤할 때 화면이 잠깐 비어 보이지 않도록 위아래로 더 그려 두는 여유분 |

overscan은 영어 그대로 쓰고 처음에 풉니다. Knot에서 쓴 325px와 설명용 예의 값을 구별합니다. 앞 편에서 정한 말도 이 편을 처음 읽는 독자가 알 수 있도록 짧은 풀이 또는 해당 설명으로 가는 링크를 둡니다.

한번 정한 말은 계속 같은 말로 씁니다. 아래 표현은 옛 문장을 대조할 때만 보고 새 본문에는 쓰지 않습니다.

| 쓰지 않는 말 | 쓸 말 |
| --- | --- |
| 목록 가상화 | 리스트 가상화 |
| 폴더 틀, 폴더 카드, 바깥 틀 | 카드 |
| 폴더 머리 | 폴더 이름 |
| 빈 높이 | 그리지 않은 행의 자리 |
| 미리 그릴 거리 | overscan |
| 한 줄로 펴기 | 폴더 이름도 한 칸으로 만들어 한 리스트로 세우기 |

## 5. 흐린 말을 구체적으로 풀기

| 흐린 말 | 구체적으로 쓴 말 |
| --- | --- |
| 화면 근처의 행 | 지금 보이는 행과 위아래 325px 안의 행 |
| 몇 개만 그려도 그대로 | 그리는 행의 수가 달라져도 카드 높이는 미리 계산한 값으로 고정 |
| 빈 곳이 보임 | 화면이 잠깐 비어 보임 |

「전체 높이」처럼 정의만으로 떠올리기 어려운 말보다 「스크롤할 수 있는 공간」처럼 독자가 화면에서 확인할 수 있는 말로 설명합니다. 숫자를 구체화하려고 자료에 없는 값을 만들지는 않습니다.

## 6. 정의보다 문제와 숫자 예를 먼저 쓰기

값의 정의를 나열하는 대신 그 값이 없으면 어떤 문제가 생기는지 보여 줍니다.

1. 설명용 조건을 먼저 정합니다. 1편의 예는 행 2,000개, 행 높이 40px, 화면 높이 240px입니다.
2. 「스크롤바가 짧아집니다」처럼 화면에서 생기는 문제를 말합니다.
3. 「2,000 × 40 = 80,000px」처럼 그 조건으로 계산해 보여 줍니다.
4. 행을 10개만 그려도 스크롤할 수 있는 공간은 80,000px로 두는 해결을 설명합니다.
5. 실제 Knot와 예가 다르면 무엇이 다른지 잇습니다. 예에서는 높이가 같지만 Knot에서는 행마다 높이가 달라 앞 행 높이를 차례로 더합니다.

설명용 수치와 측정값을 섞지 않습니다. 문제를 설명하기 전에 데모 소개를 끼워 넣지 말고, 조작이 필요한 문제에 이르렀을 때 데모로 안내합니다.

## 7. 비교는 공통점과 차이를 나누기

같은 점부터 말한 뒤 무엇이 다른지 구체적으로 씁니다.

> 두 방법 모두 전체 목록 높이만큼 스크롤 공간을 확보하지만, 저희는 행 높이를 미리 아는 조건이라 카드 높이를 계산해 고정해 뒀습니다. TanStack Virtual에서 동적으로 행 높이를 재면 전체 높이도 측정 결과에 따라 바뀔 수 있습니다.

공통점인 스크롤 공간 확보를 직접 구현만의 장점처럼 쓰지 않습니다. TanStack Virtual도 `getBoundingClientRect`나 `ResizeObserver`로 카드 위치를 재서 `scrollMargin`을 갱신할 수 있으므로, 위치를 동적으로 재는 일을 직접 구현만의 특징으로 쓰지 않습니다. 라이브러리가 모든 경우에 맞지 않는다고 넓혀 말하지 말고, Knot의 페이지 스크롤과 카드 구조에서 무엇을 더 해야 하는지 씁니다.

여러 방법은 「방법 | 장점 | 단점」 표로 비교합니다. 「얻는 것과 잃는 것」 틀에 맞추려고 장점이나 단점을 지어내지 않습니다. 기존 그림이 있으면 추상 도식과 실제 화면을 함께 보고, 코드 예시도 기존 미리보기와 연결해 설명합니다.

이번 시리즈 고치기에서는 새 그림이나 데모를 만들지 않습니다. 기존 그림과 데모를 쓰고 caption과 alt는 본문에 맞춥니다. 더 필요한 그림은 `~/.blog-work/overnight/figure-ideas.md`에 `편 · 자리 · 무엇을 보여 줄지` 꼴로 적습니다.

## 8. 측정은 이스타가 잰 것으로 쓰기

- 「제가 개발자 도구로 재 보니」, 「같은 조건에서 다시 재 보니」처럼 씁니다. 측정 스크립트가 주인공이 되지 않게 합니다.
- 본문에는 문제와 결과를 이해하는 데 필요한 숫자를 씁니다. 1편처럼 핵심 조건을 「(CPU 4배 느리게)」로 짧게 밝힐 수 있습니다.
- 장비, 횟수, 측정 구간과 값의 범위, 데이터 출처, 센 방법과 한계는 글 끝 접는 칸의 「항목 | 조건」 표에 씁니다.
- 수치를 더해 보는 표에는 합계 줄을 둡니다. 합계에 표에서 생략한 항목이 포함되면 「합계 (스타일 계산, 페인트 같은 그 밖의 일 포함)」처럼 밝힙니다. 자료에 없는 합계를 만들거나, 서로 다른 단위와 비교 방법을 억지로 더하지 않습니다.
- 표와 그림의 caption에는 날짜를 쓰지 않습니다. 필요한 측정 날짜는 접는 칸 안의 조건 표에 씁니다.
- 숫자와 사실은 자료에 있는 것만 씁니다. 읽기 정책을 지키며 자료를 확인하고, 비공개 이름이나 개인 기록 문장을 예시에도 복사하지 않습니다.

```mdx
<details>
<summary>측정 조건 자세히 보기</summary>

<Figure caption="표 N. 측정 조건" captionSide="top">

| 항목 | 조건 |
| --- | --- |
| 데이터 | 자료로 확인한 데이터 출처와 구성 |
| 장비 | 자료로 확인한 장비와 실행 조건 |
| 횟수와 범위 | 자료로 확인한 횟수와 값의 범위 |
| 측정의 한계 | 재지 않았거나 나누어 확인하지 못한 것 |

</Figure>

</details>
```

## 9. 풀이와 출처는 각주로 보내기

용어가 처음 나올 때 설명을 괄호 안에 길게 끼워 넣지 않습니다. INP, Commit 같은 용어의 자세한 풀이와 출처 링크는 `문장[^이름]`, `[^이름]: 풀이 [링크](주소)`로 글 끝에 둡니다. 앞 편으로 가는 글 링크나 데모 조작 안내까지 각주에 숨기지는 않습니다.

본문만 읽어도 설명을 따라갈 수 있어야 합니다. 카드와 행처럼 설명 내내 쓰는 말은 본문이나 그림에서 먼저 정하고, 더 알고 싶은 독자에게 필요한 정의와 근거를 각주에 둡니다.

## 10. 「AI가 쓴 느낌」 꼴과 바꾼 꼴

`voice-pairs.md` 4절에서 이스타가 짚은 문장입니다. 왼쪽은 따라 쓰지 않을 인용입니다.

| 피할 꼴 | 바꾼 꼴 |
| --- | --- |
| 아래 데모와 같은 숫자로 보겠습니다 | 간단한 예를 하나 들어 볼게요 |
| 탭을 누른 뒤 메인 스레드는 이런 일들로 바빴습니다 | 메인 스레드가 어디에 시간을 쓰고 있는지 살펴보면 아래와 같습니다 |
| X도 똑같이 하는 일이고, 달라지는 건 이 부분이에요 | X도 마찬가지예요. 다만 … 방법이 다른데요 |
| 하나씩 견줘 봤습니다 / 얻는 것과 잃는 것을 비교 | 하나하나 Knot 문서 목록의 구조에 맞는지 따져 봤습니다 |
| 앞에서 본 세 가지 문제를 … 이렇게 풀었습니다 | 그럼 앞에서 본 세 가지 문제를 … 어떻게 풀었을까요? |
| 빈 높이 / 빈 곳 / 화면 근처 | 그리지 않은 행의 자리 / 화면이 잠깐 비어 보이는 / 보이는 행과 overscan 안의 행 |
| 첫 렌더링 문제에서 memo를 먼저 떠올렸다 | 실제로 확인한 원인과 시험을 씀 |

내용 앞에서 할 일만 예고하는 문장, 정의를 여러 개 엮은 문장, 측정 조건을 잔뜩 끼운 문장도 직접 읽고 고칩니다. 검사 스크립트가 이런 문장을 모두 잡아 주지는 않습니다. 금지 표현 목록을 임의로 늘리지 말고, 추가 후보는 이스타가 검토할 제안서로 적습니다.

## 11. 쓰고 확인하는 차례

1. 기준 글의 첫머리와 이번에 쓸 절과 역할이 같은 절을 읽습니다. 실제 수정 전후 예시 서너 개는 [예시 모음](references/examples.md)에서 봅니다.
2. 자료와 개요를 확인하고, 첫머리는 1장, 본문 절은 3장의 역할에 맞춰 씁니다.
3. 처음 나오는 말이 풀렸는지, 같은 대상을 계속 같은 말로 불렀는지 확인합니다.
4. 숫자 예를 독자가 계산해 볼 수 있는지, 본문과 기존 그림의 숫자와 말이 맞는지 확인합니다.
5. 측정 세부는 접는 칸에, 자세한 용어 풀이와 출처는 각주에 둡니다.
6. `bash .claude/skills/writing-style/check.sh <글 파일>`을 출력 없이 통과시키고, 10장의 꼴도 직접 읽어 확인합니다.
7. 새 독자 검토는 글을 쓰지 않은 새 세션에 [review-post](../review-post/SKILL.md)로 맡깁니다. 검토 의견을 반영할 때 이 스킬을 다시 적용하고, 숫자나 뜻을 고쳤으면 fact-check-post로 다시 대조합니다.

끝 보고에는 고친 절과 까닭, 자료가 없어 쓰지 못한 사실, 더 필요한 그림을 적습니다.
