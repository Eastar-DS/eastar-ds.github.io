화면 근처의 행만 DOM에 그리면 스크린 리더는 DOM에 있는 행만 세어 폴더의 행 수와 지금 행의 순서를 잘못 읽고, 키보드로 포커스를 둔 행이 화면에서 멀어지면 행과 함께 포커스가 지워집니다. Knot 문서 탭 「주제별」 목록에서는 행마다 `aria-posinset`과 `aria-setsize`로 폴더 안 순서와 행 수를 알리고, 포커스가 있는 행은 범위 밖에서도 제자리에 그리면서 범위와의 사이를 간격 `li` 하나로 채웠습니다. 「라이브러리 없이 목록 가상화」 시리즈 5편이고, 카드에 그릴 범위를 구하는 계산은 [2편](/posts/virtual-list-row-range/)에 있습니다.

## 일부만 그리면 스크린 리더는 무엇을 읽을까

DOM에 있는 `li`만 세어 읽어서, 문서 100개 폴더도 항목 21개짜리 목록으로 읽고 42번째 문서를 1번째로 읽습니다. 브라우저는 DOM으로 접근성 트리를 만들고 스크린 리더는 화면의 픽셀이 아니라 접근성 트리를 읽는데, `ul`은 목록(list), `li`는 목록 항목(listitem)이 됩니다. 목록에 들어가면 스크린 리더는 「목록, 항목 N개」처럼 항목 수를 읽고, 설정에 따라 항목마다 「N개 중 M번째」처럼 순서를 읽습니다. `li`에 aria 속성이 없으면 브라우저는 같은 목록 안의 목록 항목을 세어 항목 수와 순서를 정하고, 카드의 위쪽 여백(`paddingTop`)은 요소가 아니라서 접근성 트리에 아무것도 만들지 않습니다.

요약 없는 행 100개짜리 폴더 카드를 3,000px 내리면 범위가 `{ start: 41, end: 62 }`라 카드에는 `li`가 21개 있고, 고치기 전에는 42번째 문서가 「21개 중 1번째」로 읽혔습니다. 맨 위에서는 범위가 `{ start: 0, end: 15 }`라 순서는 맞지만 15번째 문서가 「15개 중 15번째」로 읽혀, 사용자는 목록이 끝났다고 알게 되고 아래의 문서 85개를 모릅니다. 넓힌 구간에 걸치는 행 수가 위치마다 달라서, 화면이 스크롤되면 같은 문서의 항목 수와 순서도 바뀌었습니다.

## aria-posinset과 aria-setsize는 무엇을 알릴까

[`aria-setsize`](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-setsize)는 집합 전체의 항목 수를, [`aria-posinset`](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-posinset)은 집합 안에서 항목이 몇 번째인지를 1부터 세어 알리는 속성으로, 집합의 항목이 DOM에 모두 있지 않을 때 씁니다. 두 속성은 화면에 아무것도 그리지 않고 접근성 트리의 값만 바꾸며, `DocumentRow`가 폴더 안 순서(`index`, 0부터)와 폴더의 행 수(`rowCount`)를 받아 `li`에 넣게 했습니다.

```tsx title="DocumentRow.tsx"
<Item
  $isFirstRow={index === 0}
  aria-posinset={index + 1}
  aria-setsize={rowCount}
>
```

`DocumentFolder`는 `index`에 카드 안 순서가 아니라 `start`를 더한 폴더 안 순서를 넘기고, `rowCount`에는 받은 폴더 문서의 수(`documents.length`)를 넘깁니다. `start`를 빠뜨리면 카드의 첫 `li`가 다시 「1번째」로 읽히고 같은 값으로 정하는 구분선도 빠지며, `rowCount`에 그린 행 수(21)를 넘기면 42번째 행이 `aria-setsize` 21을 받아 WAI-ARIA가 정한 「`aria-posinset`은 `aria-setsize` 이하」를 어깁니다.

폴더 이름 옆에 보이는 문서 수는 서버가 센 주제의 전체 문서 수라서 `aria-setsize`에 쓰지 않았습니다. 목록은 문서를 2,000개까지 이어 받으므로 워크스페이스의 문서가 그보다 많으면 받지 못한 문서가 생기고, 예를 들어 서버의 수 120을 넘기면 마지막 행이 「120개 중 100번째」로 읽히는데 101번째부터 120번째 행은 스크롤해도 생기지 않습니다. 카드에 실제로 생길 수 있는 행의 수를 알려야 해서 `documents.length`를 넘깁니다.

## 포커스가 있는 행이 지워지면 어떻게 될까

포커스가 있는 요소가 DOM에서 빠지면 브라우저가 포커스를 문서 전체로 돌려서, 포커스 테두리가 사라지고 Enter를 눌러도 아무 링크도 열리지 않습니다. 키보드 사용자가 Tab으로 폴더의 0번 행에 포커스를 둔 뒤 마우스 휠로 목록을 내려 읽는다고 하겠습니다. 0번 행은 카드 맨 위에서 0~64px에 있어서, 화면 위쪽 끝이 389px가 되면 넓힌 구간의 위쪽 끝(389 − 325 = 64px)이 0번 행의 아래쪽 끝과 맞닿아 범위가 `{ start: 1, end: 21 }`로 바뀌고 0번 행의 `li`가 DOM에서 지워집니다.

포커스를 잃은 뒤 `document.activeElement`는 `body`가 되고(HTML 표준은 focus fixup이라 부릅니다), 다시 위로 스크롤해 0번 행이 범위에 들어와도 React가 새로 만든 `li`라서 포커스는 돌아오지 않습니다. 처음에는 포커스를 잃은 뒤 다음 Tab이 페이지 처음부터 시작한다고 보았는데, Chromium 157에서 행 `li`를 지우는 작은 HTML 페이지로 해 보니 다음 Tab은 지운 행이 있던 위치에서 다음 링크(Tab을 누를 때 카드에 있던 첫 행)로 갔고 Shift+Tab은 카드 앞의 링크로 갔습니다. Safari와 Firefox, 실제 앱에서는 확인하지 않았습니다.

## 포커스가 있는 행은 어떻게 지켰을까

폴더 카드가 포커스가 있는 행의 순서를 state로 기억하고, 포커스 행이 범위 밖에 있으면 제자리에 함께 그리면서 범위와의 사이를 사이 행들의 높이만큼 비운 간격 `li` 하나로 채웠습니다. 범위를 포커스 행까지 넓히면 쉽지만 범위는 `start`부터 `end` 앞까지 이어진 구간이라, 문서 994개 폴더의 0번 행에 포커스를 두고 900번 행까지 스크롤하면 화면 근처의 범위 `{ start: 895, end: 915 }`를 0번 행까지 넓혀 `DocumentRow` 915개를 그리게 됩니다. 간격 `li`로 채우면 화면 근처의 행 20개와 포커스 행을 더한 21개만 그리고, 간격 `li`는 58,110px 높이로 하나입니다.

그릴 항목을 차례대로 구하는 일은 `getDrawnRows`로 뺐습니다. 아래 코드는 포커스 행이 범위 밖에 있을 때의 두 분기이고, 항목 순서가 카드 위에서 아래로의 위치 순서와 같아야 차례대로 쌓았을 때 제자리에 놓입니다.

```ts title="getDrawnRows.ts"
if (keptIndex < start) {
  return {
    firstRowTop: offsets[keptIndex],
    items: [
      row(keptIndex),
      ...gap(offsets[start] - offsets[keptIndex + 1]),
      ...rangeRows,
    ],
  };
}

return {
  firstRowTop: offsets[start],
  items: [
    ...rangeRows,
    ...gap(offsets[keptIndex] - offsets[end]),
    row(keptIndex),
  ],
};
```

간격의 높이는 포커스 행이 범위보다 위면 포커스 행의 아래쪽 끝 `offsets[keptIndex + 1]`부터 범위 첫 행의 위쪽 끝 `offsets[start]`까지이고, 아래면 범위 마지막 행의 아래쪽 끝 `offsets[end]`부터 포커스 행의 위쪽 끝까지입니다. 포커스 행의 위쪽 끝부터 재면 포커스 행의 높이가 한 번 더 들어가 범위의 행이 한 행만큼 밀리고, 구분선 1px은 이미 `offsets`에 들어 있어서 다시 더하지 않습니다. 높이가 0이면(포커스 행과 범위가 맞닿으면) 간격 `li`를 만들지 않고, 범위가 비어 있으면 위쪽 여백을 `offsets[keptIndex]`로 두고 포커스 행 하나만 그려서 카드가 화면에서 멀리 떨어져도 포커스 행은 제자리에 있습니다.

카드는 `ul`이고 HTML은 `ul`의 자식으로 `li`(와 `script`, `template`)만 허용하므로 간격도 `li`로 만들고, 목록 항목이 아니라 높이만 차지하는 요소라서 `aria-hidden`을 붙여 접근성 트리에서 뺐습니다. 포커스는 행의 링크가 받은 `onFocus`로 기억하고, 카드 `ul`의 `onBlur`에서 포커스가 카드 밖으로 나가면 잊습니다.

```tsx title="DocumentFolder.tsx"
const handleCardBlur = (
  event: FocusEvent<HTMLUListElement>,
) => {
  if (!event.currentTarget.contains(event.relatedTarget)) {
    setFocusedIndex(null);
  }
};
```

DOM의 blur 이벤트는 버블링하지 않지만 React 17부터 `onBlur`는 버블링하는 focusout으로 동작해서, 카드의 `onBlur`가 안쪽 링크의 blur를 받습니다. `relatedTarget`은 포커스가 다음에 가는 요소이고, 카드 안의 다른 행으로 가면 카드 안의 링크라서 기억을 지우지 않고 다음 행의 `onFocus`가 순서를 바꿉니다. 페이지의 빈 곳을 눌러 포커스를 받을 요소 없이 빠지면 `relatedTarget`이 `null`이고 `contains(null)`은 예외 없이 거짓을 돌려줘서, 기억을 지우고 다시 렌더링할 때 포커스 행과 간격 `li`가 바로 빠집니다.

간격 `li` 안에는 링크가 없어서, 범위 밖에 둔 포커스 행에서 Tab을 누르면 DOM 순서대로 범위의 첫 행으로 갑니다. 행을 모두 그린 목록에서는 다음 행으로 가면서 화면이 3,000px 가까이 위로 돌아가는데, 지금은 보던 화면 근처의 행으로 가고 범위 첫 행의 `onFocus`가 기억을 바꾸면 포커스 행과 간격 `li`는 그리지 않습니다.

실제 빌드에서 첫 행 링크에 포커스를 두고 휠을 150px씩 30번 돌리자, 링크가 창 위쪽 끝보다 4,186px 위로 멀어져도 포커스는 끝까지 처음 링크에 있었고 빈 칸 프레임은 0장이었습니다. 카드가 넓힌 구간에서 벗어나 범위가 비었을 때는 포커스 행 하나만 그려져 있었고, 포커스 행 하나만 그린 상태에서 Tab을 누르자 포커스는 DOM 순서에서 다음 링크인, 화면 근처에 그린 다른 폴더의 13번째 행으로 갔습니다. 행을 모두 그렸을 때는 같은 폴더의 다음 행으로 가므로, Tab 순서는 행을 모두 그린 목록과 다릅니다.

## 아직 확인하지 못한 것은 무엇일까

접근성 트리의 값은 jsdom 통합 테스트와 실제 빌드로 확인했지만, 실제 스크린 리더로는 읽어 보지 않았습니다.

- VoiceOver로 읽어 보지 않았고, 표 1의 문장은 접근성 트리의 값으로 만든 예입니다. 목록에 들어갈 때 읽는 항목 수가 `li`의 `aria-setsize`를 따르는지는 브라우저와 스크린 리더 조합마다 다를 수 있습니다.
- 저장소 전역 스타일이 `ul`에 `list-style: none`을 두는데, Safari와 VoiceOver는 이런 목록을 목록으로 알리지 않는다는 보고([WebKit 버그 170179](https://bugs.webkit.org/show_bug.cgi?id=170179))가 있어서 카드가 목록으로 읽히는지부터 봐야 합니다.
- Chrome DevTools Protocol로 가져온 접근성 트리는 `aria-posinset`과 `aria-setsize`를 속성으로 내보내지 않아 확인하지 못했고, 간격 `li`가 목록 항목에서 빠진 것은 확인했습니다.
- 다른 창이나 탭으로 가면 행의 링크에도 blur가 오고 `relatedTarget`이 `null`이라 기억을 지웁니다. 창을 바꾼 동안 목록이 스크롤되면 포커스가 있던 행이 지워질 수 있지만, 실제로 그렇게 되는지는 보지 않았습니다.

## 정리

- 일부만 그린 목록에서 스크린 리더는 DOM에 있는 `li`만 세어서, 항목 수와 순서를 그린 범위에 따라 다르게 읽습니다.
- 행마다 `aria-posinset`(폴더 안 순서에 1을 더한 값)과 `aria-setsize`(받은 폴더 문서 수)를 넣어 스크롤 위치와 관계없이 「100개 중 50번째」처럼 읽게 했습니다.
- 포커스가 있는 요소가 DOM에서 빠지면 `activeElement`가 `body`가 되고, 다시 그린 행은 새 요소라 포커스가 돌아오지 않습니다.
- 포커스 행은 범위를 넓히지 않고 제자리에 그리고, 범위와의 사이를 높이만 채우는 `aria-hidden` 간격 `li` 하나로 메워 행 위치를 지켰습니다.
- 카드의 `onBlur`에서 `relatedTarget`이 카드 밖이면 기억을 지워서, 포커스가 떠나면 다시 화면 근처의 행만 그립니다.
