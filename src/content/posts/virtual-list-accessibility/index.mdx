[1편](/posts/virtualized-document-list/)에서 Knot 문서 목록에 리스트 가상화를 넣어, 보이는 행과 overscan 안의 행만 DOM에 그리게 바꿨습니다. 문서 목록은 폴더마다 폴더 이름 아래 흰 카드가 있고, 카드(`ul`) 안에 문서가 한 줄씩 행(`li`)으로 들어갑니다. 1편에서 방법을 고를 때 직접 구현의 단점으로 「뒤로 가기와 포커스 문제를 직접 풀어야 한다」고 적어 두었는데요, 뒤로 가기는 [4편](/posts/virtual-list-back-navigation/)에서 다뤘고 이번 편에서는 포커스를 포함한 접근성 문제를 다룹니다. 그리지 않은 행이 DOM에 없으니, 화면에는 문제가 없어 보여도 두 가지가 어긋났습니다.

첫째, 화면 낭독기(스크린 리더)가 듣는 순서와 행 수가 틀렸습니다. 브라우저는 카드 안에 있는 `li`만 세어 목록의 항목 수와 순서를 정하는데요, 문서 100개짜리 폴더를 내려 보다 보면 42번째 문서가 「21개 중 1번째」 항목이 됐어요. 둘째, 키보드로 행에 포커스를 둔 채 휠로 스크롤하면 그 행이 DOM에서 지워지면서 포커스가 사라졌습니다.

그래서 행마다 `aria-posinset`과 `aria-setsize`로 폴더 안 순서와 행 수를 직접 넣었고, 포커스가 있는 행은 그릴 범위 밖으로 나가도 제자리에 남겨 두었습니다. **같은 조건에서 다시 재 보니 휠로 4,500px를 내린 뒤에도 포커스는 처음 행의 링크에 그대로 있었고, 그동안 화면이 비어 보인 프레임은 한 장도 없었습니다.** 다만 실제 화면 낭독기로 들어 보는 확인은 아직 하지 못했어요.

## 화면 낭독기는 일부만 그린 목록을 어떻게 읽을까

화면 낭독기는 화면의 픽셀을 읽지 않습니다. 브라우저가 DOM으로 만든 접근성 트리[^a11y-tree]를 읽는데요, 이 트리에서 `ul`은 목록(list), `li`는 목록 항목(listitem)이 됩니다. 그리고 `li`에 따로 적은 값이 없으면, 브라우저는 같은 `ul` 안의 `li`를 세어 항목 수와 몇 번째인지를 정해요[^html-aam].

리스트 가상화를 하기 전에는 카드 안에 폴더의 행이 모두 `li`로 있었으니 이 규칙으로도 맞았습니다. 그런데 가상화한 카드에는 그릴 범위의 `li`만 있고, 위쪽의 그리지 않은 행의 자리는 카드의 `padding-top`으로 비워 둡니다([2편](/posts/virtual-list-row-range/)). 여백은 목록 항목을 만들지 않으니, 브라우저는 그린 `li`만 세게 돼요.

간단한 예를 하나 들어 볼게요. [1편 그림 6](/posts/virtualized-document-list/)의 카드는 문서 4개 가운데 2번째와 3번째 행만 그립니다. 거기 붙은 `aria-posinset`, `aria-setsize`를 빼고 보면 브라우저가 보는 항목은 2개뿐이라, 2번째 문서 「키보드 이동 점검」은 「2개 중 1번째」가 됩니다.

Knot에서는 어떻게 될까요? 통합 테스트와 같은 조건으로 계산해 볼게요. 요약 없는 행 100개짜리 카드이고, 행 높이는 첫 행 64px, 다음 행부터는 구분선 1px를 더한 65px입니다([2편](/posts/virtual-list-row-range/)). 스크롤 영역의 높이는 640px, overscan은 325px예요. 행 번호는 2편처럼 0부터 세고, 「N번째 문서」는 1부터 셉니다.

- 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 있으면 그릴 범위는 `{ start: 41, end: 62 }`라서, 카드에 `li`가 21개 있습니다. 41번 행인 42번째 문서가 「21개 중 1번째」가 돼요.
- 카드 맨 위에서는 그릴 범위가 `{ start: 0, end: 15 }`입니다. 15번째 문서가 「15개 중 15번째」, 곧 마지막 항목이 되니, 목록이 거기서 끝난 것처럼 들리겠죠? 아래에 남은 문서 85개는 항목 수에 들어가지 않습니다.

게다가 넓힌 구간에 걸치는 행 수가 위치마다 20개나 21개로 달라서, 같은 문서를 듣는 동안 스크롤하면 순서와 항목 수가 계속 바뀌었습니다.

## 순서와 행 수는 어떻게 알렸을까

브라우저가 세는 값이 틀리다면, 맞는 값을 직접 알려 주면 됩니다. `aria-setsize`는 집합 전체의 항목 수를, `aria-posinset`은 그 항목이 집합 안에서 몇 번째인지를 1부터 세어 보조 기술에 알리는 속성이에요[^aria-setsize]. MDN도 스크롤에 따라 항목을 불러와 집합의 일부만 DOM에 있을 때 이 두 속성을 쓰라고 안내합니다. 두 속성은 보조 기술에 넘기는 값만 바꾸고, 화면에 보이는 모양은 그대로예요[^wai-aria].

문서 목록에서는 행 컴포넌트 `DocumentRow`가 폴더 안 순서 `index`(0부터)와 폴더의 행 수 `rowCount`를 받아 `li`에 두 속성을 넣게 했습니다.

```tsx title="DocumentRow.tsx"
<Item
  $isFirstRow={index === 0}
  aria-posinset={index + 1}
  aria-setsize={rowCount}
>
```

`index`에는 카드 안에서 몇 번째로 그렸는지가 아니라 폴더 안 순서(`row.index`)를 넘깁니다. 그린 순서를 넘기면 카드의 첫 `li`가 다시 1번째가 되어 고치기 전과 똑같아지고, 같은 `index`로 정하는 첫 행 구분선도 어긋나요.

`rowCount`에는 받은 폴더 문서 배열의 길이 `documents.length`를 넘깁니다. 그린 행 수(위 예에서 21)를 넘기면 42번째 행이 `aria-setsize` 21을 받게 되는데요, `aria-posinset`이 집합 크기보다 커서 WAI-ARIA 규칙에 어긋납니다.

폴더 이름 옆의 문서 수도 쓰지 않았습니다. 이 숫자는 서버가 센 전체 문서 수인데요, 문서 목록은 2,000개까지만 받아 오기 때문에 받지 못한 문서가 있을 수 있어요. 그러면 스크롤해도 나오지 않는 행까지 있는 것처럼 알리게 됩니다.

통합 테스트(jsdom)에서 문서 100개 폴더의 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 오도록 카드 위치를 흉내 내 보니(`viewStart` 3,000), 카드의 첫 `li`는 `aria-posinset` 42, 마지막 `li`는 62를 받았고, 그린 `li`는 모두 `aria-setsize` 100을 받았습니다. 표 1의 고친 뒤 값과 같아요.

## 포커스가 있는 행이 지워지면 어떻게 될까

두 번째 문제는 키보드 사용자에게 생깁니다. Tab으로 폴더의 0번 행 링크에 포커스를 둔 뒤, 마우스 휠로 목록을 내려 읽는다고 해 볼게요. 표 1과 같은 카드에서 0번 행은 카드 맨 위에서 0–64px에 있습니다.

화면 위쪽 끝이 카드 맨 위에서 389px 아래까지 내려오면, 넓힌 구간의 위쪽 끝(389 − 325 = 64px)이 0번 행의 아래쪽 끝과 맞닿아요. 맞닿기만 한 행은 고르지 않으니([2편](/posts/virtual-list-row-range/)) 그릴 범위가 `{ start: 1, end: 21 }`로 바뀌고, React는 0번 행의 `li`를 DOM에서 지웁니다. 포커스가 있던 링크도 함께요.

HTML 표준은 포커스가 있던 요소가 문서에서 빠지면 포커스를 뷰포트로 돌리게 정하고 있습니다[^focus-fixup]. 이때 `document.activeElement`는 `body`가 돼요. 포커스 테두리가 사라지고, Enter를 눌러도 아무 링크도 열리지 않습니다.

다시 위로 스크롤하면 어떨까요? 0번 행이 그릴 범위에 들어오면 React가 `li`를 다시 그리지만, 이건 새로 만든 요소라서 포커스가 돌아오지 않습니다. 포커스를 되돌리는 코드도 없었으니, 키보드 사용자는 있던 위치를 잃게 되는 거예요.

## 포커스가 있는 행은 어떻게 지켰을까

가장 쉬운 방법은 그릴 범위를 포커스가 있는 행까지 넓히는 것입니다. 하지만 그릴 범위는 `start`부터 `end` 앞까지 이어진 구간이라, 넓히면 그 사이 행을 모두 그려야 해요. Knot에서 가장 큰 폴더에는 문서가 994개 있는데요, 요약 없는 행 994개짜리 카드에서 0번 행에 포커스를 두고 900번 행까지 내렸다고 해 볼게요. 스크롤 영역이 640px면 그릴 범위는 `{ start: 895, end: 915 }`입니다. 이걸 0번 행까지 넓히면 행 915개를 그리게 되니, 가상화로 줄인 일을 포커스 하나 때문에 거의 다 되살리는 셈이죠.

그래서 그릴 범위는 그대로 두고, 포커스가 있는 행(아래에서는 「포커스 행」)만 제자리에 하나 더 그렸습니다. 포커스 행과 그릴 범위 사이에 있는 행들은 그리지 않고, 그 행들의 높이를 합한 빈 `li` 하나로 채워요. 이 글에서는 이 `li`를 「간격 `li`」라고 부를게요. 위 예에서도 그리는 행은 그릴 범위의 행 20개와 포커스 행을 더한 21개이고, 0번 행과 그릴 범위 사이는 58,110px 높이의 간격 `li` 하나로 채웁니다.

그림 1은 행 높이를 100px로 단순하게 잡은 카드입니다. 왼쪽은 행을 모두 그린 카드이고, 오른쪽은 그릴 범위가 6–8번 행이고 1번 행에 포커스가 있을 때 그리는 카드예요. 오른쪽에서 위쪽 여백 100px, 1번 행 100px, 간격 `li` 400px을 차례로 쌓으면 6번 행이 왼쪽과 같은 600px에 놓입니다.

그림 1의 오른쪽 카드를 HTML로 적어 보면 아래와 같습니다. 폴더 이름과 문서 제목, 주소는 지어낸 값이에요. 고치기 전에는 그릴 범위의 `li`만 있고 위쪽 여백이 600px라서, 포커스가 있던 1번 행의 `li`와 링크가 함께 빠졌는데요. 고친 뒤에는 위쪽 여백을 1번 행의 위치인 100px로 줄이고, 1번 행과 간격 `li`를 그릴 범위의 행 앞에 둡니다.

```html title="고친 뒤: 같은 위치에서 1번 행과 간격 li를 함께 그림"
<section aria-labelledby="folder-onboarding">
  <div>
    <h3 id="folder-onboarding">온보딩</h3>
    <span>10</span>
  </div>

      <a href="/docs/2">온보딩 2일차 기록</a>
    </li>

      <a href="/docs/7">온보딩 7일차 기록</a>
    </li>
    <!-- 8번째와 9번째 행도 같은 꼴 -->
  </ul>
</section>
```

카드 높이 1000px는 그대로이고, 7번째 문서도 고치기 전과 똑같이 카드 맨 위에서 600px 아래에 놓입니다.

### 그릴 항목은 어떻게 구할까

카드에 그릴 항목을 위에서 아래 차례로 구하는 일은 `getDrawnRows`로 뺐습니다. 항목을 위치 순서대로 늘어놓아야 차례로 쌓았을 때 모두 제자리에 놓이기 때문이에요. 아래는 포커스 행(`keptIndex`)이 그릴 범위 밖에 있을 때의 두 분기이고, `offsets`는 [2편](/posts/virtual-list-row-range/)에서 구한 행 위치 배열입니다.

```ts title="getDrawnRows.ts"
if (keptIndex < start) {
  return {
    firstRowTop: offsets[keptIndex],
    items: [
      row(keptIndex),
      ...gap(offsets[start] - offsets[keptIndex + 1]),
      ...rangeRows,
    ],
  };
}

return {
  firstRowTop: offsets[start],
  items: [
    ...rangeRows,
    ...gap(offsets[keptIndex] - offsets[end]),
    row(keptIndex),
  ],
};
```

포커스 행이 그릴 범위보다 위에 있으면 포커스 행, 간격, 그릴 범위의 행 순서로 쌓고, 아래에 있으면 거꾸로 쌓아요. `firstRowTop`은 카드의 위쪽 여백이 됩니다.

간격의 높이는 두 행 사이에 있는 행들의 높이입니다. 포커스 행이 위에 있다면 포커스 행의 아래쪽 끝(`offsets[keptIndex + 1]`)부터 그릴 범위 첫 행의 위쪽 끝(`offsets[start]`)까지예요. 그림 1에 넣으면 600 − 200 = 400px입니다. 포커스 행의 위쪽 끝부터 재면 포커스 행의 높이가 한 번 더 들어가서, 그릴 범위의 행이 한 행만큼 아래로 밀려요. 구분선 1px는 이미 `offsets`에 들어 있어서 따로 더하지 않았습니다.

`gap()`은 높이가 0이면 빈 배열을 돌려줘서, 포커스 행과 그릴 범위가 맞닿아 있으면 간격 `li`를 만들지 않습니다. 그릴 범위가 비어 있으면 위쪽 여백을 `offsets[keptIndex]`로 두고 포커스 행 하나만 그립니다.

간격을 `div`가 아니라 `li`로 만든 까닭은 HTML 표준이 `ul`의 자식으로 `li`와 `script`, `template`만 허용하기 때문이에요[^ul]. 그 대신 목록 항목이 아니라 높이만 차지하는 요소라서 `aria-hidden`[^aria-hidden]을 붙였습니다.

### 포커스는 어떻게 기억하고 잊을까

카드 컴포넌트 `DocumentFolder`가 포커스 행의 폴더 안 순서를 state로 기억합니다. 행 링크가 포커스를 받으면 `onFocus`에서 그 순서를 저장하고, 포커스가 카드 밖으로 나가면 카드 `ul`의 `onBlur`에서 잊어요.

```tsx title="DocumentFolder.tsx"
const handleCardBlur = (
  event: FocusEvent<HTMLUListElement>,
) => {
  if (!event.currentTarget.contains(event.relatedTarget)) {
    setFocusedIndex(null);
  }
};
```

React의 `onBlur`는 DOM의 blur 이벤트와 달리 버블링해서[^react-blur], 카드의 `onBlur`가 안쪽 링크의 blur를 받을 수 있어요.

`relatedTarget`은 포커스가 다음에 가는 요소입니다[^related-target]. 카드 안의 다른 행으로 가면 기억을 지우지 않고, 다음 행의 `onFocus`가 기억을 바꿔요. 페이지의 빈 곳을 눌러 포커스가 빠지면 `relatedTarget`이 `null`이라 기억을 지우고, 다음 렌더링에서 포커스 행과 간격 `li`가 빠집니다.

### Tab 순서는 어떻게 달라질까

간격 `li` 안에는 링크가 없어서, 그림 1의 1번 행에서 Tab을 누르면 포커스는 DOM에서 다음 링크인 6번 행으로 갑니다. 행을 모두 그린 목록이라면 2번 행으로 갔을 테니 순서는 다르지만, 6번 행은 지금 보고 있는 그릴 범위의 첫 행이에요. 6번 행이 포커스를 받으면 기억도 바뀌어서, 다음 렌더링부터 1번 행과 간격 `li`는 그리지 않습니다.

## 실제 빌드에서는 어떻게 동작했을까

먼저 통합 테스트에서 문서 100개 폴더의 첫 행에 포커스를 두고 `viewStart`를 3,000으로 옮기자, 첫 행과 포커스가 그대로 남았어요. 포커스를 뺀 뒤 다시 스크롤하면 그때는 첫 행이 DOM에서 빠졌습니다.

다음으로 실제 빌드에 1편과 같은 시험용 데이터를 넣고, 첫 카드의 첫 행 링크에 포커스를 둔 뒤 휠로 4,500px를 내렸어요. 행 없이 카드 바탕만 보이는 빈 칸은 [3편](/posts/virtual-list-blank-frames/)과 같은 방법으로 셌습니다. 제가 개발자 도구로 일곱 번 재 보니 매번 결과가 같았습니다.

- 휠을 다 돌린 뒤에도 포커스는 처음 행의 링크에 있었습니다. 그 링크는 창 위쪽 끝보다 4,186px 위, 화면 밖에 있었지만 DOM에서 지워지지 않은 거예요.
- 그동안 화면에 나간 프레임 가운데 빈 칸이 보인 프레임은 0장이었습니다.
- 포커스가 있는 첫 카드는 넓힌 구간에서 벗어나 그릴 범위가 비어 있었어요. 앞에서 본 대로 이때는 간격 `li` 없이 포커스 행 하나만 그립니다.

이 상태에서 Tab을 누르자 포커스는 `aria-posinset`이 13인 행의 링크로 갔고, 그 링크는 창 위쪽 끝에서 411px 아래에 있었습니다. 포커스가 있는 카드에는 행이 하나뿐이라, 다음 링크는 뒤 카드에 그린 행이에요. 행을 모두 그린 목록이라면 같은 폴더의 다음 행으로 갔을 테니, 여기서도 Tab 순서가 다릅니다.

같은 측정에서 개발자 도구로 접근성 트리도 받아 봤는데요. 목록 28개와 목록 항목 20개가 있었지만, 받은 목록 항목에는 `aria-posinset`과 `aria-setsize`에 해당하는 값이 들어 있지 않았습니다. 그래서 브라우저 쪽에서는 두 값을 확인하지 못했어요.

## 아직 확인하지 못한 것은 무엇일까

두 속성의 값은 통합 테스트로만 확인했습니다.

- VoiceOver 같은 실제 화면 낭독기로는 들어 보지 않았습니다. 목록에 들어갈 때 알리는 항목 수가 `li`의 `aria-setsize`를 따르는지는 브라우저와 화면 낭독기 조합마다 다를 수 있어요.
- Knot 전역 스타일은 `ul`에 `list-style: none`을 둡니다. Safari와 VoiceOver가 이런 목록을 목록으로 알리지 않는다는 보고[^webkit]가 있어서, 카드가 목록으로 알려지는지부터 봐야 합니다.
- 간격 `li`가 접근성 트리에서 빠지는지는 아직 재지 않았습니다. 측정에서 접근성 트리를 받기 전에 포커스를 빼서, 그때는 간격 `li`가 없었어요.
- Tab으로 페이지 밖으로 나갈 때처럼 포커스가 페이지를 떠나면 `relatedTarget`이 `null`일 수 있어서, 기억을 지울 수 있습니다. 그동안 목록이 스크롤되면 포커스가 있던 행이 지워질 수 있지만, 실제로 그렇게 되는지는 보지 않았어요.
- Safari와 Firefox, 운영 환경에서는 포커스 동작을 재지 않았습니다.

## 정리

- 일부만 그린 목록에서 브라우저는 카드 안의 `li`만 세어 항목 수와 순서를 정해서, 스크롤 위치에 따라 같은 문서의 순서와 항목 수가 바뀌었습니다.
- 행마다 `aria-posinset`(폴더 안 순서 + 1)과 `aria-setsize`(받은 폴더 문서 수)를 넣어, 3,000px 내린 카드의 행이 42–62번째와 100개를 알리게 했습니다.
- 포커스가 있던 행이 DOM에서 지워지면 포커스는 `body`로 가고, 같은 행을 다시 그려도 돌아오지 않았습니다.
- 그릴 범위를 넓히지 않고 포커스 행만 제자리에 그린 뒤, 그 사이를 높이만 차지하는 간격 `li` 하나로 채워 행 위치를 지켰습니다.
- 실제 빌드에서 휠로 4,500px를 내린 뒤에도 포커스는 행 링크에 있었고 빈 칸 프레임은 0장이었습니다. 다만 Tab 순서는 행을 모두 그린 목록과 다르고, 화면 낭독기로는 아직 들어 보지 않았습니다.
