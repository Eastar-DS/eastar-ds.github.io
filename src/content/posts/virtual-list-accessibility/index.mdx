Knot의 「주제별」 탭은 녹음에서 만든 문서를 AI가 나눈 주제 폴더별로 카드에 묶어 보여 주는 목록(아래에서는 문서 목록)이고, 받은 문서는 모두 메모리에 두되 화면 근처의 행만 DOM에 그리는 리스트 가상화를 라이브러리 없이 넣었습니다([1편](/posts/virtualized-document-list/)). 화면 근처라서 그리는 행 묶음(아래에서는 범위)만 DOM에 두자 접근성 트리(브라우저가 DOM으로 만들어 스크린 리더 같은 보조 기술에 넘기는 트리)의 목록도 범위만큼 줄어서, 문서 100개짜리 폴더의 42번째 문서가 21개짜리 목록의 1번째 항목이 되었고, 키보드 포커스가 있는 행은 화면에서 멀어지면 DOM에서 지워져 포커스를 잃었습니다. 행마다 `aria-posinset`과 `aria-setsize`로 폴더 안 순서와 행 수를 넣고, 포커스가 있는 행은 범위 밖에서도 제자리에 그리면서 범위와의 사이를 높이만 차지하는 `li` 하나로 채웠더니, 실제 빌드에서 휠로 4,500px를 내린 뒤에도 포커스가 행 링크에 있었습니다.

## 일부만 그리면 스크린 리더는 무엇을 알게 될까

브라우저가 그린 `li`만 세어 항목 수와 순서를 정하므로, 스크린 리더도 범위 안의 항목 수와 순서만 받습니다. 스크린 리더는 화면의 픽셀이 아니라 브라우저가 DOM으로 만든 접근성 트리를 읽는데, 접근성 트리에서 `ul`은 목록(list), `li`는 목록 항목(listitem)이 됩니다. HTML 요소가 접근성 API에 어떻게 대응하는지 정한 W3C 문서인 [HTML-AAM](https://www.w3.org/TR/html-aam-1.0/)은 `li`의 집합 크기를 부모 `ul` 안의 `li` 수로 정하고, [MDN의 `aria-setsize` 문서](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-setsize)도 브라우저가 묶음 안의 항목마다 집합 크기와 위치를 저절로 계산한다고 설명합니다. 문서 목록은 카드 `ul`에 범위의 `li`만 두고 그리지 않은 위쪽 행의 높이는 `ul`의 `padding-top`으로 비워 두므로([2편](/posts/virtual-list-row-range/)), 여백은 항목을 만들지 않고 브라우저가 세는 항목 수와 순서도 범위 안에서 정해집니다.

Knot 통합 테스트와 같은 조건(요약 없는 행 100개, 첫 행 64px, 다음 행부터 구분선 1px를 더한 65px, 스크롤 영역 640px, overscan 325px)으로 계산하면, 카드 맨 위에서 3,000px 내려온 화면의 범위는 0부터 센 `{ start: 41, end: 62 }`입니다. 범위는 `start`부터 `end` 앞까지라 카드에 `li`가 21개 있고, 행 번호는 0부터 세며 「N번째」는 1부터 센 순서라서 41번 행인 42번째 문서는 21개 중 1번째 항목이 됩니다. 카드 맨 위에서는 범위가 `{ start: 0, end: 15 }`라 15번째 문서가 15개 중 15번째, 곧 마지막 항목이 되어 목록이 거기서 끝난 것처럼 알려지고, 아래의 문서 85개는 항목 수에 들어가지 않습니다.

범위에 걸치는 행 수도 위치마다 20개나 21개로 달라서, 같은 문서의 순서와 항목 수가 스크롤할 때마다 바뀌었습니다.

## aria-posinset과 aria-setsize로 무엇을 알렸을까

[`aria-setsize`](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-setsize)는 집합 전체의 항목 수를, [`aria-posinset`](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-posinset)은 집합 안에서 몇 번째인지를 1부터 세어 보조 기술에 알리는 속성이고, MDN은 스크롤에 따라 항목을 불러와 집합의 일부만 DOM에 있을 때 두 속성을 쓰라고 안내합니다. [WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/)에 따르면 집합의 요소가 모두 DOM에 있을 때는 두 속성이 필요 없으며, 명세는 접근성 API로 값을 드러내는 일 말고는 브라우저가 평소대로 동작한다고 정해서, 두 속성을 넣어도 스스로 화면에 그리는 것은 없습니다.

문서 목록에서는 행 컴포넌트 `DocumentRow`가 폴더 안 순서 `index`(0부터)와 폴더의 행 수 `rowCount`를 받아 `li`에 두 속성을 넣게 했습니다.

```tsx title="DocumentRow.tsx"
<Item
  $isFirstRow={index === 0}
  aria-posinset={index + 1}
  aria-setsize={rowCount}
>
```

폴더 카드 `DocumentFolder`는 그릴 행 목록의 항목마다 들어 있는 폴더 안 순서 `row.index`를 `index`로, 받은 폴더 문서 배열의 길이 `documents.length`를 `rowCount`로 넘깁니다. 카드 안에서 몇 번째로 그렸는지를 넘기면 카드의 첫 `li`가 다시 1번째가 되고 같은 `index`로 정하는 첫 행 구분선도 어긋나며, 그린 행 수(위 예에서 21)를 `rowCount`로 넘기면 42번째 행이 `aria-setsize` 21을 받아 WAI-ARIA가 정한 「`aria-posinset`은 집합 크기 이하」를 어깁니다.

폴더 이름 옆에 보이는 문서 수는 서버가 센 주제의 전체 문서 수라서 `aria-setsize`에 쓰지 않았습니다. 문서 목록은 문서를 100개씩 20번, 2,000개까지 이어 받으므로 워크스페이스의 문서가 그보다 많으면 받지 못한 문서가 생기는데, 서버의 수를 넘기면 받은 문서보다 큰 항목 수를 알려서, 스크롤해도 나오지 않는 행까지 목록에 있는 것처럼 알려집니다. 카드에 실제로 생길 수 있는 행의 수를 알리려고 `documents.length`를 넘겼습니다.

통합 테스트(jsdom)에서 문서 100개 폴더의 카드 위치를 흉내 내어 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 오게 하자(`viewStart` 3,000), 카드의 첫 `li`는 `aria-posinset` 42, 마지막 `li`는 62를 받았고 그린 `li`는 모두 `aria-setsize` 100을 받아 표 1의 고친 뒤 값과 같았습니다.

## 포커스가 있는 행이 지워지면 어떻게 될까

포커스가 있던 행이 DOM에서 지워지면 포커스는 뷰포트로 돌아가고, 같은 행을 다시 그려도 포커스는 돌아오지 않습니다. 키보드 사용자가 Tab으로 폴더의 0번 행 링크에 포커스를 둔 뒤, 마우스 휠로 목록을 내려 읽는다고 하겠습니다. 0번 행은 카드 맨 위에서 0–64px에 있어서, 스크롤 영역 640px에서 화면 위쪽 끝이 카드 맨 위에서 389px 내려오면 넓힌 구간의 위쪽 끝(389 − 325 = 64px)이 0번 행의 아래쪽 끝과 맞닿고, 범위가 `{ start: 1, end: 21 }`로 바뀌어 0번 행의 `li`가 DOM에서 지워집니다.

[HTML 표준](https://html.spec.whatwg.org/multipage/infrastructure.html#node-remove-focus-fixup)은 포커스가 있던 요소가 문서에서 빠지면 문서의 포커스를 뷰포트로 돌리게 정하고, 포커스가 뷰포트로 돌아간 뒤 [`document.activeElement`](https://html.spec.whatwg.org/multipage/interaction.html#dom-document-activeelement)는 `body`를 돌려줍니다. 다시 위로 스크롤해 0번 행이 범위에 들어오면 React가 `li`를 새로 만들지만, 포커스를 새 링크로 되돌리는 코드는 없었으므로 키보드 사용자는 있던 위치를 잃습니다.

## 포커스가 있는 행은 어떻게 지켰을까

폴더 카드가 포커스가 있는 행의 순서를 state로 기억하고, 포커스 행이 범위 밖에 있으면 제자리에 함께 그리면서 범위와의 사이를 사이 행들의 높이만큼 비운 `li` 하나(아래에서는 간격 `li`)로 채웠습니다. 범위를 포커스 행까지 넓히는 방법도 있지만 범위는 `start`부터 `end` 앞까지 이어진 구간이라, 스크롤 영역 640px에서 문서 994개 폴더의 0번 행에 포커스를 두고 900번 행까지 내리면 화면 근처의 범위 `{ start: 895, end: 915 }`를 0번 행까지 넓혀 행 915개를 그리게 됩니다. 간격 `li`로 채우면 화면 근처의 행 20개와 포커스 행을 더한 21개만 그리고, 0번 행과 범위 사이는 58,110px 높이의 간격 `li` 하나로 채웁니다.

그림 1의 카드를 DOM으로 적으면 아래와 같습니다. 폴더 이름과 문서 제목, 주소는 지어낸 값이고, 행 높이는 그림과 같게 100px로 두었습니다. 포커스 행을 지키기 전에는 범위의 `li`만 있어서, 포커스가 있던 1번 행의 `li`와 링크가 함께 빠집니다.

```html title="고치기 전: 1번 행에 포커스를 두고 6–8번 행까지 스크롤한 뒤"
<section aria-labelledby="folder-onboarding">

    <li aria-posinset="7" aria-setsize="10">
      <a href="/docs/7">온보딩 7일차 기록</a>
    </li>

```

고친 뒤에는 위쪽 여백을 1번 행의 시작 위치인 100px로 줄이고, 1번 행과 간격 `li`를 범위의 행 앞에 둡니다.

```html title="고친 뒤: 같은 위치에서 1번 행과 간격 li를 함께 그림"
<section aria-labelledby="folder-onboarding">
  <div>
    <h3 id="folder-onboarding">온보딩</h3>
    <span>10</span>
  </div>
  <ul style="height: 1000px; padding-top: 100px">
    <li aria-posinset="2" aria-setsize="10">
      <a href="/docs/2">온보딩 2일차 기록</a>
    </li>
    <li aria-hidden="true" style="height: 400px"></li>
    <li aria-posinset="7" aria-setsize="10">
      <a href="/docs/7">온보딩 7일차 기록</a>
    </li>
    <!-- 8번째와 9번째 행도 같은 꼴 -->
  </ul>
</section>
```

그릴 항목을 위에서 아래 차례로 구하는 일은 `getDrawnRows`로 뺐습니다. 아래 코드는 포커스 행(`keptIndex`)이 범위 밖에 있을 때의 두 분기로, `offsets`는 행마다의 시작 위치 배열이고([2편](/posts/virtual-list-row-range/)), 항목 순서가 카드 안의 위치 순서와 같아야 차례로 쌓았을 때 제자리에 놓입니다.

```ts title="getDrawnRows.ts"
if (keptIndex < start) {
  return {
    firstRowTop: offsets[keptIndex],
    items: [
      row(keptIndex),
      ...gap(offsets[start] - offsets[keptIndex + 1]),
      ...rangeRows,
    ],
  };
}

return {
  firstRowTop: offsets[start],
  items: [
    ...rangeRows,
    ...gap(offsets[keptIndex] - offsets[end]),
    row(keptIndex),
  ],
};
```

`gap()`은 높이가 0보다 크면 간격 항목 하나가 든 배열을, 아니면 빈 배열을 돌려주므로 `items`에 펼쳐 넣습니다. 간격의 높이는 포커스 행이 범위보다 위면 포커스 행의 아래쪽 끝 `offsets[keptIndex + 1]`부터 범위 첫 행의 위쪽 끝 `offsets[start]`까지이고, 아래면 범위 마지막 행의 아래쪽 끝 `offsets[end]`부터 포커스 행의 위쪽 끝까지입니다. 그림 1에 넣으면 600 − 200 = 400px이고, 포커스 행의 위쪽 끝부터 재면 포커스 행의 높이가 한 번 더 들어가 범위의 행이 한 행만큼 밀립니다. 구분선 1px은 이미 `offsets`에 들어 있어서 다시 더하지 않았고, 높이가 0이면(포커스 행과 범위가 맞닿으면) 간격 `li`를 만들지 않으며, 범위가 비면 위쪽 여백을 `offsets[keptIndex]`로 두고 포커스 행 하나만 그립니다.

[HTML 표준은 `ul`의 자식으로 `li`와 `script`, `template`만 허용](https://html.spec.whatwg.org/multipage/grouping-content.html#the-ul-element)하므로 간격도 `li`로 만들었고, 목록 항목이 아니라 높이만 차지하는 요소라서 [`aria-hidden`](https://www.w3.org/TR/wai-aria-1.2/#aria-hidden)을 붙였습니다. 포커스는 행 링크가 받은 `onFocus`로 기억하고, 카드 `ul`의 `onBlur`에서 포커스가 카드 밖으로 나가면 잊습니다.

```tsx title="DocumentFolder.tsx"
const handleCardBlur = (
  event: FocusEvent<HTMLUListElement>,
) => {
  if (!event.currentTarget.contains(event.relatedTarget)) {
    setFocusedIndex(null);
  }
};
```

DOM의 [blur 이벤트](https://developer.mozilla.org/en-US/docs/Web/API/Element/blur_event)는 버블링하지 않지만 [React 17부터 `onBlur`는 버블링하는 focusout으로 동작](https://legacy.reactjs.org/blog/2020/08/10/react-v17-rc.html)해서, 카드의 `onBlur`가 안쪽 링크의 blur를 받습니다. [`relatedTarget`](https://developer.mozilla.org/en-US/docs/Web/API/FocusEvent/relatedTarget)은 포커스가 다음에 가는 요소라서, 카드 안의 다른 행으로 가면 기억을 지우지 않고 다음 행의 `onFocus`가 순서를 바꿉니다. 페이지의 빈 곳을 눌러 포커스를 받을 요소 없이 빠지면 `relatedTarget`이 `null`이고 [`contains(null)`](https://dom.spec.whatwg.org/#dom-node-contains)은 거짓을 돌려주므로, 기억을 지운 다음 렌더링에서 포커스 행과 간격 `li`가 빠집니다.

간격 `li` 안에는 링크가 없어서, 그림 1처럼 범위 위쪽에 둔 1번 행에 포커스가 있을 때 Tab을 누르면 DOM 순서에서 다음 링크인 범위의 첫 행, 곧 6번 행으로 갑니다. 행을 모두 그린 목록이라면 다음 링크는 바로 아래 2번 행이라 보던 화면과 떨어져 있지만, 지금은 보던 화면 근처의 6번 행으로 가고, 6번 행의 `onFocus`가 기억을 바꾸면 다음 렌더링에서 1번 행과 간격 `li`는 그리지 않습니다.

## 실제 빌드에서는 어떻게 동작했을까

통합 테스트에서 문서 100개 폴더의 첫 행에 포커스를 두고 `viewStart`가 3,000이 되도록 카드 위치를 바꾸자 첫 행은 DOM에 있었고 포커스도 첫 행에 있었으며, 첫 행에서 blur한 뒤 다시 스크롤하자 첫 행이 DOM에서 빠졌습니다.

2026년 11월 12일에는 포커스 행을 지키는 코드가 들어간 로컬 빌드 두 개(뒤로 가기를 고치기 전과 뒤, [4편](/posts/virtual-list-back-navigation/))를 측정 서버에 띄우고, 1편과 같은 시험용 응답(문서 1,939개, 폴더 28개)으로 Playwright가 띄운 Chrome(창 1200×818, CPU 느리게 하기 없음)에서 쟀습니다. 측정 스크립트는 첫 카드의 첫 행 링크에 포커스를 두고 휠을 150px씩 30번 돌려 `main`의 `scrollTop`을 4,500px로 만들었고, [3편](/posts/virtual-list-blank-frames/)과 같이 행이 덮지 않는 카드 영역을 자홍색으로 칠한 뒤 화면 프레임을 받아 빈 칸을 셌습니다.

- 일곱 번 모두 결과가 같았습니다. 휠을 다 돌린 뒤에도 포커스는 행 링크에 있었고, 링크는 창 위쪽 끝보다 4,186px 위에 있었으며, 받은 프레임 104–115장 가운데 빈 칸이 보인 프레임은 0장이었습니다.
- 포커스가 있는 첫 카드는 넓힌 구간에서 벗어나 범위가 비어 있었고, 앞 절에서 본 대로 범위가 비면 간격 `li` 없이 포커스 행 하나만 그리므로 카드에는 포커스 행 하나만 있었습니다.
- 포커스 행 하나만 그린 상태에서 Tab을 누르자 포커스는 `aria-posinset`이 13인 행의 링크로 갔고, 링크는 창 위쪽 끝에서 411px 아래에 있었으며 `scrollTop`은 4,500px에서 3,795px로 줄었습니다. 브라우저가 포커스를 받은 링크를 화면 안으로 스크롤해서 줄었는지는 따로 확인하지 않았습니다. 포커스 카드에는 행이 하나뿐이라 코드로 따지면 DOM에서 다음 링크는 뒤 카드에 그린 행이고, 행을 모두 그린 목록에서는 같은 폴더의 1번 행이 다음 링크이므로 Tab 순서가 행을 모두 그린 목록과 다릅니다.

같은 측정에서 Chrome DevTools Protocol로 접근성 트리를 받으니 목록이 28개, 목록 항목이 20개 있었지만, 받은 목록 항목에는 `aria-posinset`과 `aria-setsize`에 해당하는 값이 들어 있지 않아 브라우저 쪽에서는 두 값을 확인하지 못했습니다.

## 아직 확인하지 못한 것은 무엇일까

두 속성의 값은 jsdom 통합 테스트로 확인했지만, 실제 스크린 리더로는 들어 보지 않았습니다.

- VoiceOver를 비롯한 스크린 리더로 읽어 보지 않았고, 목록에 들어갈 때 알리는 항목 수가 `li`의 `aria-setsize`를 따르는지는 브라우저와 스크린 리더 조합마다 다를 수 있습니다.
- Knot 전역 스타일이 `ul`에 `list-style: none`을 두는데, Safari와 VoiceOver가 이런 링크 목록을 목록으로 알리지 않는다는 보고([WebKit 버그 170179](https://bugs.webkit.org/show_bug.cgi?id=170179))가 있어서 카드가 목록으로 알려지는지부터 봐야 합니다.
- 간격 `li`에 `aria-hidden`을 붙였지만, 측정 스크립트가 접근성 트리를 받기 전에 포커스를 빼서 간격 `li`가 접근성 트리에서 빠지는지는 아직 재지 않았습니다.
- 다른 창이나 탭으로 가면 `relatedTarget`이 `null`일 수 있어 기억을 지울 수 있고, 그동안 목록이 스크롤되면 포커스가 있던 행이 지워질 수 있지만 실제로 그렇게 되는지는 보지 않았습니다.
- Safari와 Firefox, 운영 앱에서는 포커스 동작을 재지 않았습니다.

## 정리

- 일부만 그린 목록에서 브라우저는 `ul` 안의 `li`만 세어 항목 수와 순서를 정해서, 스크롤 위치에 따라 같은 문서의 순서와 항목 수가 바뀌었습니다.
- 행마다 `aria-posinset`(폴더 안 순서에 1을 더한 값)과 `aria-setsize`(받은 폴더 문서 수)를 넣어, 통합 테스트에서 3,000px 내린 카드의 행이 42–62번째와 100개를 알리게 했습니다.
- 포커스가 있는 요소가 DOM에서 빠지면 `activeElement`가 `body`가 되고, 다시 그린 행으로 포커스를 되돌리는 코드는 없었습니다.
- 포커스 행은 범위를 넓히지 않고 제자리에 그리면서, 범위와의 사이를 높이만 차지하는 `aria-hidden` 간격 `li` 하나로 채워 행 위치를 지켰습니다.
- 실제 빌드에서 휠로 4,500px를 내린 뒤에도 포커스는 행 링크에 있었고 빈 칸 프레임은 0장이었지만, Tab 순서는 행을 모두 그린 목록과 다르고 스크린 리더로는 아직 들어 보지 않았습니다.
