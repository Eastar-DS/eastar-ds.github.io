Knot의 「주제별」 탭은 녹음에서 만든 문서를 AI가 나눈 주제 폴더별로 카드에 묶어 보여 주는 목록(아래에서는 문서 목록)이고, 받은 문서는 모두 메모리에 두되 화면 근처의 행만 DOM에 그리는 리스트 가상화를 라이브러리 없이 넣었습니다([1편](/posts/virtualized-document-list/)). 가상화한 문서 목록을 깊이 스크롤한 뒤 문서를 열었다가 뒤로 돌아오면, 스크롤 위치는 돌아왔지만 화면 대부분이 행 없이 보이는 프레임이 한 장 있었습니다. 스크롤 위치가 한 번에 15,795px 바뀐 뒤 scroll 이벤트에서 구한 새 범위를 React가 페인트 다음 작업으로 미뤄서 생긴 프레임이었고, 마지막으로 그린 행이 화면을 덮지 못할 때만 `flushSync`로 이벤트 안에서 렌더링하게 해서 빈 프레임을 0장으로 줄이면서 휠 스크롤의 프레임 간격은 늘리지 않았습니다.

## 뒤로 가기에서 무엇이 보였을까

스크롤 위치와 누른 행의 위치는 돌아왔지만, 돌아오는 동안 높이 750px인 스크롤 영역의 대부분이 행 없이 카드 바탕으로 보인 프레임이 한 장 있었습니다(세는 방법은 다음 문단). 문서 목록과 문서 보기 화면은 같은 레이아웃 안에서 창이 아니라 `main` 요소가 스크롤하는데, 브라우저가 기록마다 되돌려 주는 스크롤 위치에 문서 목록 화면의 `main`은 들어 있지 않았습니다. 그래서 Knot의 스크롤 복원 훅이 history 항목마다 `main`의 `scrollTop`을 저장해 두었다가, 뒤로 가기로 돌아오면 [`useLayoutEffect`](https://react.dev/reference/react/useLayoutEffect) 안에서 한 번에 되돌립니다. 문서 목록은 행을 일부만 그려도 카드 높이를 행을 모두 그린 높이로 두므로([2편](/posts/virtual-list-row-range/)), 목록 응답이 있으면 화면이 바뀐 첫 커밋에서 15,795px 같은 깊은 위치까지 한 번에 갑니다.

2026년 11월 12일에 가상화는 했지만 뒤로 가기를 고치기 전인 빌드(커밋 `95436b0d`까지, 아래에서는 고치기 전 빌드이며 3편의 가상화 전 빌드와 다름)를 로컬 측정 서버에 띄우고, [3편](/posts/virtual-list-blank-frames/)과 같이 행이 덮지 않는 카드 영역을 자홍색으로 칠한 뒤 Chrome DevTools Protocol의 [`Page.startScreencast`](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast)로 화면에 합성된 프레임을 PNG 이미지로 받아 자홍색 가로줄을 셌습니다. 측정 스크립트는 휠을 150px씩 돌려 `scrollTop`을 15,795px로 만들고, 화면 안의 행을 눌러 문서 보기로 간 뒤 0.8초 머물렀다가 뒤로 가기를 누르고 2.5초 동안 프레임을 받았습니다. 같은 빌드로 세 번 재니 받은 프레임 156–158장 가운데 매번 1장에서 자홍색 PNG 가로줄이 622줄 보였고(PNG 가로줄과 CSS px의 비율은 3편과 같이 확인하지 못함), 2.5초 뒤 `scrollTop`은 15,795px, 누른 행은 창 위쪽 끝에서 170px로 누르기 전과 같았습니다.

## 왜 한 프레임이 비었을까

범위 계산은 맞았지만, scroll 이벤트에서 부른 `setState`를 React가 페인트 다음 작업에서 렌더링해서 화면이 먼저 이전 행으로 그려졌기 때문입니다. 순서를 따라가려면 브라우저와 React가 일을 처리하는 때를 알아야 합니다. 작업(task)은 브라우저가 하나씩 꺼내 처리하는 일 단위이고 화면 갱신은 작업과 작업 사이에 들어가며, 마이크로태스크는 지금 실행 중인 일이 끝나자마자 다음 작업이나 화면 갱신보다 먼저 처리하는 일입니다.

- 브라우저는 화면을 그릴 때가 되면 [HTML 표준의 화면 갱신 단계(update the rendering)](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering)에서 scroll 이벤트 보내기, `requestAnimationFrame` 콜백, 스타일 계산과 레이아웃, `ResizeObserver` 알림, 페인트를 차례로 합니다. [CSSOM View 규격](https://drafts.csswg.org/cssom-view/)에서 스크립트가 `scrollTop`을 바꾼 스크롤도 scroll 이벤트를 대기 목록에 넣기만 하므로, 이벤트는 다음 화면 갱신 단계의 앞부분에 옵니다.
- React는 `setState`를 받으면 업데이트의 우선순위로 렌더링할 때를 정합니다. React 19.2.8의 react-dom 코드에서 click이나 keydown 안의 업데이트는 이벤트가 끝난 뒤의 마이크로태스크에서 렌더링하고, scroll이나 wheel처럼 연달아 오는 이벤트 안의 업데이트는 연속 이벤트 우선순위(`ContinuousEventPriority`)라서, React가 렌더링할 때를 정하는 내부 패키지 Scheduler가 만든 다음 작업에서 렌더링합니다.
- `useLayoutEffect` 안에서 부른 `setState`는 페인트 전에 처리됩니다. [`flushSync`](https://react.dev/reference/react-dom/flushSync)는 콜백 안의 업데이트를 동기로 렌더링해 DOM을 바로 갱신하고, React 19.2.8 코드에서는 React 커밋(렌더링 결과를 DOM에 반영하는 단계) 안의 `useLayoutEffect`까지 돌린 뒤에 돌아옵니다.

그래서 click 안의 업데이트는 다음 화면 갱신 전에 렌더링되지만, scroll 안의 업데이트는 같은 화면 갱신의 페인트가 끝난 뒤 다음 작업에서 렌더링됩니다. 그림 1에서는 「화면 갱신 1」의 페인트가 React 렌더링보다 앞에 오는지를 고치기 전과 고친 뒤로 견주면 됩니다.

그림의 「화면 갱신 1」에서 페인트할 때의 카드 DOM은 아래와 같습니다. 폴더 이름과 문서 제목은 지어낸 값이고, 행 높이는 실제 값(요약 없는 첫 행 64px, 다음 행부터 구분선 1px를 더한 65px)으로 계산했습니다.

```html title="고치기 전: 화면 갱신 1의 페인트 때"
<main>
  <section aria-labelledby="folder-weekly">
    <div>
      <h3 id="folder-weekly">주간 회의</h3>
      <span>100</span>
    </div>
    <!-- 높이: 100행 6,499px, 그린 행 없음 -->
    <ul style="height: 6499px; padding-top: 0"></ul>
  </section>
</main>
```

고친 뒤에는 같은 화면 갱신 단계 안에서 `flushSync`가 새 범위를 커밋하므로, 페인트할 때 카드에는 0부터 센 7–28번 행이 들어 있습니다.

```html title="고친 뒤: flushSync로 7–28번 행을 커밋한 뒤"
<main>
  <section aria-labelledby="folder-weekly">
    <div>
      <h3 id="folder-weekly">주간 회의</h3>
      <span>100</span>
    </div>
    <!-- 높이: 100행 6,499px, 위쪽 여백: 7번 행 시작 454px -->
    <ul style="height: 6499px; padding-top: 454px">
      <li aria-posinset="8" aria-setsize="100">
        <a href="/docs/8">회의 기록 8</a>
      </li>
      <li aria-posinset="9" aria-setsize="100">
        <a href="/docs/9">회의 기록 9</a>
      </li>
      <!-- 9–27번 행(aria-posinset 10–28) 생략 -->
      <li aria-posinset="29" aria-setsize="100">
        <a href="/docs/29">회의 기록 29</a>
      </li>
    </ul>
  </section>
</main>
```

고치기 전 코드에서 범위 계산은 두 번 다 맞았습니다. 처음 계산은 스크롤 위치를 되돌리기 전, 곧 카드가 화면보다 15,000px 아래에 있을 때 했으니 빈 범위 `{ start: 0, end: 0 }`이 맞고, scroll 이벤트에서 화면 795–1,545px를 위아래로 325px씩 넓힌 470–1,870px에 걸친 행을 고른 `{ start: 7, end: 29 }`도 맞았습니다(`end`는 그린 마지막 행의 다음 번호). 그러나 React가 두 번째 결과를 페인트 다음 작업에서 렌더링해서, 화면 갱신 1의 페인트는 위 첫 번째 DOM으로 카드의 795–1,545px를 그렸습니다. 휠 스크롤에서도 scroll 이벤트의 업데이트는 같은 방식으로 미뤄지지만, 휠 한 번에 움직이는 거리(측정에서는 150px와 300px)가 미리 그려 둔 325px보다 짧아서 이전 행이 화면을 덮습니다.

## 모든 scroll 이벤트에 flushSync를 걸면 어떻게 됐을까

뒤로 가기 빈 프레임은 0장이 되었지만, 휠 스크롤 프레임 간격의 99% 값이 고치기 전 빌드의 11.9ms에서 16.6ms(150px 휠), 17.3ms(300px 휠)로 늘었습니다. 처음에는 scroll 이벤트와 크기 변화 알림에서 범위를 바꿀 때마다 `applyRange`를 `flushSync`로 감쌌고, 뒤로 가기를 두 번 재니 두 번 모두 빈 칸 프레임이 0장이었습니다. 휠 측정은 3편과 같은 방법(CPU 4배 느림, 휠을 150px 또는 300px씩 150번)으로 했고, 프레임 간격은 `requestAnimationFrame` 콜백 사이의 시간이며 11월 12일 측정에서도 간격의 가운데값은 8ms 안팎이었습니다. 최대값도 13ms(150px 휠)와 15ms(300px 휠)에서 20ms와 18ms로 늘었습니다.

어디에 시간이 들었는지 프로파일로 나눠 보지는 않았고, 코드에서 보이는 차이는 아래와 같습니다.

- 문서 목록은 폴더 카드마다 훅이 `main`에 scroll 처리기를 하나씩 붙여서, 폴더가 28개인 측정 데이터에서는 처리기가 28개입니다. 미루면 scroll 이벤트 한 번에서 범위가 바뀐 카드들의 업데이트를 React가 다음 작업에서 함께 렌더링하고 한 번 커밋하지만, `flushSync`는 카드의 처리기마다 렌더링과 커밋을 끝내고 돌아와서 커밋도 여러 번 합니다.
- 다음 카드의 처리기는 `getBoundingClientRect`로 카드 위치를 재는데, 앞 카드의 커밋으로 DOM이 바뀐 뒤에 위치를 읽으면 브라우저가 레이아웃을 앞당겨 계산하게 할 수 있습니다([강제 동기 레이아웃](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)). 미룰 때는 28개 처리기가 같은 레이아웃을 읽습니다.
- 이런 일이 모두 화면 갱신 단계 안에서 페인트보다 앞에 일어나서, 범위가 바뀌는 프레임마다 페인트가 그만큼 늦어집니다.

## 언제만 flushSync를 쓰게 했을까

마지막으로 그린 행이 화면에 보이는 카드 부분을 덮지 못할 때만 `flushSync`를 쓰게 했습니다. 스크롤은 나빠지면 안 되는 항목이었고, scroll 이벤트를 받은 때 DOM에 있는 행은 마지막으로 커밋한 범위의 행이므로 마지막으로 그린 행이 화면을 덮으면 이번 프레임을 이전 행으로 그려도 빈 칸이 없습니다. 아래 처리기는 덮을 때는 업데이트를 미루고, 덮지 못할 때만 이벤트 안에서 렌더링합니다.

```ts title="useVisibleRowRange.ts" {5,9}
const handleViewChange = () => {
  const view = measureView();
  const { start, end } = drawnRangeRef.current;

  if (isViewCovered({ offsets, start, end, ...view })) {
    applyRange(getRange(view));
    return;
  }
  flushSync(() => applyRange(getRange(view)));
};
```

판정 함수 `isViewCovered`는 화면과 카드가 겹치는 구간이 그린 행 안에 들어가는지 봅니다.

```ts title="isViewCovered.ts"
const cardHeight = offsets[offsets.length - 1];
const visibleTop = Math.max(viewStart, 0);
const visibleBottom = Math.min(viewEnd, cardHeight);

if (visibleBottom <= visibleTop) return true;
if (start === end) return false;

return (
  offsets[start] <= visibleTop &&
  visibleBottom <= offsets[end]
);
```

`viewStart`와 `viewEnd`는 카드 맨 위를 0으로 둔 화면 위쪽 끝과 아래쪽 끝이고, `offsets`는 행마다의 시작 위치 배열입니다([2편](/posts/virtual-list-row-range/)). 카드 위쪽 끝보다 위는 폴더 제목 같은 카드 밖이라 행이 없어도 빈 칸이 아니므로 0으로 자르고, 카드가 화면 밖이라 겹치는 구간이 없으면 덮을 곳이 없어 참을 돌려줍니다. 판정은 이벤트가 scroll인지 크기 변화인지, 휠인지 뒤로 가기인지를 보지 않고 위치만 봅니다. 예를 들어 그림 1의 카드에서 화면 위쪽 끝이 3,000px일 때 그린 `{ start: 41, end: 63 }`은 2,664–4,094px를 덮으므로, 화면 아래쪽 끝(3,750px)보다 344px를 더 덮어 휠 300px까지는 렌더링을 미루고, 350px부터는 화면 아래쪽 끝 4,100px를 덮지 못해 `flushSync`를 씁니다.

마지막으로 커밋한 범위는 state가 아니라 ref(`drawnRangeRef`)에 `useLayoutEffect`로 담아 읽습니다. 처리기를 붙이는 effect는 행 위치가 바뀔 때만 다시 돌아서, 처리기 안에서 state를 읽으면 effect를 만든 첫 렌더링의 `{ start: 0, end: 0 }`만 보게 되고, 카드가 보이는 동안 판정이 늘 거짓이 되어 모든 scroll 이벤트에 `flushSync`를 건 것과 같아집니다. `flushSync`는 `useLayoutEffect`까지 돌린 뒤에 돌아오므로, 처리기가 다음에 불릴 때 ref에는 벌써 새 범위가 들어 있습니다.

## 고친 뒤 무엇이 달라졌을까

고른 빌드는 뒤로 가기 빈 칸 프레임이 0장이었고, 휠 스크롤 프레임 간격의 99% 값은 함께 잰 고치기 전 빌드와 1ms 안쪽으로 차이가 났으며 최대값은 같거나 작았습니다. 세 빌드 모두 2026년 11월 12일에 뒤로 가기와 휠 스크롤을 항목마다 같은 측정 스크립트로 쟀고, 휠 스크롤의 빈 칸 프레임은 세 빌드 모두 0장이었습니다.

## 아직 확인하지 못한 것은 무엇일까

뒤로 가기 말고도 스크롤 위치가 한 번에 크게 바뀌는 경우가 있는데, 아래 경우는 실제 빌드에서 재지 않았습니다.

- 내용이 아직 짧아 스크롤 복원 훅이 `requestAnimationFrame` 콜백에서 위치를 되돌리는 경우는 재지 않았습니다. 화면 갱신 단계에서 scroll 이벤트는 rAF 콜백보다 먼저 보내지므로, rAF 콜백에서 바뀐 위치의 scroll 이벤트는 다음 프레임에 오고 다음 프레임 전의 페인트는 이전 범위로 그려질 수 있습니다. 위 측정은 문서 보기에 0.8초 머문 뒤 돌아온 경우입니다.
- 창을 키워 `main`이 높아질 때도 `ResizeObserver` 콜백 안의 업데이트가 다음 작업으로 미뤄져서 scroll과 같은 처리기를 쓰게 했지만, 코드와 표준의 순서로 따진 것이고 실제 빌드에서 재지는 않았습니다.
- 스크롤바를 끌어 멀리 이동하는 동작에서 합성기 스레드가 먼저 그리는 프레임까지 막는지는 확인하지 않았습니다.
- 측정 결과 파일에는 빌드 이름이 적혀 있지 않아서, 표 1에서 어느 결과가 어느 빌드인지는 팀 보고 원고에 적은 대응을 따랐습니다.

## 정리

- 뒤로 가기의 빈 프레임은 범위 계산이 틀려서가 아니라, React가 scroll 이벤트 안의 업데이트를 연속 이벤트 우선순위로 보고 페인트 다음 작업에서 렌더링해서 생겼습니다.
- 휠 한 번은 미리 그려 둔 325px 안쪽이라 이전 행이 화면을 덮지만, 15,795px를 한 번에 바꾸는 뒤로 가기는 덮지 못합니다.
- 모든 scroll 이벤트에 `flushSync`를 걸면 빈 프레임은 사라졌지만, 카드마다 커밋과 레이아웃이 페인트 앞에서 일어나 휠 스크롤 프레임 간격의 99% 값이 16.6–17.3ms로 늘었습니다.
- 마지막으로 그린 행이 화면에 보이는 카드 부분을 덮지 못할 때만 `flushSync`를 써서, 뒤로 가기 빈 프레임 0장과 고치기 전과 비슷한 휠 프레임 간격을 함께 얻었습니다.
- 마지막으로 그린 범위는 effect 안의 처리기가 첫 렌더링의 state를 보지 않도록 ref에 담아 읽습니다.
