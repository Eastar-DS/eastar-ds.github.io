[1편](/posts/virtualized-document-list/)에서 Knot 문서 목록에 리스트 가상화를 넣어, 보이는 행과 overscan 안의 행만 DOM에 그리게 바꿨습니다. 문서 목록은 폴더마다 폴더 이름 아래 흰 카드가 있고, 카드 안에 문서가 한 줄씩 행으로 들어가는데요. 카드 높이는 행을 모두 그린 높이로 고정해 두고, 그리지 않은 행의 자리는 비워 둡니다.

그런데 목록을 한참 내려 문서 하나를 열었다가 뒤로 가기로 돌아오면, 스크롤 위치는 제자리로 돌아오는데 그 사이 한 프레임 동안 화면이 거의 다 비어 보였습니다. 이 글에서도 [3편](/posts/virtual-list-blank-frames/)처럼 행 없이 카드 바탕만 보이는 부분을 「빈 칸」이라고 부를게요. 3편에서는 overscan을 325px로 두어 휠 스크롤의 빈 칸을 막았는데요, 뒤로 가기는 스크롤 위치가 한 번에 15,795px나 바뀌니 overscan으로는 덮을 수 없었습니다.

제가 개발자 도구로 재 보니 뒤로 가기를 세 번 하는 동안 매번 한 프레임씩 화면 대부분이 빈 칸이었어요. 원인은 그릴 범위 계산이 아니라 React가 렌더링하는 때에 있었습니다. 범위는 맞게 구했지만, React가 scroll 이벤트에서 받은 업데이트를 화면을 그린 다음으로 미뤄서 그 한 프레임은 이전 행으로 그려졌던 거예요.

그래서 지금 그려 둔 행이 화면을 덮지 못할 때만 React의 `flushSync`로 scroll 이벤트 안에서 바로 렌더링하게 했습니다. **같은 조건에서 다시 재 보니 뒤로 가기의 빈 칸 프레임은 0장이 됐고, 휠 스크롤의 프레임 간격은 고치기 전과 1ms 안쪽으로만 달랐습니다.**

## 뒤로 가기에서 무엇이 보였을까

Knot의 문서 목록과 문서 보기 화면은 창 전체가 아니라 그 안의 `main` 요소가 스크롤하는데요. 브라우저는 뒤로 가기에서 창의 스크롤 위치는 되돌려 주지만, Knot에서 `main` 안의 스크롤 위치는 돌아오지 않았습니다. 그래서 Knot에는 스크롤 위치를 직접 되돌리는 훅이 있어요. 기록(history) 항목마다 `main`의 `scrollTop`을 저장해 두었다가, 뒤로 가기로 돌아오면 목록을 그린 직후 화면을 그리기 전에(`useLayoutEffect`[^layout-effect]) 저장한 위치로 한 번에 옮깁니다.

이때 행은 아직 하나도 그리지 않았지만 카드 높이는 행을 모두 그린 높이라서, 스크롤할 수 있는 공간은 처음부터 다 있습니다. 그래서 15,795px처럼 깊은 위치로도 바로 옮길 수 있어요.

빈 칸은 [3편](/posts/virtual-list-blank-frames/)과 같은 방법으로 셌습니다. 측정할 때만 카드 바탕을 자홍색, 행 바탕을 흰색으로 칠하고, 화면에 나간 프레임을 한 장씩 받아 자홍색이 보이는 프레임을 세는 거예요. 목록을 15,795px까지 내린 뒤 화면에 보이는 문서를 열었다가 뒤로 가기로 돌아오는 동안 프레임을 받았습니다.

세 번 재 보니 매번 받은 프레임 가운데 한 장에서 화면 대부분이 자홍색이었습니다. 그 뒤 프레임에는 행이 다시 보였고, 스크롤 위치와 누른 행의 위치도 문서를 열기 전과 같았어요. 위치를 되돌리는 일은 제대로 했는데, 돌아오는 길에 빈 칸이 한 프레임 보인 거예요.

## 왜 한 프레임이 비었을까

순서를 따라가려면 브라우저가 화면을 언제 그리는지부터 알아야 합니다. 메인 스레드는 일을 작업(task) 단위로 하나씩 꺼내 처리하고, 작업과 작업 사이에 화면을 다시 그립니다[^task]. 이 글에서는 화면을 다시 그리는 이 단계를 「화면 갱신」이라고 부를게요. 화면 갱신에서 브라우저는 scroll 이벤트를 보내고, `requestAnimationFrame` 콜백을 부르고, 스타일과 레이아웃을 계산한 뒤 페인트합니다[^update-rendering]. scroll 이벤트가 같은 화면 갱신의 페인트보다 먼저 오니, 이벤트 안에서 DOM을 바꾸면 그 프레임에 바로 반영할 수 있어요.

React는 `setState`를 받아도 바로 렌더링하지 않고, 어떤 이벤트에서 받았는지에 따라 렌더링할 때를 정합니다[^priority]. 클릭이나 키 입력에서 받은 업데이트는 이벤트 처리가 끝나자마자, 다음 화면 갱신 전에 렌더링해요. 반면 scroll이나 wheel처럼 연달아 오는 이벤트에서 받은 업데이트는 다음 작업으로 미룹니다.

이제 뒤로 가기를 따라가 볼게요. 목록 맨 위에서 15,000px 아래에 요약 없는 행 100개짜리 카드가 있고, `main`의 보이는 높이는 750px, 돌아갈 위치는 15,795px라고 해 보겠습니다. 행 번호는 [2편](/posts/virtual-list-row-range/)처럼 0부터 세고, 그릴 범위 `{ start, end }`의 `end`는 그 뒤로 그리지 않는 첫 행 번호예요.

1. 뒤로 가기를 누르면 React가 문서 목록을 그리고 커밋합니다. 이때 카드도 그릴 범위를 구하는데, `scrollTop`은 아직 0이라 카드가 화면보다 15,000px 아래에 있어요. 그래서 그릴 범위는 `{ start: 0, end: 0 }`, 그릴 행이 없습니다.
2. 같은 커밋에서 스크롤 복원 훅이 `scrollTop`을 15,795px로 옮깁니다. 이제 화면은 카드의 795–1,545px를 보여 줘야 해요.
3. 화면 갱신이 시작되고 브라우저가 scroll 이벤트를 보냅니다. 스크립트로 `scrollTop`을 바꿔도 scroll 이벤트는 다음 화면 갱신에서 와요[^cssom-scroll]. 카드마다 이 이벤트에 그릴 범위를 다시 구하는 함수(아래에서는 처리기)가 달려 있는데요, 처리기는 화면 795–1,545px를 위아래로 overscan 325px만큼 넓힌 470–1,870px에 걸친 행을 골라, 그릴 범위 `{ start: 7, end: 29 }`를 구하고 `setState`를 부릅니다.
4. React는 scroll 이벤트에서 받은 이 업데이트를 다음 작업으로 미룹니다. 브라우저는 기다리지 않고 레이아웃과 페인트를 이어 가는데, 카드에는 아직 행이 하나도 없어요. 이 프레임이 빈 칸으로 가득한 프레임입니다.
5. 다음 작업에서 React가 7–28번 행을 렌더링하고 커밋해, 다음 화면 갱신부터 행이 보입니다.

범위 계산은 두 번 다 맞았습니다. 1번에서 카드는 정말 화면 밖에 있었고, 3번에서 구한 범위도 화면을 덮는 행이었어요. 문제는 3번에서 구한 범위가 4번의 페인트에 늦었다는 점입니다. 그림 1의 「고치기 전」이 이 순서이고, 「화면 갱신 1」에서 페인트가 React의 렌더링보다 앞에 오는 걸 볼 수 있어요.

4번에서 페인트할 때 카드의 DOM은 아래와 같습니다. 폴더 이름과 문서 제목은 지어낸 값이고, 행 높이는 실제 값으로 계산했어요. 요약 없는 첫 행은 64px, 다음 행부터는 구분선 1px를 더해 65px입니다([2편](/posts/virtual-list-row-range/)).

```html title="고치기 전: 화면 갱신 1의 페인트 때"
<main>
  <section aria-labelledby="folder-weekly">
    <div>
      <h3 id="folder-weekly">주간 회의</h3>
      <span>100</span>
    </div>
    <!-- 높이: 100행 6,499px, 그린 행 없음 -->
    <ul style="height: 6499px; padding-top: 0"></ul>
  </section>
</main>
```

카드 높이 6,499px는 그대로라 스크롤 위치는 맞지만, 카드 안에 그린 행이 하나도 없습니다. 화면에 보이는 카드의 795–1,545px가 모두 빈 칸인 거죠.

그럼 휠 스크롤은 왜 괜찮았을까요? 휠 스크롤에서도 scroll 이벤트의 업데이트는 똑같이 다음 작업으로 미뤄집니다. 다만 휠 한 번에 움직이는 거리(측정에서는 150px와 300px)가 overscan 325px보다 짧아서, 미뤄지는 동안에도 이전에 그려 둔 행이 화면을 덮어요. 뒤로 가기는 15,795px를 한 번에 옮기니 이전 행으로는 덮을 수 없습니다.

## 모든 scroll 이벤트에 flushSync를 걸면 어떻게 됐을까

React가 업데이트를 미루지 않게 하는 방법이 있는데요, `flushSync`[^flushsync]입니다. 콜백 안의 업데이트는 미루지 않고 렌더링해서, DOM까지 바꾼 뒤에 돌아와요. 처음에는 scroll 이벤트와 크기 변화 알림에서 그릴 범위를 바꿀 때마다 `flushSync`로 감쌌습니다. 뒤로 가기를 두 번 재 보니 두 번 모두 빈 칸 프레임이 0장이었어요.

그런데 이번에는 휠 스크롤이 나빠졌습니다. 3편과 같은 방법으로 휠 스크롤 동안의 프레임 간격을 재 보니, 99% 값[^p99]이 고치기 전 11.9ms에서 16.6ms(150px 휠), 17.3ms(300px 휠)로 늘었어요. 가장 긴 간격도 13ms와 15ms에서 20ms와 18ms가 됐습니다. 휠 스크롤은 나빠지면 안 되는 항목이라 이대로 둘 수는 없었어요.

어디에 시간이 들었는지 프로파일로 나눠 보지는 않았는데요, 코드로 보면 짐작 가는 곳이 있습니다.

- 그릴 범위는 카드마다 따로 구해서, 카드마다 `main`에 scroll 처리기가 하나씩 붙습니다. 폴더가 28개인 측정 데이터에서는 처리기가 28개예요. 업데이트를 미루면 React가 범위가 바뀐 카드들을 다음 작업에서 한꺼번에 렌더링할 수 있지만, `flushSync`는 처리기마다 렌더링과 커밋을 끝내고 돌아와서 커밋도 여러 번 합니다.
- 다음 카드의 처리기는 `getBoundingClientRect`로 카드 위치를 재는데요. 앞 카드의 커밋으로 DOM이 바뀐 뒤에 위치를 물으면, 브라우저가 레이아웃을 앞당겨 다시 계산해야 할 수 있습니다[^forced-layout]. 미룰 때는 28개 처리기가 모두 같은 레이아웃을 읽어요.
- 이런 일이 모두 화면 갱신 안에서 페인트보다 먼저 일어나서, 범위가 바뀌는 프레임마다 페인트가 그만큼 늦어집니다.

## 그럼 flushSync는 언제만 써야 할까

scroll 이벤트를 받은 때 DOM에 있는 행은 마지막으로 커밋한 그릴 범위의 행입니다. 이 행이 화면을 덮고 있다면, 업데이트를 미뤄서 이번 프레임을 이전 행으로 그려도 빈 칸은 없어요. 휠 스크롤이 대부분 그렇죠. 렌더링을 기다릴 수 없는 경우는 뒤로 가기처럼 이전 행이 화면을 덮지 못할 때예요. 그래서 처리기가 먼저 지금 그린 행이 화면을 덮는지 보고, 덮지 못할 때만 `flushSync`를 쓰게 했습니다.

```ts title="useVisibleRowRange.ts" {5,9}
const handleViewChange = () => {
  const view = measureView();
  const { start, end } = drawnRangeRef.current;

  if (isViewCovered({ offsets, start, end, ...view })) {
    applyRange(getRange(view));
    return;
  }
  flushSync(() => applyRange(getRange(view)));
};
```

덮는지는 `isViewCovered`가 봅니다.

```ts title="isViewCovered.ts"
const cardHeight = offsets[offsets.length - 1];
const visibleTop = Math.max(viewStart, 0);
const visibleBottom = Math.min(viewEnd, cardHeight);

if (visibleBottom <= visibleTop) return true;
if (start === end) return false;

return (
  offsets[start] <= visibleTop &&
  visibleBottom <= offsets[end]
);
```

`offsets`는 [2편](/posts/virtual-list-row-range/)에서 구한 행 위치의 배열이고, 마지막 값은 카드 높이예요. `viewStart`와 `viewEnd`도 2편처럼 화면 위쪽 끝과 아래쪽 끝이 카드 맨 위에서 몇 px 아래에 있는지입니다. 판정은 세 단계로 합니다.

1. 화면 가운데 카드와 겹치는 구간만 봅니다. 카드 위쪽 끝보다 위는 폴더 이름 같은 카드 밖이라, 행이 없어도 빈 칸이 아니니까요.
2. 겹치는 구간이 없으면 카드가 화면 밖에 있으니 덮을 곳도 없습니다. 그래서 참을 돌려줘요.
3. 카드가 보이는데 그린 행이 없으면 거짓입니다. 그린 행이 있으면, 그린 첫 행의 위치부터 그린 마지막 행의 아래쪽 끝(`offsets[end]`)까지가 겹치는 구간을 감싸는지 봅니다.

그림 1의 카드로 예를 들어 볼게요. 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 있으면 그릴 범위는 `{ start: 41, end: 63 }`이고, 그린 행은 2,664–4,094px를 덮습니다. 화면 아래쪽 끝(3,750px)보다 344px를 더 덮고 있는 거죠. 그래서 휠 한 번에 300px를 움직이면 화면 아래쪽 끝이 4,050px라 덮고 있으니 렌더링을 미루고, 350px를 움직이면 4,100px까지 덮지 못하니 `flushSync`를 씁니다. 판정은 이벤트가 scroll인지 크기 변화인지, 휠인지 뒤로 가기인지 보지 않고 위치만 봐요.

뒤로 가기에서는 앞 절 1번에서 그린 행이 없었으니, 3번의 처리기가 `flushSync`를 씁니다. 그래서 그림 1의 「고친 뒤」처럼 화면 갱신 1의 페인트 전에 7–28번 행이 커밋되고, 그 프레임부터 행이 보여요.

마지막으로 커밋한 그릴 범위는 state가 아니라 ref(`drawnRangeRef`)에 담아 읽습니다. 처리기는 effect 안에서 만든 함수라서 행 위치가 바뀔 때만 새로 만들어지는데요. 처리기 안에서 state를 바로 읽으면 처리기를 만든 첫 렌더링의 `{ start: 0, end: 0 }`만 보게 됩니다. 그러면 카드가 보이는 동안 판정이 늘 거짓이 되어, 모든 scroll 이벤트에 `flushSync`를 건 것과 같아져요. 그래서 커밋할 때마다 `useLayoutEffect`에서 ref를 새 범위로 바꿔 둡니다. `flushSync`도 `useLayoutEffect`까지 돌린 뒤에 돌아오므로, 처리기가 다음에 불릴 때 ref에는 이미 새 범위가 들어 있어요.

## 얼마나 달라졌을까

같은 조건에서 세 빌드를 다시 재 보니, 덮지 못할 때만 `flushSync`를 쓴 빌드는 뒤로 가기의 빈 칸 프레임이 0장이었습니다. 휠 스크롤 프레임 간격의 99% 값은 고치기 전 빌드와 1ms 안쪽으로만 달랐고, 가장 긴 간격은 같거나 짧았어요. 휠 스크롤의 빈 칸 프레임은 세 빌드 모두 0장이었습니다.

## 아직 확인하지 못한 경우

뒤로 가기 말고도 스크롤 위치가 한 번에 크게 바뀌는 경우가 있는데요, 아래 경우는 재지 않았습니다.

- 목록을 다시 불러오는 중이라 아직 돌아갈 위치만큼 길지 않으면, 스크롤 복원 훅은 내용이 길어질 때까지 기다렸다가 `requestAnimationFrame` 콜백에서 위치를 되돌립니다. 화면 갱신에서 scroll 이벤트는 rAF 콜백보다 먼저 오니, 이때 바뀐 위치의 scroll 이벤트는 다음 화면 갱신에 와요. 그 사이 페인트는 이전 범위로 그려질 수 있습니다.
- 창을 키워 `main`이 높아질 때도 `ResizeObserver` 콜백의 업데이트가 다음 작업으로 미뤄져서 같은 처리기를 쓰게 했지만, 코드와 표준의 순서로 따진 것이고 재지는 않았습니다.
- 스크롤바를 끌어 멀리 옮기는 동작에서, 합성기 스레드가 먼저 내보내는 프레임([3편](/posts/virtual-list-blank-frames/))까지 막는지는 확인하지 않았습니다.

## 정리

- 뒤로 가기의 빈 칸은 그릴 범위 계산이 틀려서가 아니라, React가 scroll 이벤트에서 받은 업데이트를 페인트 다음 작업으로 미뤄서 생겼습니다.
- 휠 한 번은 overscan 325px 안이라 이전 행이 화면을 덮지만, 15,795px를 한 번에 옮기는 뒤로 가기는 덮지 못했습니다.
- 모든 scroll 이벤트에 `flushSync`를 걸면 빈 칸은 사라졌지만, 휠 스크롤 프레임 간격의 99% 값이 16.6–17.3ms로 늘었습니다.
- 그린 행이 화면을 덮지 못할 때만 `flushSync`를 써서, 뒤로 가기 빈 칸 프레임 0장과 고치기 전과 비슷한 휠 프레임 간격을 함께 얻었습니다.
- 처리기가 첫 렌더링의 state를 보지 않도록, 마지막으로 커밋한 그릴 범위는 ref에 담아 읽습니다.
