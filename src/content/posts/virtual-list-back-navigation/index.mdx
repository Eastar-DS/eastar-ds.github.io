깊이 스크롤한 목록에서 문서를 열었다가 뒤로 돌아오면 스크롤 위치는 돌아왔지만, 화면 대부분이 행 없이 보이는 프레임이 한 장 있었습니다. 스크롤 위치를 한 번에 되돌린 뒤 scroll 이벤트에서 구한 새 범위를 React가 페인트 다음 작업으로 미뤄서였고, 그린 행이 화면을 덮지 못할 때만 `flushSync`로 이벤트 안에서 렌더링하게 해서 휠 스크롤의 프레임 간격을 지키며 막았습니다. 「라이브러리 없이 목록 가상화」 시리즈 4편이고, 휠 스크롤 중의 빈 칸과 빈 칸 프레임을 센 방법은 [3편](/posts/virtual-list-blank-frames/)에 있습니다.

## 뒤로 가기에서는 왜 한 프레임이 비었을까

스크롤 위치를 한 번에 15,795px 되돌린 뒤 scroll 이벤트에서 구한 새 범위를, React가 페인트 다음 작업에서 렌더링했기 때문입니다. Knot 문서 탭의 「주제별」 목록과 문서 보기 화면은 같은 레이아웃 안에서 `main`이 스크롤하는데 브라우저는 창의 스크롤 위치만 기록마다 되돌려 주므로, Knot의 스크롤 복원 훅이 기록(history 항목)마다 `main`의 `scrollTop`을 저장해 두었다가 뒤로 가기로 돌아오면 `useLayoutEffect` 안에서 한 번에 되돌립니다.

실제 빌드에서 15,795px까지 스크롤한 뒤 화면 안의 행을 눌러 문서를 열었다가 뒤로 가기를 하며, 3편과 같이 행이 덮지 않는 카드 영역을 자홍색으로 칠하고 화면에 합성된 프레임을 받아 보았습니다. 스크롤 위치와 누른 행의 위치는 돌아왔지만 받은 프레임 157장 가운데 1장에서 자홍색 가로줄이 622줄 보였고, 두 번째로 재었을 때도 1장이 나왔습니다. 스크롤 영역의 보이는 높이가 750px라서, 화면 대부분이 행 없이 카드 바탕으로 보인 프레임입니다. 순서를 따라가려면 브라우저와 React가 일을 처리하는 때를 알아야 합니다.

- 화면을 그릴 때가 되면 브라우저는 화면 갱신 단계(HTML 표준의 update the rendering)에서 scroll 이벤트 보내기, `requestAnimationFrame` 콜백, 스타일 계산과 레이아웃, `ResizeObserver` 알림, 페인트를 차례로 합니다. 스크립트가 `scrollTop`을 바꾸면 scroll 이벤트는 바로 오지 않고 다음 화면 갱신 단계의 앞부분에 옵니다.
- React는 `setState`를 받으면 업데이트의 우선순위로 렌더링할 때를 정합니다. React 19.2.8 코드에서 click이나 keydown 안의 업데이트는 이벤트가 끝난 뒤의 마이크로태스크에서 렌더링하고, scroll이나 wheel 안의 업데이트는 연속 이벤트 우선순위(ContinuousEventPriority)라서 Scheduler가 만든 다음 작업(task)에서 렌더링합니다.
- `useLayoutEffect` 안에서 부른 `setState`는 페인트 전에 동기로 렌더링하고, [`flushSync`](https://react.dev/reference/react-dom/flushSync)는 콜백 안의 업데이트를 렌더링하고 커밋하고 `useLayoutEffect`까지 돌린 뒤에 돌아옵니다.

고치기 전 코드에서 범위 계산은 두 번 다 맞았습니다. 처음 계산은 스크롤 위치를 되돌리기 전에 했으니 `{ start: 0, end: 0 }`이 맞고, scroll 이벤트의 계산도 `{ start: 7, end: 29 }`로 맞았지만, React가 두 번째 결과를 페인트 다음 작업에서 렌더링해서 화면 갱신 1의 페인트가 795~1,545px를 행 없이 그렸습니다. 휠 스크롤에서도 scroll 이벤트의 업데이트는 같은 방식으로 미뤄지지만, 휠 한 번은 325px 안쪽이라 미리 그려 둔 행이 화면을 덮습니다.

## flushSync를 모든 scroll 이벤트에 걸면 왜 안 될까

범위가 바뀐 카드마다 렌더링과 커밋을 페인트 앞에서 끝내게 되어, 휠 스크롤의 프레임 간격이 늘었기 때문입니다. 처음에는 scroll 이벤트와 크기 변화 알림에서 범위를 바꿀 때마다 `flushSync`로 감쌌는데, 뒤로 가기 빈 칸 프레임은 두 번 잰 기록 모두 0장이 되었지만 CPU 4배 느림에서 휠 스크롤 프레임 간격의 99% 값이 3편에서 잰 325px 빌드의 12.3ms에서 16.6ms(150px 휠), 17.3ms(300px 휠)로 늘었습니다. 측정한 화면은 120Hz라 16.7ms가 프레임 두 장 길이여서, 느린 1%의 프레임에서는 사이의 한 장을 건너뛰었다는 뜻입니다. 어디에 시간이 들었는지 프로파일로 나눠 보지는 않았지만, 코드에서 보이는 차이는 아래와 같습니다.

- 미루면 scroll 이벤트 한 번에서 범위가 바뀐 카드들의 업데이트를 React가 다음 작업에서 함께 렌더링하고 한 번 커밋하지만, `flushSync`는 카드의 처리기마다 렌더링과 커밋을 끝내고 돌아와서 커밋도 여러 번 합니다.
- 다음 카드의 처리기는 `getBoundingClientRect`로 위치를 재는데, 앞 카드의 커밋으로 DOM이 바뀌었으면 브라우저가 위치를 재기 전에 레이아웃을 다시 계산합니다.
- 일이 모두 화면 갱신 단계 안에서 페인트보다 앞에 일어나서, 범위가 바뀌는 프레임마다 페인트가 그만큼 늦어집니다.

## 언제만 flushSync를 쓰게 했을까

스크롤은 나빠지면 안 되는 항목이라서, `flushSync`를 쓰는 때를 미루면 빈 칸이 보이는 때로 좁혔습니다. scroll 이벤트를 받은 때 DOM에 있는 행은 마지막으로 커밋한 범위의 행이므로, 마지막으로 그린 행이 화면에 보이는 카드 부분을 모두 덮으면 이번 프레임을 이전 행으로 그려도 빈 칸이 없고 덮지 못할 때만 빈 칸이 보입니다.

```ts title="useVisibleRowRange.ts" {5,9}
const handleViewChange = () => {
  const view = measureView();
  const { start, end } = drawnRangeRef.current;

  if (isViewCovered({ offsets, start, end, ...view })) {
    applyRange(getRange(view));
    return;
  }
  flushSync(() => applyRange(getRange(view)));
};
```

```ts title="isViewCovered.ts"
const cardHeight = offsets[offsets.length - 1];
const visibleTop = Math.max(viewStart, 0);
const visibleBottom = Math.min(viewEnd, cardHeight);

if (visibleBottom <= visibleTop) return true;
if (start === end) return false;

return (
  offsets[start] <= visibleTop &&
  visibleBottom <= offsets[end]
);
```

`isViewCovered`는 먼저 화면과 카드가 겹치는 구간, 곧 화면에 보이는 카드 부분을 구합니다. 카드 위쪽 끝보다 위는 폴더 제목 같은 카드 밖이라 행이 없어도 빈 칸이 아니므로 0으로 자르고, 카드가 화면 밖이라 겹치는 구간이 없으면 덮을 곳이 없어 참을 돌려줍니다. 판정은 이벤트가 scroll인지 크기 변화인지, 휠인지 뒤로 가기인지를 보지 않고 위치만 봅니다. 화면 위쪽 끝 3,000px에서 그린 `{ start: 41, end: 63 }`(4,094px까지)은 휠 300px까지는 화면을 덮어 렌더링을 미루고, 350px부터는 화면 아래쪽 끝 4,100px를 덮지 못해 `flushSync`를 씁니다.

마지막으로 커밋한 범위는 state가 아니라 ref(`drawnRangeRef`)에 `useLayoutEffect`로 담아 읽습니다. 범위를 구하는 effect는 행 위치가 바뀔 때만 다시 만들어지므로 처리기 안에서 state를 읽으면 effect를 만든 첫 렌더링의 `{ start: 0, end: 0 }`만 보게 되고, 카드가 보이는 동안 판정이 늘 거짓이 되어 모든 scroll 이벤트에 `flushSync`를 건 것과 같아집니다. `flushSync`는 `useLayoutEffect`까지 돌린 뒤에 돌아와서, 다음 줄에서 ref를 읽으면 벌써 새 범위가 들어 있습니다.

고른 빌드는 뒤로 가기 빈 칸 프레임이 0장이고, 휠 스크롤 프레임 간격은 함께 잰 고치기 전 빌드와 1ms 안쪽으로 차이가 나서 늘지 않았습니다. 세 빌드 모두 휠 스크롤 빈 칸 프레임은 0장이었고, 판정 함수는 단위 테스트 5건을 먼저 쓰고 구현했습니다. 화면을 그리는 순서는 jsdom에서 볼 수 없어서, 통합 테스트 대신 실제 빌드로 확인했습니다.

## 아직 확인하지 못한 것은 무엇일까

뒤로 가기 말고도 스크롤 위치가 한 번에 크게 바뀌는 경우가 있는데, 아래 경우는 실제 빌드에서 재지 않았습니다.

- 내용이 아직 짧아 스크롤 복원 훅이 `requestAnimationFrame` 콜백에서 위치를 되돌리는 경우는 재지 않았습니다. 화면 갱신 단계에서 scroll 이벤트는 rAF 콜백보다 먼저 보내지므로, rAF 콜백에서 바뀐 위치의 scroll 이벤트는 다음 프레임에 오고 다음 프레임 전의 페인트는 이전 범위로 그려질 수 있습니다. 측정은 문서 보기에 0.8초 머문 뒤 돌아온 경우입니다.
- 창을 키워 `main`이 높아질 때 `ResizeObserver` 콜백 안의 업데이트도 다음 작업으로 미뤄져서 같은 처리기를 쓰게 했지만, 코드와 표준의 순서로 따진 것이고 실제 빌드에서 재지는 않았습니다.
- 스크롤바를 끌어 멀리 이동하는 동작에서 합성기가 먼저 그리는 프레임까지 막는지는 확인하지 않았습니다.

## 정리

- 뒤로 가기의 빈 프레임은 범위 계산이 틀려서가 아니라, React가 scroll 이벤트 안의 업데이트를 연속 이벤트 우선순위로 보고 페인트 다음 작업에서 렌더링해서 생겼습니다.
- 휠 한 번은 미리 그려 둔 행이 화면을 덮지만, 15,795px를 한 번에 바꾸는 뒤로 가기는 덮지 못합니다.
- 모든 scroll 이벤트에 `flushSync`를 걸면 빈 프레임은 사라지지만, 카드마다 커밋과 레이아웃이 페인트 앞에서 일어나 휠 스크롤 프레임 간격의 99% 값이 16.6~17.3ms로 늘었습니다.
- 마지막으로 그린 행이 화면에 보이는 카드 부분을 덮지 못할 때만 `flushSync`를 써서, 빈 프레임 0장과 고치기 전과 같은 프레임 간격을 함께 지켰습니다.
- 마지막으로 그린 범위는 effect 안의 처리기가 옛 state를 보지 않도록 ref에 담아 읽습니다.
