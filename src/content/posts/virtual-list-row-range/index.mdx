Knot의 「주제별」 탭은 AI가 나눈 주제 폴더별로 녹음 문서를 묶어 보여 주는 목록(아래에서는 문서 목록)이고, 목록 가상화는 받은 데이터는 모두 메모리에 두고 화면 근처의 행만 DOM에 그리는 방법이라서, 가상화한 문서 목록은 어느 행이 화면 근처에 있는지를 행을 그리기 전에 알아야 합니다. 행 높이를 상수로 정해 행 시작 위치를 쌓고, 화면 구간을 위아래로 넓혀 걸친 행을 고르고, 카드에 전체 높이와 위쪽 여백을 주는 순서로 풀었습니다.

[1편](/posts/virtualized-document-list/)에서 문서 1,939개를 모두 그리던 문서 목록을 가상화했습니다. 문서 목록은 폴더마다 `section` 안에 폴더 머리와 카드(`ul`)를 두고, 스크롤은 창이 아니라 화면 레이아웃의 `main` 요소가 맡습니다. 폴더 틀은 모두 그리고 카드 안의 행(`li`)만 가상화했으므로 아래 계산은 모두 카드 하나를 기준으로 합니다. 행 번호는 0부터 세고, 범위 `{ start, end }`의 `end`는 그리지 않는 첫 행 번호이며, 「N번째」는 1부터 센 순서를 말할 때만 씁니다.

## 행 높이는 그리기 전에 어떻게 알까

Knot의 문서 행은 제목과 요약을 각각 한 줄에서 말줄임하므로, 행 높이는 요약이 있는지만 보면 정해집니다. 행을 그린 뒤 높이를 재는 방식으로는 그리기 전에 화면 근처의 행을 고를 수 없어서, 행의 여백과 글줄 높이를 더한 값을 rem 상수(`ROW_HEIGHT_REM`)로 정했습니다.

<Figure caption="표 1. 문서 행 높이를 이루는 값 (1rem이 16px일 때)" captionSide="top">

| 부분 | 요약 없는 행 | 요약 있는 행 |
| --- | ---: | ---: |
| 위 여백 | 20px | 20px |
| 제목 한 줄 (1rem, 줄 높이 1.5) | 24px | 24px |
| 제목과 요약 사이 | 없음 | 4px |
| 요약 한 줄 | 없음 | 24px |
| 아래 여백 | 20px | 20px |
| 합계 | 64px (4rem) | 92px (5.75rem) |

</Figure>

둘째 행부터는 행 사이 구분선 1px(`ROW_DIVIDER_PX`)이 위쪽 테두리로 그어져 행 높이에 더해집니다. `getRowOffsets`는 행마다 위쪽 끝이 카드 맨 위에서 몇 px 아래에 있는지를 차례로 쌓아 행 수보다 하나 긴 배열을 돌려주고, 배열의 마지막 값이 카드 전체 높이가 됩니다.

```ts title="getRowOffsets.ts"
export const getRowOffsets = ({
  documents,
  remPx,
}: GetRowOffsetsParams) => {
  const offsets = [0];

  documents.forEach(({ summary }, index) => {
    const rowHeightRem =
      summary === null
        ? ROW_HEIGHT_REM.withoutSummary
        : ROW_HEIGHT_REM.withSummary;
    const dividerPx = index === 0 ? 0 : ROW_DIVIDER_PX;

    offsets.push(
      offsets[index] + rowHeightRem * remPx + dividerPx,
    );
  });

  return offsets;
};
```

요약이 있음, 없음, 없음인 행 셋이면 첫 행은 구분선 없이 92px이고 둘째와 셋째 행은 64px에 구분선 1px을 더한 65px이라서, 돌려주는 값은 `[0, 92, 157, 222]`입니다. 구분선을 빼먹으면 `[0, 92, 156, 220]`, 첫 행에도 넣으면 `[0, 93, 158, 223]`이 되어 행 위치가 계산과 어긋납니다.

`remPx`는 1rem이 몇 px인지를 `document.documentElement`의 계산된 글자 크기에서 읽은 값입니다. 브라우저 설정에서 글자 크기를 키워 1rem이 20px이 되면 요약 없는 행은 80px로 커지지만 구분선은 px로 정한 값이라 1px이어서, 요약 없는 행 두 개는 `[0, 80, 161]`이 됩니다. `getRowOffsets`의 테스트 6건은 문서가 없는 폴더(`[0]`), 요약 없는 행 하나(64px), 요약 있는 행 하나(92px), 둘째 행부터의 구분선, 높이가 다른 행이 섞인 경우, 1rem이 20px인 경우를 다룹니다.

## 화면 구간은 어떻게 잴까

화면 구간은 카드 맨 위를 0으로 둔 좌표로 잽니다. 페이지 전체를 하나의 좌표로 계산하려면 탭 머리 높이, 폴더 머리 높이, 머리와 카드 사이 12px, 폴더 사이 간격을 모두 JavaScript에 다시 적어야 하고, 디자인이 바뀔 때 CSS와 JavaScript를 함께 고쳐야 합니다. 카드가 실제로 어디에 있는지는 브라우저가 [`getBoundingClientRect`](https://developer.mozilla.org/en-US/docs/Web/API/Element/getBoundingClientRect)로 알려 주므로, 직접 계산하는 값은 카드 안의 행 높이까지로 줄어듭니다.

```ts title="useVisibleRowRange.ts"
const viewStart =
  main.getBoundingClientRect().top -
  card.getBoundingClientRect().top;
const viewEnd = viewStart + main.clientHeight;
```

`viewStart`는 화면 위쪽 끝이 카드 맨 위에서 몇 px 아래에 있는지이고, 카드가 화면 위쪽 끝보다 아래에 보이면 음수가 됩니다. 예를 들어 창에서 `main`의 위쪽 끝이 100px, 카드의 위쪽 끝이 400px에 있고 `main`의 높이가 800px이면, `viewStart`는 100 − 400 = −300이고 `viewEnd`는 500이라서 카드의 처음 500px이 화면에 보입니다. 빼는 순서를 거꾸로 하면 부호가 뒤집혀, 화면 위로 지나간 카드와 아직 아래에 있는 카드를 서로 바꿔 계산합니다.

## 넓힌 구간에 걸친 행은 어떻게 고를까

화면 구간을 위아래로 미리 그릴 거리(px)만큼 늘린 다음, 늘린 구간에 조금이라도 걸친 행을 모두 고릅니다. 처음 구현은 화면에 걸친 행의 위아래로 5행씩 더 그리는 행 개수 방식이었는데, 행 개수 방식은 화면에 걸친 행이 있을 때만 행을 더하므로 화면 밖에 있는 카드는 행을 하나도 그리지 않았습니다. 그러면 스크롤로 카드가 화면에 들어오는 첫 프레임에는 카드에 그려 둔 행이 없어서, 범위를 다시 구해 그리기 전에 첫 프레임이 화면에 나가면 행이 비어 보일 수 있습니다. 폴더가 28개라 스크롤하는 동안 카드 경계를 자주 지나가며, 휠 스크롤 프레임이 범위를 다시 구하기 전에 화면에 나갈 수 있는 까닭은 [3편](/posts/virtual-list-blank-frames/)에서 다룹니다.

그래서 `getVisibleRange`는 화면 구간을 위아래로 `overscanPx`(미리 그릴 거리)만큼 넓힌 다음, 넓힌 구간에 조금이라도 걸친 행의 처음과 끝을 `{ start, end }`로 돌려주게 바꿨습니다. 아래 코드는 함수 본문입니다.

```ts title="getVisibleRange.ts" {1-2}
const rangeStart = viewStart - overscanPx;
const rangeEnd = viewEnd + overscanPx;
const rowCount = offsets.length - 1;
let firstInRange = -1;
let lastInRange = -1;

for (let index = 0; index < rowCount; index += 1) {
  const isInRange =
    offsets[index + 1] > rangeStart &&
    offsets[index] < rangeEnd;

  if (isInRange) {
    if (firstInRange === -1) firstInRange = index;
    lastInRange = index;
  }
}

if (firstInRange === -1) return { start: 0, end: 0 };

return { start: firstInRange, end: lastInRange + 1 };
```

<Figure caption="표 2. 행 위치가 [0, 64, 157, 222, 287]인 카드를 화면 높이 800px에서 볼 때 두 방식이 고른 범위" captionSide="top">

| 상황 | 행 개수 방식 (5행) | px 방식 (100px) |
| --- | --- | --- |
| 카드 아래쪽 끝이 화면 위쪽 끝과 맞닿음 (`viewStart` 287, `viewEnd` 1,087) | `{ start: 0, end: 0 }` | `{ start: 2, end: 4 }` |
| 카드가 화면 아래쪽 끝보다 50px 아래에 있음 (`viewStart` −850, `viewEnd` −50) | `{ start: 0, end: 0 }` | `{ start: 0, end: 1 }` |

</Figure>

i번 행은 아래쪽 끝 `offsets[i + 1]`이 넓힌 구간의 위쪽 끝보다 크고, 위쪽 끝 `offsets[i]`가 넓힌 구간의 아래쪽 끝보다 작을 때 걸친 것으로 봅니다. 두 비교에 등호가 없어서 끝이 딱 맞닿기만 한 행은 빠지고, 예를 들어 행 위치가 `[0, 64, 157, 222, 287]`이고 미리 그릴 거리 없이 화면이 157–600px이면 157px에서 끝나는 1번 행은 그리지 않아 결과가 `{ start: 2, end: 4 }`입니다. `end`는 범위에 들지 않는 첫 행이라서 `documents.slice(start, end)`로 그릴 문서를 고를 수 있고, 걸친 행이 없으면 `{ start: 0, end: 0 }`을 돌려줘서 `slice` 결과가 빈 배열이 됩니다.

요약이 [없음, 있음, 없음, 없음]인 카드가 화면 위쪽 끝보다 조금 위로 올라가 있는 경우로 값이 흐르는 순서를 따라가 보겠습니다.

1. `getRowOffsets`가 `[0, 64, 157, 222, 287]`을 돌려줍니다.
2. 창에서 `main`의 위쪽 끝이 56px, 카드의 위쪽 끝이 −344px, `main`의 높이가 800px이라서 `viewStart`는 56 − (−344) = 400, `viewEnd`는 1,200입니다.
3. 미리 그릴 거리 325px로 넓힌 구간은 75–1,525px입니다.
4. 카드의 아래쪽 끝(287px)은 화면 위쪽 끝(400px)보다 113px 위라서 화면에는 행이 하나도 보이지 않지만, 아래쪽 끝이 75px보다 아래인 1, 2, 3번 행은 넓힌 구간에 걸칩니다.
5. 결과는 `{ start: 1, end: 4 }`이고, 카드는 1, 2, 3번 행을 그립니다.

넓힌 구간에 걸친 행은 언제나 카드 안의 행이라서, 범위를 카드 안으로 자르는 코드도 필요 없어졌습니다. 행 개수 방식으로 만든 첫 구현에 px 방식의 기대값으로 바꾼 테스트를 돌려 6건이 실패하는 것을 먼저 확인했고, 고친 뒤 지금 `getVisibleRange`의 테스트는 맞닿은 행, 카드 밖으로 나간 넓힌 구간, 화면 밖이지만 넓힌 구간에 걸친 카드, 행이 없는 카드를 포함해 8건입니다. 미리 그릴 거리를 325px로 정한 측정은 [3편](/posts/virtual-list-blank-frames/)에서 다룹니다.

## 카드 높이와 첫 렌더링은 어떻게 다룰까

카드에는 행을 모두 그린 높이(`offsets`의 마지막 값)를 주고 그린 첫 행의 위쪽 끝(`offsets[start]`)만큼 위쪽 여백을 줘서 그린 행을 원래 위치에 놓았고, 첫 렌더링은 빈 범위로 시작해 `useLayoutEffect`에서 채웠습니다. 행을 일부만 그리면 카드가 그린 행만큼 짧아져서, 스크롤하며 행을 지우고 그릴 때마다 아래 폴더가 위아래로 움직이고 스크롤바 길이도 바뀌기 때문입니다.

<Figure caption="그림 1. 요약 없는 문서 1,000개 폴더의 카드가 높이 600px인 main 맨 위에 있고, 화면 위쪽 끝이 카드 맨 위에서 30,000px 아래에 있을 때(viewStart 30,000) 카드 하나의 구성입니다. 행 번호는 0부터 세고, 세로 길이는 비율대로 그리지 않았습니다.">

</Figure>

그림 1의 카드는 행을 모두 그린 높이 64,999px(64 + 999 × 65)를 갖고, 위쪽 여백 29,639px로 456번 행의 위쪽 끝을 맞춥니다. 아래 두 코드 칸은 같은 구조를 지어낸 폴더 「디자인 리뷰」와 요약 없는 문서 8개로 줄여 보여 줍니다. 설명을 위해 `main` 높이는 130px, 미리 그릴 거리는 30px로 줄였고, 행 안의 날짜와 녹음 길이, 구분선 스타일은 빼고 제목 링크만 적었으며 `/docs/1` 같은 주소도 지어낸 값입니다.

```html title="가상화 전: 문서 8개를 모두 그림"
<main>
  <section aria-labelledby="folder-review">
    <div>
      <h3 id="folder-review">디자인 리뷰</h3>
      <span>8</span>
    </div>
    <ul>
      <li><a href="/docs/1">버튼 크기 맞추기</a></li>
      <li><a href="/docs/2">색 대비 다시 보기</a></li>
      <li><a href="/docs/3">빈 화면 문구</a></li>
      <li><a href="/docs/4">아이콘 굵기</a></li>
      <li><a href="/docs/5">모바일 여백</a></li>
      <li><a href="/docs/6">오류 안내 위치</a></li>
      <li><a href="/docs/7">탭 이름 정하기</a></li>
      <li><a href="/docs/8">카드 그림자</a></li>
    </ul>
  </section>
</main>
```

행 위치는 `[0, 64, 129, 194, 259, 324, 389, 454, 519]`이고, 화면 위쪽 끝이 카드 맨 위에서 200px 아래에 있을 때(`viewStart` 200) 화면 구간 200–330px를 30px씩 넓힌 170–360px에 걸친 행은 2–5번 행입니다.

```html title="가상화 후: viewStart 200"
<main>
  <section aria-labelledby="folder-review">
    <div>
      <h3 id="folder-review">디자인 리뷰</h3>
      <span>8</span>
    </div>
    <!-- 높이: 8행 519px, 위쪽 여백: 2번 행 시작 129px -->
    <ul style="height: 519px; padding-top: 129px">
      <li aria-posinset="3" aria-setsize="8">
        <a href="/docs/3">빈 화면 문구</a>
      </li>
      <li aria-posinset="4" aria-setsize="8">
        <a href="/docs/4">아이콘 굵기</a>
      </li>
      <li aria-posinset="5" aria-setsize="8">
        <a href="/docs/5">모바일 여백</a>
      </li>
      <li aria-posinset="6" aria-setsize="8">
        <a href="/docs/6">오류 안내 위치</a>
      </li>
    </ul>
  </section>
</main>
```

Knot의 전역 스타일이 [`box-sizing: border-box`](https://developer.mozilla.org/en-US/docs/Web/CSS/box-sizing)라서 위쪽 여백 129px, 그린 행 260px, 아래쪽 빈 높이 130px이 모두 카드 높이 519px 안에 들어갑니다. 위쪽 여백을 위한 빈 `li`는 만들지 않고, `aria-posinset`과 `aria-setsize`로 폴더 안의 순서와 전체 행 수를 알리는 까닭은 [5편](/posts/virtual-list-accessibility/)에서 다룹니다. 실제 코드도 두 값을 카드에 인라인 스타일로 넣습니다.

```tsx title="DocumentFolder.tsx"
<Card
  ref={cardRef}
  style={{ height: cardHeight, paddingTop: firstRowTop }}
  onBlur={handleCardBlur}
>
```

위쪽 여백은 스크롤할 때마다 바뀌는 값이라 CSS-in-JS 라이브러리인 Emotion의 styled 컴포넌트에 넘기지 않았습니다. [Emotion 문서](https://emotion.sh/docs/best-practices)의 예처럼 값이 다른 스타일마다 클래스가 따로 생기므로, 스크롤 위치마다 새 클래스가 만들어지지 않게 인라인 스타일로 넣었습니다.

카드 위치를 `getBoundingClientRect`로 재려면 카드 `ul`이 DOM에 있어야 하는데, 첫 렌더링에서 행을 모두 만들면 행 1,939개를 만든 뒤에 줄이게 되어 가상화로 줄이려던 마운트를 다시 하게 됩니다. 그래서 처음 범위를 `{ start: 0, end: 0 }`으로 두고 범위는 [`useLayoutEffect`](https://react.dev/reference/react/useLayoutEffect)에서 구했으며, `main` 높이가 640px이고 요약 없는 행 100개짜리 카드가 맨 위에 있으면 첫 화면은 아래 순서로 나옵니다.

1. 첫 렌더링: 범위가 `{ start: 0, end: 0 }`이라 `li`가 0개이고, 카드 높이는 6,499px입니다.
2. React 커밋: React가 렌더링 결과를 DOM에 반영하는 단계에서 카드 `ul`을 DOM에 붙입니다.
3. `useLayoutEffect`: 카드 위치를 재서 `viewStart` 0, `viewEnd` 640으로 범위 `{ start: 0, end: 15 }`를 구해 `setRange`에 넘깁니다.
4. 다시 렌더링: React 문서에 따르면 layout effect 안에서 바꾼 상태는 브라우저가 화면을 다시 그리기 전에 처리되므로, `li` 15개가 붙습니다.
5. 페인트: 사용자가 처음 보는 화면에는 행 15개가 있습니다.

[`useEffect`](https://react.dev/reference/react/useEffect)는 클릭 같은 상호작용으로 생긴 effect가 아니면 브라우저가 화면을 먼저 그린 뒤에 도는 경우가 많아서, 1번 결과인 행 없는 카드가 한 프레임 보일 수 있습니다.

## 언제 범위를 다시 구할까

`useVisibleRowRange` 훅은 카드를 감싼 `main`의 scroll 이벤트와 [`ResizeObserver`](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)의 크기 변화 알림을 받을 때마다 범위를 다시 구합니다. 한 번 스크롤하는 동안 scroll 이벤트가 여러 번 오는데 대부분은 범위를 바꾸지 않으므로, 범위가 같으면 `setRange`에 이전 상태 객체를 돌려줍니다.

```ts title="useVisibleRowRange.ts"
const applyRange = (next: RowRange) => {
  setRange((previous) =>
    previous.start === next.start &&
    previous.end === next.end
      ? previous
      : next,
  );
};
```

`getVisibleRange`는 부를 때마다 새 객체를 돌려주므로, 비교 없이 `setRange(next)`를 부르면 내용이 같아도 React가 [`Object.is`](https://react.dev/reference/react/useState#setstate)로 다른 상태라고 보고 다시 렌더링합니다. 이전 객체를 돌려주면 `Object.is` 비교가 같다고 나와 React가 다시 렌더링을 건너뜁니다. scroll 이벤트 처리에는 뒤로 가기에서 화면을 덮지 못할 때를 위한 판정도 들어 있는데, [4편](/posts/virtual-list-back-navigation/)에서 다룹니다.

처음 구현은 범위를 첫 화면과 scroll 이벤트에서 구했는데, scroll 이벤트는 스크롤 위치가 바뀔 때 오므로 창을 키워 `main`이 높아져도 스크롤 위치가 그대로면 범위를 다시 구하지 않았습니다. 표 3은 요약 없는 행 100개짜리 카드를 `main` 640px에서 그린 뒤 스크롤하지 않고 창 높이만 바꾼 경우의 계산입니다.

<Figure caption="표 3. 요약 없는 행 100개짜리 카드를 main 640px에서 그린 뒤, 스크롤하지 않고 창 높이만 바꾼 경우 (미리 그릴 거리 325px)" captionSide="top">

| `main` 높이 | 크기 변화를 받지 않을 때 그린 행 | 화면 안 빈 곳 | 크기 변화를 받을 때 그린 행 |
| ---: | --- | --- | --- |
| 640px | `{ start: 0, end: 15 }`, 974px까지 | 없음 | `{ start: 0, end: 15 }`, 974px까지 |
| 900px | `{ start: 0, end: 15 }`, 974px까지 | 없음 | `{ start: 0, end: 19 }`, 1,234px까지 |
| 1,000px | `{ start: 0, end: 15 }`, 974px까지 | 974–1,000px | `{ start: 0, end: 21 }`, 1,364px까지 |
| 1,200px | `{ start: 0, end: 15 }`, 974px까지 | 974–1,200px | `{ start: 0, end: 24 }`, 1,559px까지 |

</Figure>

미리 그릴 거리만큼은 화면 아래에 그려 두었으므로 `main`이 조금 높아질 때는 빈 곳이 생기지 않고, 그려 둔 행의 아래쪽 끝(974px)보다 높아질 때부터 빕니다. 그래서 `ResizeObserver`로 `main`을 지켜보며 크기가 바뀔 때도 범위를 다시 구하게 했습니다.

```ts title="useVisibleRowRange.ts"
main.addEventListener("scroll", handleViewChange, {
  passive: true,
});
const resizeObserver = new ResizeObserver(handleViewChange);

resizeObserver.observe(main);

return () => {
  main.removeEventListener("scroll", handleViewChange);
  resizeObserver.disconnect();
};
```

[MDN의 `observe` 설명](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver/observe)대로 요소가 그려져 있고 크기가 0이 아니면 지켜보기 시작할 때 알림이 한 번 오지만, 이미 구한 범위와 같아서 위의 비교가 다시 렌더링을 건너뜁니다. effect의 정리 함수에서 `disconnect`를 빼먹으면 언마운트한 폴더의 콜백이 크기가 바뀔 때마다 계속 불리므로, scroll 리스너를 떼는 곳에서 함께 끊습니다.

jsdom의 `ResizeObserver`는 크기 변화를 알리지 않아서, 통합 테스트에서는 `vi.stubGlobal`로 테스트가 정한 때에 알리는 구현으로 바꿨습니다. `main` 높이를 640px에서 1,200px로 바꾸고 알리면 20번 행(1,299–1,364px)이 생기는지 보는 테스트는 구현 전에는 실패했고 구현 뒤에 통과했습니다.

## 그린 첫 행의 구분선은 왜 어긋났을까

카드의 첫 `li`가 폴더의 첫 행이 아닌데도 구분선을 긋지 않아서 어긋났습니다. 처음 구분선 규칙은 Emotion의 `& + &` 선택자였는데, CSS 인접 형제 선택자라서 바로 앞에 형제 `li`가 있는 `li`는 위쪽 테두리를 긋고 DOM에서 첫 번째인 `li`는 폴더 안 순서와 관계없이 테두리가 빠졌습니다. `getRowOffsets`는 0번이 아닌 행에 모두 1px을 더해 계산하므로, 일부만 그리면 그린 첫 행이 계산보다 1px 짧게 그려지고 아래 행이 모두 1px씩 위에 놓였습니다.

<Figure caption="그림 2. 요약이 [있음, 없음, 있음, 없음, 없음]인 카드를 행을 모두 그린 경우와, 1번 행부터 그린 고치기 전 코드로 견줬습니다. 숫자는 행의 위쪽 끝이 카드 맨 위에서 몇 px 아래에 있는지이고, 계산과 다른 위치에는 계산 값을 함께 적었습니다. 세로 길이는 0.6배로 줄이고 1px 구분선은 굵게 그렸습니다.">
  <FirstRowDividerDiagram />
</Figure>

그림 2의 카드는 행 위치가 `[0, 92, 157, 250, 315, 380]`인데, 1번 행부터 그리면 고치기 전에는 2, 3, 4번 행의 위쪽 끝이 156, 249, 314px로 계산보다 1px씩 위였습니다. 빠진 구분선은 카드의 첫 `li` 것 하나라서 어긋남은 1px보다 커지지 않고, 카드 높이는 380px로 고정되어 있어 마지막 행 아래가 1px 빕니다. 그래서 구분선을 DOM 순서가 아니라 폴더 안 순서로 긋게 바꿨습니다.

```tsx title="DocumentRow.tsx"
<Item
  $isFirstRow={index === 0}
  aria-posinset={index + 1}
  aria-setsize={rowCount}
>
```

`Item`의 스타일은 `$isFirstRow`가 거짓인 행에 위쪽 테두리 1px을 긋습니다.

```tsx title="DocumentRow.tsx"
const Item = styled.li<{ $isFirstRow: boolean }>`
  border-top: ${({ theme, $isFirstRow }) =>
    $isFirstRow
      ? "none"
      : `1px solid ${theme.neutral[200]}`};
`;
```

`DocumentFolder`는 `map`이 주는 카드 안 순서가 아니라 행의 폴더 안 순서를 `index`로 넘기므로, 범위가 `{ start: 41, end: 62 }`라면 그린 `li` 21개가 모두 구분선을 긋습니다. 고친 뒤에는 그림 2의 2, 3, 4번 행이 157, 250, 315px로 계산과 같았고, 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 오도록 카드 위치를 정한 뒤(`viewStart` 3,000) 그린 첫 행인 41번 행과 둘째 행에 구분선이 있는지 보는 통합 테스트를 더했습니다.

## 계산이 실제 화면과 맞았을까

개선 전 로컬 빌드에 문서 1,939개, 폴더 28개짜리 목록 응답을 넣고 행 1,939개와 카드 28개의 높이를 모두 재어 보니 계산과 같았습니다. 팀 보고의 측정은 글을 쓰며 다시 재지 않았고 원자료도 없어서 아래 표의 값은 모두 팀 보고에 적은 값이며, 1rem 20px 줄의 행 수는 팀 보고에 적혀 있지 않습니다.

| --- | ---: | ---: | ---: | ---: | --- |
| 16px | 64px (25개) | 65px (1,906개) | 92px (3개) | 93px (5개) | 28개 모두 0px |

가장 큰 폴더(문서 994개)의 카드 높이는 1rem이 16px일 때 64,609px, 20px일 때 80,513px로 두 경우 모두 계산과 같았습니다. 가상화한 빌드는 [1편](/posts/virtualized-document-list/)의 2026년 11월 12일 측정(CPU 4배 느림, 시험용 응답 문서 1,939개)에서 DOM에 있는 문서 행이 13개였고, `main`의 스크롤 높이는 개선 전과 후 모두 128,317px로 같았습니다.

통합 테스트는 jsdom이 레이아웃을 계산하지 않아서 `main`의 보이는 높이(640px)와 카드 위치를 `vi.spyOn`으로 정하고, 폴더 하나에 요약 없는 문서 100개를 넣었습니다. 처음 그린 카드는 0번 행과 9번 행이 있고 99번 행이 없으며 높이가 6,499px인지, `viewStart`가 3,000이 되도록 카드 위치를 바꾸고 scroll 이벤트를 보내면 46번 행이 생기는지를 보며, 두 건 모두 구현 전에는 행을 모두 그려서 실패했고 구현 뒤에 통과했습니다.

## 정리

- 행 높이가 요약 유무로 정해지게 해 두면 행을 그리기 전에 `getRowOffsets`로 시작 위치를 쌓을 수 있고, 구분선처럼 px로 정한 값에는 `remPx`를 곱하지 않습니다.
- 화면 구간을 카드 맨 위 기준으로 재면 카드 밖 여백과 머리 높이를 JavaScript에 다시 적지 않아도 되고, 카드가 화면보다 아래에 있으면 `viewStart`가 음수입니다.
- 행 개수 방식은 화면 밖 카드에 행을 그리지 않아서, 화면 구간을 px로 넓혀 걸친 행을 등호 없는 비교로 고르고 `end`를 범위 밖 첫 행으로 둬 `slice`에 넣었습니다.
- 카드에는 행을 모두 그린 높이와 그린 첫 행의 위쪽 끝만큼의 여백을 주고, 첫 렌더링은 빈 범위로 시작해 `useLayoutEffect`에서 채웁니다.
- 범위가 같으면 이전 상태를 돌려줘 렌더링을 건너뛰고, scroll 이벤트가 오지 않는 크기 변화는 `ResizeObserver`로 받으며, 구분선은 폴더 안 순서로 긋습니다.
- 팀 보고에 적은 실측에서 행 1,939개와 카드 28개의 높이가 계산과 같았고, 가상화 뒤에도 `main`의 스크롤 높이는 128,317px로 같았습니다.
