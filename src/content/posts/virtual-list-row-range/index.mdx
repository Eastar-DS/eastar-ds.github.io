[1편](/posts/virtualized-document-list/)에서 Knot 문서 목록에 리스트 가상화를 넣어, 문서 1,939개를 모두 그리던 화면을 보이는 행과 overscan 안의 행만 그리게 바꿨습니다. overscan은 빠르게 스크롤할 때 화면이 잠깐 비어 보이지 않도록 화면 위아래로 더 그려 두는 여유분이에요. 문서 목록은 폴더마다 위에 폴더 이름이 있고, 그 아래 흰 카드 안에 문서가 한 줄씩 행으로 들어가는데요. 폴더 이름과 카드는 모두 그리고, 카드 안의 행만 카드마다 따로 가상화했습니다.

그런데 보이는 행만 그리려면, 행을 그리기 전에 어느 행이 화면에 보일지 알아야 합니다. 행이 화면의 어디에 놓일지는 보통 그려 봐야 알 수 있는데 말이죠. 그래서 행마다 카드의 어디에 놓일지 미리 더해 두고, 지금 화면이 카드의 어디를 보고 있는지 브라우저에게 물어본 뒤, 그 구간에 걸친 행만 골랐습니다.

처음 구현은 세 곳에서 틀렸습니다. 화면 밖 카드는 행을 하나도 그려 두지 않았고, 창을 키워도 그릴 행을 다시 고르지 않았으며, 일부만 그린 카드에서는 행이 1px씩 위로 밀렸어요. 셋을 고치고 나서 계산이 맞는지도 확인했는데요, 가상화하기 전 빌드에서 행 1,939개와 카드 28개의 실제 높이를 재 보니 모두 계산과 같았습니다.

## 행 높이는 그리기 전에 어떻게 알까

1편의 예에서는 행 높이를 모두 40px로 두고 곱셈으로 위치를 구했는데요, Knot의 행은 높이가 두 가지입니다. 행마다 문서 제목이 한 줄 있고, 요약이 있는 문서는 그 아래 요약이 한 줄 더 있어요. 제목과 요약은 길어도 한 줄에서 말줄임표로 자르기 때문에 줄 수가 늘지 않습니다. 그래서 행 높이는 요약이 있는지만 보면 정해집니다.

행을 그린 뒤에 높이를 재면, 이미 행을 다 그린 뒤라 가상화하는 뜻이 없어지죠. 그래서 행의 여백과 글줄 높이를 더한 값을 rem 상수(`ROW_HEIGHT_REM`)로 정해 두었습니다.

<Figure caption="표 1. 문서 행 높이를 이루는 값 (1rem이 16px일 때)" captionSide="top">

| 부분 | 요약 없는 행 | 요약 있는 행 |
| --- | ---: | ---: |
| 위 여백 | 20px | 20px |
| 제목 한 줄 (1rem, 줄 높이 1.5) | 24px | 24px |
| 제목과 요약 사이 | 없음 | 4px |
| 요약 한 줄 | 없음 | 24px |
| 아래 여백 | 20px | 20px |
| 합계 | 64px (4rem) | 92px (5.75rem) |

</Figure>

행 사이에는 1px 구분선도 있습니다. 둘째 행부터 위쪽 테두리로 긋기 때문에 그 행의 높이에 1px이 더해져요. 구분선 두께는 rem이 아니라 px로 정한 값(`ROW_DIVIDER_PX`)입니다.

이 두 값이 있으면 행마다 위쪽 끝이 카드 맨 위에서 몇 px 아래에 있는지 구할 수 있습니다. 이 글에서는 이 값을 「행 위치」라고 부를게요. 행 번호는 코드처럼 0부터 세는데요, 카드의 첫 행인 0번 행의 위치는 0px이고, 그다음 행의 위치는 앞 행의 위치에 앞 행의 높이를 더한 값입니다. `getRowOffsets`가 이 덧셈을 차례로 해서 행 위치를 배열로 돌려줘요.

```ts title="getRowOffsets.ts"
export const getRowOffsets = ({
  documents,
  remPx,
}: GetRowOffsetsParams) => {
  const offsets = [0];

  documents.forEach(({ summary }, index) => {
    const rowHeightRem =
      summary === null
        ? ROW_HEIGHT_REM.withoutSummary
        : ROW_HEIGHT_REM.withSummary;
    const dividerPx = index === 0 ? 0 : ROW_DIVIDER_PX;

    offsets.push(
      offsets[index] + rowHeightRem * remPx + dividerPx,
    );
  });

  return offsets;
};
```

요약이 있음, 없음, 없음인 행 셋으로 계산해 볼게요. 0번 행은 구분선 없이 92px이고, 1번과 2번 행은 64px에 구분선 1px을 더한 65px이라서 결과는 `[0, 92, 157, 222]`입니다. 배열이 행 수보다 하나 긴데요, 마지막 값 222는 마지막 행의 아래쪽 끝이라서 곧 카드 높이가 됩니다. 구분선을 빼먹으면 `[0, 92, 156, 220]`이 되고, 0번 행에도 넣으면 `[0, 93, 158, 223]`이 되어 실제 화면과 어긋나요.

`remPx`는 1rem이 몇 px인지를 페이지의 실제 글자 크기에서 읽은 값입니다. 브라우저 설정에서 글자 크기를 키워 1rem이 20px이 되면 요약 없는 행은 80px로 커지지만, 구분선은 그대로 1px이에요. 그래서 요약 없는 행 두 개는 `[0, 80, 161]`이 됩니다. `getRowOffsets`의 테스트 6건은 문서가 없는 폴더(`[0]`), 요약이 있는 행과 없는 행, 둘째 행부터 붙는 구분선, 높이가 다른 행이 섞인 경우, 1rem이 20px인 경우를 확인합니다.

## 어느 행을 그릴까

### 화면은 카드의 어디를 보고 있을까

행 위치를 카드 맨 위를 0으로 두고 구했으니, 화면도 같은 기준으로 잽니다. 지금 화면의 위쪽 끝과 아래쪽 끝이 카드 맨 위에서 몇 px 아래에 있는지 알면, 그 사이에 있는 행이 보이는 행이에요.

페이지 맨 위를 기준으로 잡을 수도 있었는데요, 그러면 카드마다 페이지 맨 위에서 몇 px 떨어져 있는지 알아야 합니다. 목록 위 탭 영역의 높이, 폴더 이름의 높이, 폴더 이름과 카드 사이 12px, 폴더 사이 간격을 모두 JavaScript에 다시 적어야 하고, 디자인이 바뀌면 CSS와 JavaScript를 함께 고쳐야 하죠. 1편에서 말한 대로, 카드가 지금 화면의 어디에 있는지는 브라우저에게 물어보면 됩니다(`getBoundingClientRect`[^rect]). Knot에서는 창이 아니라 `main` 요소가 스크롤되므로, `main`과 카드의 위치 차이로 화면 구간을 구합니다.

```ts title="useVisibleRowRange.ts"
const viewStart =
  main.getBoundingClientRect().top -
  card.getBoundingClientRect().top;
const viewEnd = viewStart + main.clientHeight;
```

`viewStart`는 화면 위쪽 끝이, `viewEnd`는 화면 아래쪽 끝이 카드 맨 위에서 몇 px 아래에 있는지입니다. 예를 들어 창 맨 위에서 `main`의 위쪽 끝이 100px, 카드의 위쪽 끝이 400px 아래에 있고 `main`의 높이가 800px이라고 해 볼게요. 그러면 `viewStart`는 100 − 400 = −300, `viewEnd`는 500이라서 카드의 처음 500px이 화면에 보입니다. 이렇게 카드가 화면 위쪽 끝보다 아래에서 시작하면 `viewStart`가 음수가 돼요.

### 그릴 범위

이제 행 위치와 화면 구간을 견줘서 그릴 행을 고르면 됩니다. 고른 결과는 `{ start, end }`로 돌려주는데요, `start`는 그릴 첫 행 번호이고 `end`는 그 뒤로 그리지 않는 첫 행 번호예요. 그래서 `documents.slice(start, end)`로 그릴 문서를 바로 고를 수 있습니다. 이 글에서는 이 값을 「그릴 범위」라고 부를게요.

### 처음 구현은 화면 밖 카드를 비워 두었다

처음에는 overscan을 행 개수로 정했습니다. 화면에 걸친 행을 찾고, 그 위아래로 5행씩 더 그리는 방식이었어요. 그런데 이 방식은 화면에 걸친 행이 있어야 위아래로 행을 더할 수 있습니다. 화면 밖에 있는 카드는 걸친 행이 없으니, 행을 하나도 그려 두지 않았어요.

문제는 스크롤해서 카드가 화면에 들어오는 순간입니다. 카드에 그려 둔 행이 없으니, 그릴 범위를 다시 구해 행을 그리기 전에 그 프레임이 화면에 나가면 카드가 잠깐 비어 보일 수 있어요. 문서 목록은 폴더가 28개라서 스크롤하는 동안 카드 경계를 자주 지나갑니다. 휠 스크롤에서 범위를 다시 구하기 전에 프레임이 나갈 수 있는 까닭은 [3편](/posts/virtual-list-blank-frames/)에서 다룹니다.

### 화면 구간을 px로 넓혀서 걸친 행 고르기

그래서 overscan을 px로 바꿨습니다. 화면 구간을 위아래로 `overscanPx`만큼 넓힌 다음, 넓힌 구간에 조금이라도 걸친 행을 고르는 거예요. 이러면 카드가 화면 밖에 있어도 넓힌 구간 안에 들어온 행은 미리 그려 둘 수 있습니다. 아래 코드는 `getVisibleRange`의 본문입니다.

```ts title="getVisibleRange.ts" {1-2}
const rangeStart = viewStart - overscanPx;
const rangeEnd = viewEnd + overscanPx;
const rowCount = offsets.length - 1;
let firstInRange = -1;
let lastInRange = -1;

for (let index = 0; index < rowCount; index += 1) {
  const isInRange =
    offsets[index + 1] > rangeStart &&
    offsets[index] < rangeEnd;

  if (isInRange) {
    if (firstInRange === -1) firstInRange = index;
    lastInRange = index;
  }
}

if (firstInRange === -1) return { start: 0, end: 0 };

return { start: firstInRange, end: lastInRange + 1 };
```

i번 행의 아래쪽 끝은 `offsets[i + 1]`, 위쪽 끝은 `offsets[i]`입니다. 아래쪽 끝이 넓힌 구간의 위쪽 끝보다 아래에 있고, 위쪽 끝이 넓힌 구간의 아래쪽 끝보다 위에 있으면 걸친 행으로 봐요. 두 비교에 등호가 없어서, 끝이 딱 맞닿기만 한 행은 고르지 않습니다. 걸친 행이 하나도 없으면 `{ start: 0, end: 0 }`을 돌려주고, 이때 `slice` 결과는 빈 배열이에요.

두 방식이 화면 밖 카드에서 어떻게 다른지 보면 아래와 같습니다. 요약이 없음, 있음, 없음, 없음인 행 넷이 든 카드라서 행 위치는 `[0, 64, 157, 222, 287]`입니다.

<Figure caption="표 2. 행 위치가 [0, 64, 157, 222, 287]인 카드를 높이 800px인 화면에서 볼 때 두 방식이 고른 그릴 범위 (설명을 위해 px 방식의 overscan은 100px로 둠)" captionSide="top">

| 상황 | 행 개수 방식 (위아래 5행) | px 방식 (위아래 100px) |
| --- | --- | --- |
| 카드 아래쪽 끝이 화면 위쪽 끝과 맞닿음 (`viewStart` 287, `viewEnd` 1,087) | `{ start: 0, end: 0 }` | `{ start: 2, end: 4 }` |
| 카드가 화면 아래쪽 끝보다 50px 아래에 있음 (`viewStart` −850, `viewEnd` −50) | `{ start: 0, end: 0 }` | `{ start: 0, end: 1 }` |

</Figure>

두 경우 모두 화면에 보이는 행은 없는데요, 행 개수 방식은 아무것도 그리지 않고 px 방식은 화면 가까이에 있는 행을 그려 둡니다. Knot에서 쓰는 overscan 325px로도 계산해 볼게요. 같은 카드의 아래쪽 끝(287px)이 화면 위쪽 끝보다 113px 위에 있다면(`viewStart` 400, `viewEnd` 1,200), 넓힌 구간은 75–1,525px입니다. 화면에는 행이 하나도 보이지 않지만, 아래쪽 끝이 75px보다 아래에 있는 1, 2, 3번 행이 넓힌 구간에 걸쳐서 그릴 범위는 `{ start: 1, end: 4 }`가 돼요.

넓힌 구간에 걸친 행은 언제나 카드 안의 행이라서, 범위를 카드의 행 수 안으로 자르는 코드도 필요 없어졌습니다. 고칠 때는 px 방식의 기대값으로 바꾼 테스트를 처음 구현에 먼저 돌려 6건이 실패하는 것을 확인했어요. 지금 `getVisibleRange`의 테스트는 맞닿은 행, 카드 밖으로 나간 넓힌 구간, 화면 밖이지만 넓힌 구간에 걸친 카드, 행이 없는 카드를 포함해 8건입니다. overscan을 325px로 정한 까닭은 [3편](/posts/virtual-list-blank-frames/)에서 다룹니다.

## 그린 행은 어떻게 제자리에 놓을까

그릴 범위를 구했으면 카드에 두 값을 줍니다. [1편](/posts/virtualized-document-list/)의 그림 5, 6에서 본 카드 높이(`height`)와 위쪽 여백(`padding-top`)이에요. 카드 높이는 행 위치 배열의 마지막 값, 그러니까 행을 모두 그렸을 때의 높이입니다. 위쪽 여백은 그릴 첫 행의 위치(`offsets[start]`)이고요. 카드 높이가 고정되어 있으니 스크롤하며 행을 지우고 그려도 아래 폴더가 움직이지 않고, 스크롤바 길이도 그대로입니다.

<Figure caption="그림 1. 요약 없는 문서 1,000개가 든 카드를 높이 600px인 main에서 볼 때, 화면 위쪽 끝이 카드 맨 위에서 30,000px 아래에 있으면(viewStart 30,000) 카드는 이렇게 그립니다. 가운데 10행이 보이는 행, 그 위아래 5행씩이 overscan 325px 안의 행(그림의 「미리 그린 행」)이고, 행 없이 옅게 칠한 칸이 그리지 않은 행의 자리입니다. 행 번호는 0부터 세고, 세로 길이는 비율대로 그리지 않았습니다.">
  <VirtualWindowDiagram />
</Figure>

그림 1의 카드 높이는 64,999px(64 + 999 × 65)입니다. 위쪽 여백 29,639px가 0–455번 행의 자리를 채워서, DOM에서 첫 `li`인 456번 행이 원래 위치에 놓여요. Knot의 전역 스타일이 `box-sizing: border-box`[^border-box]라서 위쪽 여백과 그린 행, 그리지 않은 행의 자리가 모두 카드 높이 안에 들어갑니다. 위쪽 여백을 채우려고 빈 `li`를 만들지는 않았어요. 일부만 그린 행을 화면 낭독기가 제대로 읽게 하는 방법은 [5편](/posts/virtual-list-accessibility/)에서 다룹니다.

실제 코드에서는 두 값을 카드에 인라인 스타일로 넣습니다.

```tsx title="DocumentFolder.tsx"
<Card
  ref={cardRef}
  style={{ height: cardHeight, paddingTop: firstRowTop }}
  onBlur={handleCardBlur}
>
```

Knot는 스타일을 CSS-in-JS 라이브러리인 Emotion으로 쓰는데요, 위쪽 여백은 스크롤할 때마다 바뀌는 값이라 Emotion의 styled 컴포넌트에 넘기지 않았습니다. Emotion은 값이 다른 스타일마다 클래스를 따로 만들어서[^emotion], 스크롤 위치마다 새 클래스가 생기기 때문이에요.

### 첫 화면에서 카드가 비지 않게 하려면

카드 위치를 `getBoundingClientRect`로 재려면 카드 `ul`이 먼저 DOM에 있어야 합니다. 그렇다고 첫 렌더링에서 행을 모두 만들면, 행 1,939개를 만든 뒤에 다시 줄이게 되어 가상화로 줄이려던 일을 그대로 하게 돼요. 그래서 처음 그릴 범위는 `{ start: 0, end: 0 }`으로 두고, 실제 범위는 `useLayoutEffect`[^layout-effect]에서 구했습니다.

`main` 높이가 640px이고, 요약 없는 행 100개가 든 카드가 맨 위에 있다고 해 볼게요. 첫 화면은 아래 순서로 나옵니다.

1. 첫 렌더링: 그릴 범위가 `{ start: 0, end: 0 }`이라 `li`는 0개이고, 카드 높이는 6,499px입니다.
2. DOM 반영: React가 카드 `ul`을 DOM에 붙입니다.
3. `useLayoutEffect`: 카드 위치를 재면 `viewStart`는 0, `viewEnd`는 640이고, 그릴 범위 `{ start: 0, end: 15 }`를 구해 `setRange`에 넘깁니다.
4. 다시 렌더링: layout effect 안에서 바꾼 상태는 브라우저가 화면을 그리기 전에 처리되므로, `li` 15개가 붙습니다.
5. 페인트: 사용자가 처음 보는 화면에는 행 15개가 있습니다.

`useEffect`를 썼다면 어땠을까요? 클릭 같은 상호작용으로 생긴 effect가 아니면 `useEffect`는 브라우저가 화면을 먼저 그린 뒤에 도는 경우가 많습니다[^effect]. 그러면 1번 결과인 행 없는 카드가 한 프레임 보일 수 있어요.

## 언제 범위를 다시 구할까

`useVisibleRowRange` 훅은 `main`의 scroll 이벤트가 올 때마다 그릴 범위를 다시 구합니다. 한 번 스크롤하는 동안 scroll 이벤트는 여러 번 오는데, 대부분은 그릴 범위를 바꾸지 않아요. 그래서 범위가 같으면 `setRange`에 이전 상태 객체를 그대로 돌려줍니다.

```ts title="useVisibleRowRange.ts"
const applyRange = (next: RowRange) => {
  setRange((previous) =>
    previous.start === next.start &&
    previous.end === next.end
      ? previous
      : next,
  );
};
```

`getVisibleRange`는 부를 때마다 새 객체를 돌려줍니다. 비교 없이 `setRange(next)`를 부르면 내용이 같아도 React는 `Object.is`로 견줘 다른 상태라고 보고 다시 렌더링해요[^object-is]. 이전 객체를 돌려주면 `Object.is` 비교가 같다고 나와서 다시 렌더링을 건너뜁니다. scroll 이벤트 처리에는 뒤로 가기에서 화면을 덮지 못할 때를 위한 판정도 들어 있는데, [4편](/posts/virtual-list-back-navigation/)에서 다룹니다.

### 창을 키워도 범위를 다시 구하지 않았다

처음 구현은 첫 화면과 scroll 이벤트에서만 그릴 범위를 구했습니다. 그런데 scroll 이벤트는 스크롤 위치가 바뀔 때만 와요. 창을 키워 `main`이 높아져도 스크롤 위치가 그대로면 범위를 다시 구하지 않았습니다. 요약 없는 행 100개가 든 카드를 `main` 640px에서 그린 뒤, 스크롤하지 않고 창 높이만 바꾸면 아래와 같아요.

<Figure caption="표 3. 요약 없는 행 100개가 든 카드를 main 640px에서 그린 뒤, 스크롤하지 않고 창 높이만 바꾼 경우 (overscan 325px)" captionSide="top">

| `main` 높이 | 크기 변화를 받지 않을 때 그린 행 | 화면이 비어 보이는 구간 | 크기 변화를 받을 때 그린 행 |
| ---: | --- | --- | --- |
| 640px | `{ start: 0, end: 15 }`, 974px까지 | 없음 | `{ start: 0, end: 15 }`, 974px까지 |
| 900px | `{ start: 0, end: 15 }`, 974px까지 | 없음 | `{ start: 0, end: 19 }`, 1,234px까지 |
| 1,000px | `{ start: 0, end: 15 }`, 974px까지 | 974–1,000px | `{ start: 0, end: 21 }`, 1,364px까지 |
| 1,200px | `{ start: 0, end: 15 }`, 974px까지 | 974–1,200px | `{ start: 0, end: 24 }`, 1,559px까지 |

</Figure>

overscan만큼은 화면 아래에 그려 두었으니 `main`이 조금 높아질 때는 괜찮습니다. 하지만 그려 둔 행의 아래쪽 끝(974px)보다 화면이 길어지면 그 아래가 비어 보여요. 그래서 `ResizeObserver`[^resize-observer]로 `main`을 지켜보며 크기가 바뀔 때도 범위를 다시 구하게 했습니다.

```ts title="useVisibleRowRange.ts"
main.addEventListener("scroll", handleViewChange, {
  passive: true,
});
const resizeObserver = new ResizeObserver(handleViewChange);

resizeObserver.observe(main);

return () => {
  main.removeEventListener("scroll", handleViewChange);
  resizeObserver.disconnect();
};
```

지켜보기 시작할 때도 알림이 한 번 오는데요, 이미 구한 범위와 같아서 앞의 비교가 다시 렌더링을 건너뜁니다. effect의 정리 함수에서 `disconnect`를 빼먹으면, 언마운트한 폴더의 콜백이 크기가 바뀔 때마다 계속 불려요. 그래서 scroll 리스너를 떼는 곳에서 함께 끊었습니다.

테스트 환경인 jsdom의 `ResizeObserver`는 크기 변화를 알려 주지 않습니다. 그래서 통합 테스트에서는 `vi.stubGlobal`로 테스트가 정한 때에 알리는 구현으로 바꿨어요. `main` 높이를 640px에서 1,200px로 바꾸고 알렸을 때 20번 행(1,299–1,364px)이 생기는지 보는 테스트는, 고치기 전에는 실패했고 고친 뒤에 통과했습니다.

## 그린 첫 행의 구분선은 왜 어긋났을까

일부만 그린 카드에서 행이 1px씩 위로 밀린 까닭은 구분선이었습니다. 처음에는 구분선을 Emotion의 `& + &` 선택자로 그었는데요. `li + li`와 같은 CSS 인접 형제 선택자라서, 바로 앞에 형제 `li`가 있는 `li`만 위쪽 테두리를 긋습니다. 행을 모두 그릴 때는 폴더의 0번 행만 구분선이 없으니 문제가 없었어요.

가상화하면 사정이 달라집니다. 카드의 첫 `li`가 폴더의 0번 행이 아닐 때가 많은데, 앞에 형제 `li`가 없으니 이 행도 구분선이 빠졌어요. `getRowOffsets`는 0번이 아닌 행에 모두 1px을 더해 계산했으니, 그린 첫 행이 계산보다 1px 짧게 그려지고 그 아래 행이 모두 1px씩 위에 놓였습니다.

<Figure caption="그림 2. 요약이 있음, 없음, 있음, 없음, 없음인 카드를 행을 모두 그린 경우와, 1번 행부터 그린 고치기 전 코드로 견줬습니다. 숫자는 행 위치이고, 계산과 다른 위치에는 계산 값을 함께 적었습니다. 세로 길이는 0.6배로 줄이고 1px 구분선은 굵게 그렸습니다.">
  <FirstRowDividerDiagram />
</Figure>

그림 2의 카드는 행 위치가 `[0, 92, 157, 250, 315, 380]`입니다. 1번 행부터 그리면, 고치기 전에는 2, 3, 4번 행의 위쪽 끝이 156, 249, 314px로 계산보다 1px씩 위였어요. 빠진 구분선은 카드의 첫 `li` 하나뿐이라 어긋남이 1px보다 커지지는 않습니다. 카드 높이는 380px로 고정되어 있어서 마지막 행 아래가 1px 비고요.

그래서 구분선을 DOM 순서가 아니라 폴더 안 순서로 긋게 바꿨습니다. `DocumentFolder`가 `map`의 순서 대신 행의 폴더 안 번호를 `index`로 넘기고, `Item`은 0번 행이 아닌 행에 위쪽 테두리 1px을 긋습니다.

```tsx title="DocumentRow.tsx"
<Item
  $isFirstRow={index === 0}
  aria-posinset={index + 1}
  aria-setsize={rowCount}
>
```

```tsx title="DocumentRow.tsx"
const Item = styled.li<{ $isFirstRow: boolean }>`
  border-top: ${({ theme, $isFirstRow }) =>
    $isFirstRow
      ? "none"
      : `1px solid ${theme.neutral[200]}`};
`;
```

이제 그릴 범위가 `{ start: 41, end: 62 }`라면 그린 `li` 21개가 모두 구분선을 긋습니다. 고친 뒤에는 그림 2의 2, 3, 4번 행이 157, 250, 315px로 계산과 같았어요. 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 오도록 둔 뒤(`viewStart` 3,000), 그린 첫 행인 41번 행과 그다음 행에 구분선이 있는지 보는 통합 테스트도 더했습니다.

## 계산이 실제 화면과 맞았을까

마지막으로 계산한 행 위치가 실제 화면과 같은지 확인했습니다. 행을 모두 그리는 가상화 전 빌드라면 모든 행의 실제 높이를 잴 수 있는데요, 이 빌드에 1편과 같은 구성의 목록 응답(문서 1,939개, 폴더 28개)를 넣고, 행 1,939개와 카드 28개의 높이를 모두 재서 계산과 견줬습니다. 브라우저 글자 크기를 키워 1rem이 20px인 경우도 함께 봤어요.

| 1rem | 요약 없음, 0번 행 | 요약 없음, 나머지 행 | 요약 있음, 0번 행 | 요약 있음, 나머지 행 | 카드 높이와 계산의 차이 |
| --- | ---: | ---: | ---: | ---: | --- |

행 높이는 모두 표 1의 값에 구분선 1px을 더한 그대로였고, 카드 28개의 높이도 계산과 1px도 다르지 않았습니다. 가장 큰 폴더(문서 994개)의 카드 높이는 1rem이 16px일 때 64,609px, 20px일 때 80,513px로 두 경우 모두 계산과 같았어요.

가상화한 뒤에도 마찬가지였습니다. 1편의 측정에서 DOM에 있는 문서 행은 13개로 줄었지만, `main`의 스크롤 높이는 가상화 전과 후 모두 128,317px로 같았어요. 카드 높이를 행 위치로 미리 고정해 둔 덕분입니다.


## 정리

- 행 높이가 요약 유무로만 정해지게 해 두면, 행을 그리기 전에 `getRowOffsets`로 행 위치를 쌓을 수 있습니다. px로 정한 구분선에는 `remPx`를 곱하지 않습니다.
- 화면 구간은 카드 맨 위를 기준으로 브라우저에게 물어 재고, 위아래로 overscan(px)만큼 넓혀 걸친 행을 고릅니다. 처음처럼 행 개수로 정하면 화면 밖 카드가 비어 있게 됩니다.
- 카드에는 행을 모두 그린 높이와 그릴 첫 행의 위치만큼 위쪽 여백을 주고, 첫 화면은 빈 범위로 그린 뒤 `useLayoutEffect`에서 채웁니다.
- 범위가 같으면 이전 상태를 돌려줘 렌더링을 건너뛰고, 창 크기 변화는 `ResizeObserver`로 받습니다. 구분선은 DOM 순서가 아니라 폴더 안 순서로 긋습니다.
- 가상화하기 전 빌드에서 행 1,939개와 카드 28개의 높이를 재 보니 모두 계산과 같았고, 가상화한 뒤에도 스크롤 높이는 128,317px로 그대로였습니다.

[^effect]: 클릭 같은 상호작용이 아닐 때 effect가 언제 도는지는 React 문서의 주의 사항에 있습니다. [React의 useEffect 설명](https://react.dev/reference/react/useEffect)
