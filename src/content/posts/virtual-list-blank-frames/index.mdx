Knot 문서 탭 「주제별」 목록을 가상화한 뒤 휠 스크롤 중에 카드가 한 프레임 비어 보였는데, 행을 그리는 일이 느려서가 아니라 합성기 스레드가 메인 스레드를 기다리지 않고 먼저 스크롤한 프레임이 나가서였습니다. 빈 칸은 휠 한 번의 거리가 화면 아래로 미리 그려 둔 거리보다 길 때 생겨서, 미리 그릴 범위를 행 개수가 아니라 거리로 넓히고 실제 빌드에서 빈 칸 프레임을 세어 325px로 정했습니다. 「라이브러리 없이 목록 가상화」 시리즈 3편이고, 행 위치와 그릴 범위를 구하는 계산은 [2편](/posts/virtual-list-row-range/)에, 뒤로 가기에서 보인 빈 프레임은 [4편](/posts/virtual-list-back-navigation/)에 있습니다.

## 휠 스크롤의 빈 칸은 왜 생길까

Chrome은 휠 스크롤을 메인 스레드와 따로 합성기 스레드에서 화면에 내보낼 수 있어서, 메인 스레드가 범위를 다시 구하기 전의 DOM으로 그린 프레임이 먼저 나갑니다.

- 메인 스레드는 JavaScript, 스타일 계산, 레이아웃, 페인트 기록을 맡고, React의 렌더링과 `main`의 scroll 리스너도 여기서 돕니다.
- 합성기 스레드(compositor)는 메인 스레드가 넘긴 페인트 결과를 타일로 래스터해 두고, 레이어를 움직이고 겹쳐 화면에 내보낼 프레임을 만듭니다.
- 휠 이벤트를 막는 리스너가 없으면 합성기 스레드가 스크롤 위치를 바꾸고 프레임을 만들어서 메인 스레드가 바빠도 스크롤이 끊기지 않지만, 합성기가 쓰는 레이어는 메인 스레드가 마지막으로 넘긴 DOM으로 그린 것이라, 아직 DOM에 없는 행은 프레임에 나오지 않습니다.

미리 그릴 거리가 160px인 빌드에서 휠을 한 번 돌린 경우를 따라가 보겠습니다. 요약 없는 행(구분선을 더해 65px)만 있는 큰 카드에서 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 있고, 스크롤 영역(`main`)의 보이는 높이는 750px이며, 측정한 화면은 120Hz라 프레임이 8.3ms마다 한 장씩 나갑니다.

1. 휠을 돌리기 전 화면은 카드의 3,000~3,750px를 보여 주고, DOM에는 범위 `{ start: 43, end: 61 }`의 `li` 18개가 2,794~3,964px를 덮고 있습니다.
2. 휠을 아래로 한 번 돌려 300px 스크롤을 요청합니다.
3. 합성기 스레드가 스크롤 위치를 300px 내리고, 메인 스레드를 기다리지 않고 래스터해 둔 레이어로 프레임을 만듭니다.
4. 합성기 프레임의 화면은 3,300~4,050px인데 `li`는 3,964px에서 끝나서, 화면 아래쪽 86px에는 행 없이 카드 바탕이 보입니다.
5. 메인 스레드가 scroll 이벤트를 받아 범위를 `{ start: 48, end: 65 }`로 다시 구하고 React가 커밋하면, 다음 프레임부터는 `li`가 3,119~4,224px를 덮어 빈 칸이 없습니다.

빈 칸은 휠 한 번의 거리가 화면 아래로 그려 둔 거리보다 길 때 두 거리의 차이만큼 생깁니다. 그릴 범위는 넓힌 구간에 걸친 행을 행 경계까지 고르므로 그려 둔 거리는 미리 그릴 거리 이상이고, 요약 없는 행 카드에서는 미리 그릴 거리에 64px를 더한 값까지 됩니다. 그래서 휠 한 번이 미리 그릴 거리 이하면 어느 위치에서도 빈 칸이 없고, 미리 그릴 거리에 64px를 더한 값보다 길면 어느 위치에서나 빈 칸이 생기며, 두 값 사이면 화면과 행 경계가 어긋난 정도에 따라 달라집니다. 예를 들어 미리 그릴 거리 325px에서 휠이 420px이면 가장 큰 빈 칸은 420 − 325 = 95px이고, 3,000px 위치에서는 행 경계까지 344px를 그려 두어서 76px가 빕니다.

## 미리 그릴 범위를 왜 거리로 정했을까

행 개수로 넓히면 화면에 걸친 행이 없는 카드, 곧 화면 밖에 있는 카드의 첫 행을 미리 그리지 않기 때문입니다. 처음 이슈에는 화면 위아래로 행을 5개씩 더 그리기로 적었고 첫 구현도 화면에 걸친 행이 있을 때 위아래로 5행씩 더했는데, 걸친 행이 하나도 없는 카드는 넓힐 기준이 없어 아무 행도 그리지 않았습니다. 폴더가 28개라 스크롤하는 동안 폴더 경계를 자주 지나가고, 카드가 화면에 들어오는 첫 프레임은 합성기가 먼저 내보낼 수 있어서 폴더 경계를 지날 때마다 카드가 한 프레임 비어 보였습니다.

<Figure caption="표 1. 행 위치가 [0, 64, 157, 222, 287]인 카드에서 두 방식이 고르는 행" captionSide="top">

| 상황 | 행 개수 방식 (위아래 5행) | 거리 방식 (100px) |
| --- | --- | --- |
| 카드 아래쪽 끝이 화면 위쪽 끝과 맞닿음 (`viewStart` 287, `viewEnd` 900) | `{ start: 0, end: 0 }` | `{ start: 2, end: 4 }` |
| 카드 맨 위가 화면 아래쪽 끝보다 50px 아래 (`viewStart` −400, `viewEnd` −50) | `{ start: 0, end: 0 }` | `{ start: 0, end: 1 }` |

</Figure>

거리로 넓히면 화면 밖에 있어도 가까운 카드의 행은 미리 그리고, 넓힌 구간보다 먼 카드에는 행을 그리지 않습니다. 빈 칸이 생기는지는 한 프레임에 스크롤하는 거리로 정해지므로 행이 64px이든 92px이든 같은 기준을 쓸 수 있고, 값은 요약 없는 행 5개쯤인 325px로 시작해 실제 빌드에서 재서 정하기로 했습니다.

## 빈 칸 프레임은 어떻게 셌을까

카드에서 행이 덮지 않는 곳을 자홍색으로 칠하는 CSS를 넣고, 화면에 합성된 프레임을 CDP screencast로 받아 자홍색이 보인 프레임을 셌습니다. JavaScript로 DOM을 검사하면 메인 스레드에서 돌아서, 합성기가 먼저 내보낸 프레임이 화면에 어떻게 보였는지는 알 수 없기 때문입니다.

```js title="check-2-4.mjs"
const CARD = "section[aria-labelledby] > ul";
const BLANK_CSS =
  `${CARD}{background:#ff00ff !important}` +
  `${CARD} > li{background:#ffffff !important}`;
```

카드 `ul`에는 행을 모두 그린 높이와 위쪽 여백이 들어 있어서, `li`가 덮지 않는 `ul`의 영역은 위쪽 여백과 마지막 `li` 아래입니다. 앱의 색 가운데 자홍색(#ff00ff)에 가까운 색이 없어서, 프레임에 자홍색이 보이면 행이 없는 카드 영역이 화면에 나간 것입니다. [Chrome DevTools Protocol](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast)에 `Page.startScreencast`를 보내면 Chrome이 화면에 합성한 프레임을 하나씩 보내 주는데, 합성기가 메인 스레드를 기다리지 않고 만든 프레임도 함께 옵니다. 창이 1200×818이라 프레임의 가로줄 하나가 CSS 1px이고, 자홍색에 가까운 픽셀이 20개 넘는 가로줄이 4줄 이상인 프레임을 빈 칸 프레임으로 셌습니다.

빌드마다 휠을 16ms 간격으로 150번 돌려(150px 휠이면 22,500px) CPU 제한 없음과 4배 느림에서 프레임을 모았고, 개선 전 빌드와 미리 그릴 거리만 0px, 160px, 325px, 650px로 바꾼 빌드 네 개를 쟀습니다. 모든 빌드는 세션 녹화가 없는 프로덕션 빌드입니다.

## 325px는 어떻게 정했을까

휠 한 번에 150px와 300px씩 돌렸을 때 빈 칸 프레임이 하나도 없던 값 가운데, DOM에 두는 행이 적은 325px를 골랐습니다.

<Figure caption="표 2. 휠 스크롤 빈 칸 프레임 (CPU 4배 느림, 괄호 안은 CPU 제한 없음)" captionSide="top">

| 미리 그릴 거리 | 휠 한 번 150px | 휠 한 번 300px |
| ---: | --- | --- |
| 0px | 400프레임 중 221개 (392프레임 중 220개) | 재지 않음 |
| 160px | 403프레임 중 0개 (404프레임 중 0개) | 396프레임 중 216개 (402프레임 중 224개) |
| 325px | 404프레임 중 0개 (406프레임 중 0개) | 410프레임 중 0개 (391프레임 중 0개) |
| 650px | 401프레임 중 0개 (404프레임 중 0개) | 408프레임 중 0개 (427프레임 중 0개) |

</Figure>

빈 칸은 휠 한 번의 거리가 미리 그릴 거리보다 긴 두 조건에서만 생겼고, 휠을 돌리는 동안 받은 프레임의 절반쯤에 보였습니다. 프레임마다 자홍색 줄의 가장 큰 값은 150줄과 140줄로, 휠 거리에서 미리 그릴 거리를 뺀 150 − 0px, 300 − 160px와 같았습니다. CPU를 4배 느리게 해도 빈 칸 프레임 수가 거의 같아서(221개와 220개, 216개와 224개), 빈 칸은 행을 그리는 시간이 길어서가 아니라 합성기 프레임이 메인 스레드의 일보다 먼저 나가는 순서 때문에 생긴다고 볼 수 있습니다.

650px도 빈 칸이 없었지만, 미리 그릴 거리가 길수록 탭에 들어올 때 만드는 요소와 스크롤하며 더하고 지우는 `li`가 함께 늘어납니다.

<Figure caption="표 3. 미리 그릴 거리마다 DOM에 둔 행과 화면 요소 (실제 빌드)" captionSide="top">

| 미리 그릴 거리 | 탭에 들어온 직후 | 22,500px 스크롤한 뒤 |
| ---: | --- | --- |
| 0px | 행 8개, 요소 309개 | 행 12개, 요소 346개 |
| 160px | 행 11개, 요소 336개 | 행 18개, 요소 400개 |
| 325px | 행 13개, 요소 354개 | 행 22개, 요소 436개 |
| 650px | 행 18개, 요소 399개 | 행 32개, 요소 526개 |

</Figure>

스크롤한 뒤의 행 수는 (보이는 높이 750px + 미리 그릴 거리 × 2) ÷ 65px 안팎이고, 탭에 들어온 직후에 더 적은 까닭은 첫 카드 위로는 넓힌 구간이 카드 밖이라 그릴 행이 없기 때문입니다. 행을 그리고 지우는 일이 스크롤을 늦추지도 않아서, 150px 휠로 150번 스크롤하는 동안 CPU 4배 느림의 프레임 간격은 개선 전 빌드가 가운데값 8.3ms, 99% 11.5ms, 최대 13ms였고 325px 빌드가 8.4ms, 12.3ms, 13ms였으며, 50ms 넘는 긴 작업은 두 빌드 모두 없었습니다.

휠 한 번에 325px보다 많이 스크롤하면 빈 칸이 생길 수 있어서, 측정 결과와 함께 상수 주석에 적어 두었습니다. 같은 계산으로 화면 위치 65곳(행 하나 길이)을 모두 돌려 보면, 350px 휠은 65곳 가운데 25곳에서 최대 25px, 400px 휠은 모든 곳에서 최대 75px가 빕니다.

```ts title="overscan.ts"
/**
 * 화면 위아래로 넓혀서 미리 그릴 거리(px).
 * …
 * 실제 빌드에서 휠 한 번에 300px씩 스크롤했을 때
 * 160px는 빈 칸이 보였고 325px는 보이지 않아서
 * 325px로 정했어요.
 * 휠 한 번에 이 거리보다 많이 스크롤하면
 * 빈 칸이 보일 수 있어요.
 */
export const OVERSCAN_PX = 325;
```

## 휠 스크롤에서 아직 막지 못한 빈 칸은 무엇일까

휠 한 번에 325px보다 많이 스크롤하는 장치나 설정에서는 빈 칸이 한 프레임 보일 수 있고, 아래 경우는 재지 않았거나 다 막지 못했습니다.

- 스크롤바를 끌어 멀리 이동하는 동작은 따로 재지 않았습니다. 그린 행이 화면을 덮지 못하면 scroll 이벤트 안에서 렌더링하게 해 두었지만(4편), 합성기가 먼저 그리는 프레임까지 막는지는 확인하지 않았습니다.
- 휠을 위로 돌리면 화면 위쪽 끝이 그린 첫 행보다 위로 올라가는지가 빈 칸을 정하는데, 측정은 휠을 아래로만 돌렸습니다.
- 세션 녹화를 켜고 CPU를 4배 느리게 하면, 300px 휠을 세 번 잰 가운데 한 번 빈 칸 프레임이 4개(425프레임 중) 나왔고 스크롤 프레임 간격의 99% 값도 12ms대에서 15~20ms로 늘었습니다. 녹화 도구가 행을 그리고 지우는 DOM 변화까지 기록하기 때문입니다.

## 정리

- 휠 스크롤의 빈 칸은 합성기 스레드가 메인 스레드보다 먼저 스크롤한 프레임에서 생기고, 휠 한 번의 거리가 화면 아래로 그려 둔 거리보다 긴 만큼 보입니다.
- 미리 그릴 범위를 행 개수로 넓히면 화면 밖 카드의 첫 행을 그리지 않아서, 거리로 넓혀 가까운 카드도 미리 그리고 행 높이와 관계없이 같은 기준을 쓰게 했습니다.
- 빈 칸 프레임은 행이 덮지 않는 카드 영역을 자홍색으로 칠하고 CDP screencast로 받은 프레임에서 셌습니다.
- CPU를 4배 느리게 해도 빈 칸 프레임 수가 같아서, 빈 칸은 그리는 속도가 아니라 프레임이 나가는 순서의 문제였습니다.
- 150px와 300px 휠에서 빈 칸이 없던 325px와 650px 가운데, DOM에 두는 행이 적은 325px를 골랐습니다.
