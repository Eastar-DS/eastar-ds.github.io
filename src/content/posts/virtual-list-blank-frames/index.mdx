Knot의 「주제별」 탭은 녹음에서 만든 문서를 AI가 나눈 주제 폴더별로 묶어 보여 주는 목록(아래에서는 문서 목록)이고, 받은 문서를 모두 메모리에 두고 화면 근처의 행만 DOM에 그리는 목록 가상화를 넣었으므로([1편](/posts/virtualized-document-list/)) 스크롤로 새 행이 화면에 들어올 때 아직 그리지 않은 곳이 한 프레임 비어 보일 수 있습니다. Chrome은 휠 스크롤 프레임을 메인 스레드가 행을 다시 그리기 전에 화면에 내보낼 수 있어서, 화면 위아래로 미리 그려 둘 거리를 휠 한 번에 움직이는 거리보다 길게 잡아야 합니다. 2026년 11월 12일에 실제 빌드에서 미리 그릴 거리를 0px, 160px, 325px, 650px로 바꿔 가며 빈 칸이 보인 프레임을 세었고, 휠 한 번에 150px와 300px씩 스크롤할 때 빈 칸 프레임이 하나도 없던 값 가운데 DOM에 두는 행이 적은 325px를 골랐습니다.

문서 목록은 폴더마다 카드(`ul`)를 두고, 카드에는 행을 모두 그린 높이를 주되 화면 구간을 위아래로 미리 그릴 거리만큼 넓힌 구간에 걸친 행만 `li`로 그립니다. 그리는 행 묶음을 범위 `{ start, end }`라고 하며, 행 번호는 0부터 세고 `end`는 그리지 않는 첫 행 번호입니다([2편](/posts/virtual-list-row-range/)).

## 휠 스크롤 중 빈 칸은 왜 생길까

Chrome은 휠 스크롤 프레임을 메인 스레드와 따로 합성기 스레드에서 만들 수 있어서, 메인 스레드가 그릴 행을 다시 고르기 전의 DOM으로 만든 프레임이 먼저 화면에 나갈 수 있기 때문입니다. 프레임은 화면에 한 번 내보내는 그림 한 장을 말하고, 브라우저 안에서는 아래처럼 일을 나눠 맡습니다.

- 메인 스레드는 JavaScript 실행, 스타일 계산, 레이아웃, 페인트 기록을 맡고, React 렌더링과 스크롤 영역(`main`)의 scroll 리스너도 메인 스레드에서 돕니다.
- 합성기 스레드(compositor thread)는 메인 스레드가 넘긴 레이어(페이지를 나눠 따로 그리는 판)를 타일로 나눠 래스터 스레드에 맡기고, 래스터(그리기 명령을 픽셀로 바꾸는 일)된 레이어를 움직이고 겹쳐 화면에 내보낼 프레임을 만듭니다([Chrome의 렌더링 단계 설명](https://developer.chrome.com/blog/inside-browser-part3)). 그래서 합성기 스레드는 이미 픽셀로 바꿔 둔 그림의 위치만 바꿔 스크롤한 프레임을 만들 수 있고, DOM에 없는 행은 픽셀로 바꿔 둔 그림에도 없습니다.
- [Chrome의 입력 처리 설명](https://developer.chrome.com/blog/inside-browser-part4)을 보면, 합성기 스레드가 메인 스레드를 기다릴지는 wheel이나 touch처럼 스크롤을 막을 수 있는 입력 이벤트의 리스너에 달려 있습니다. 스크롤을 막을 수 있는 리스너가 없거나 스크롤을 막지 않는(`passive`) 리스너만 있으면 합성기 스레드는 메인 스레드를 기다리지 않고 새 프레임을 만들 수 있습니다. 문서 목록이 범위를 다시 구하는 리스너는 스크롤이 일어난 뒤에 알리는 scroll 이벤트에 `passive: true`로 달려 있어서, 아직 DOM에 없는 행은 합성기 스레드가 먼저 만든 프레임에 나오지 않습니다.

미리 그릴 거리가 160px인 빌드에서 휠을 한 번 돌린 경우를 따라가 보겠습니다. 요약 없는 행(구분선을 더해 65px)만 994개 있는 큰 카드에서 화면 위쪽 끝이 카드 맨 위에서 3,000px 아래에 있고(`viewStart` 3,000), 측정한 창(1200×818)에서 `main`의 보이는 높이는 750px입니다.

1. 휠을 돌리기 전 화면은 카드의 3,000–3,750px를 보여 주고, DOM에는 범위 `{ start: 43, end: 61 }`의 `li` 18개가 2,794–3,964px를 덮고 있습니다.
2. 휠을 아래로 한 번 돌려 300px 스크롤을 요청합니다.
3. 합성기 스레드가 스크롤 위치를 300px 내리고, 메인 스레드를 기다리지 않고 래스터해 둔 레이어로 프레임을 만듭니다.
4. 합성기 스레드가 만든 프레임의 화면은 3,300–4,050px인데 `li`는 3,964px에서 끝나서, 화면 아래쪽 86px에는 행 없이 카드 바탕이 보입니다.
5. 메인 스레드가 scroll 이벤트를 받아 범위를 `{ start: 48, end: 65 }`로 다시 구하고 React가 커밋하면, 다음 프레임부터는 `li`가 3,119–4,224px를 덮어 빈 칸이 없습니다.

빈 칸은 휠 한 번의 거리가 화면 아래로 그려 둔 거리보다 길 때 두 거리의 차이만큼 생깁니다. 그릴 행은 넓힌 구간에 조금이라도 걸친 행을 행 경계까지 고르므로, 화면 아래로 그려 둔 거리는 미리 그릴 거리 이상이고 넓힌 구간 끝에 걸친 행의 나머지만큼 더 깁니다. 요약 없는 행은 65px이고 끝에 맞닿기만 한 행은 고르지 않으므로, 더 길어지는 길이는 많아야 64px입니다. 그래서 휠 한 번의 거리에 따라 빈 칸은 아래처럼 달라집니다.

- 미리 그릴 거리 이하: 어느 화면 위치에서도 빈 칸이 없습니다.
- 미리 그릴 거리에 64px를 더한 값보다 김: 어느 화면 위치에서나 빈 칸이 생깁니다.
- 두 값 사이: 화면 끝과 행 경계가 어긋난 정도에 따라 빈 칸이 생기기도 하고 생기지 않기도 합니다.

예를 들어 미리 그릴 거리 325px에서 휠이 420px이면 가장 큰 빈 칸은 420 − 325 = 95px이고, 3,000px 위치에서는 행 경계까지 344px를 그려 두어서 76px가 빕니다.

```html title="휠을 돌리기 전: 0–3번 행이 0–259px를 덮음"
      </li>
```


카드 `ul`은 행을 모두 그린 높이와 그린 첫 행의 시작 위치만큼의 위쪽 여백을 인라인 스타일로 갖고 있어서(계산은 [2편](/posts/virtual-list-row-range/)), 행이 덮지 않는 위쪽 여백과 마지막 `li` 아래에는 `ul`의 바탕이 보입니다. 휠 한 번에 100px를 움직였는데 화면 아래로 그려 둔 거리가 65px(259 − 194)라서, 차이인 35px가 빈 칸으로 보였습니다.

## 미리 그릴 범위를 왜 거리로 정했을까

행 개수로 넓히면 화면에 걸친 행이 없는 카드, 곧 화면 밖에 있는 카드는 행을 하나도 미리 그리지 않아서, 카드가 화면에 들어오는 첫 프레임에 첫 행들이 빌 수 있기 때문입니다. Knot 저장소의 이슈 #1117(1편의 결정 기록 ADR 1117과 번호가 같은 이슈)에는 화면 위아래로 행을 5개씩 더 그리기로 적었고, 처음 짠 코드(커밋하지 않음)도 화면에 걸친 행이 있을 때만 위아래로 5행을 더했습니다. 문서 목록은 폴더 28개의 카드가 이어져 있어 스크롤하는 동안 카드 경계를 자주 지나가므로, 행 개수 방식이었다면 카드가 화면에 들어올 때마다 한 프레임 비어 보일 수 있었습니다. 다만 행 개수 방식으로 빌드해서 잰 기록은 없고, 첫 커밋부터 거리 방식으로 바꿨습니다.

거리 방식은 화면 위아래를 같은 px만큼 넓힌 구간에 조금이라도 걸친 행을 고르므로, 화면 밖이라도 가까운 카드의 첫 행은 미리 그리고 넓힌 구간보다 먼 카드에는 행을 그리지 않습니다. 예를 들어 행 위치가 `[0, 64, 157, 222, 287]`인 카드의 맨 위가 화면 아래쪽 끝보다 50px 아래에 있으면, 행 개수 방식은 걸친 행이 없어 아무 행도 고르지 않지만 거리를 100px로 넓히면 0번 행을 고릅니다(두 방식의 비교 표는 [2편](/posts/virtual-list-row-range/)).

빈 칸이 생기는지는 한 프레임에 스크롤하는 거리로 정해지므로, 거리로 정하면 행이 64px이든 92px이든 같은 기준을 쓸 수 있습니다. 값은 요약 없는 행 5개쯤인 325px로 시작해서, 실제 빌드에서 빈 칸이 생기는지 재서 정하기로 했습니다.

## 빈 칸 프레임은 어떻게 셌을까

카드 바탕을 자홍색, 행 바탕을 흰색으로 칠하는 측정용 CSS를 넣고, 화면에 합성된 프레임을 CDP(Chrome DevTools Protocol, 자동화 도구가 Chrome을 조종하는 프로토콜)의 screencast로 받아 자홍색이 보인 프레임을 셌습니다. JavaScript로 DOM을 검사하는 코드는 메인 스레드에서 돌아서, 합성기 스레드가 먼저 내보낸 프레임이 화면에 어떻게 보였는지는 알 수 없기 때문입니다.

측정 스크립트가 페이지에 넣은 CSS는 아래와 같습니다.

```js title="check-2-4.mjs"
const CARD = "section[aria-labelledby] > ul";
const BLANK_CSS =
  `${CARD}{background:#ff00ff !important}` +
  `${CARD} > li{background:#ffffff !important}`;
```

앞 절의 코드 칸에서 행이 덮지 않는 `ul`의 바탕이 자홍색(#ff00ff)으로 칠해지므로, 프레임에 자홍색이 보이면 행이 없는 카드 영역이 화면에 나간 것입니다. Knot 프론트엔드 코드의 색 가운데 자홍색에 가까운 색은 없었고, 행을 모두 그리는 가상화 전 빌드에서도 빈 칸 프레임은 0개였습니다.

- CDP의 [`Page.startScreencast`](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast)를 보내면 Chrome이 화면 프레임을 하나씩 보내 줍니다. 합성기 스레드가 메인 스레드보다 먼저 만든 프레임도 함께 잡힌다는 점은 문서에 없고, 측정 스크립트를 만들 때 세운 전제입니다.
- 프레임은 가로 1200, 세로 818을 넘지 않는 PNG 이미지로 받았고, 자홍색에 가까운 픽셀(빨강과 파랑이 225보다 크고 초록이 40보다 작은 픽셀)이 20개 넘는 PNG 이미지 가로줄이 4줄 이상인 프레임을 빈 칸 프레임으로 셌습니다. 측정 창은 1200×818에 화면 배율 2였고, 결과 파일에 PNG 이미지 크기를 적지 않아서 PNG 가로줄 하나가 CSS 몇 px인지는 확인하지 못했습니다.
- 휠은 `main`의 맨 위에서 아래로만 16ms 간격으로 150번 돌렸고(150px 휠이면 22,500px), CPU 제한 없음과 CPU 4배 느림(CDP로 CPU를 4배 느리게 흉내 낸 조건)에서 따로 모았습니다.
- 표 1의 받은 프레임 수는 CDP가 보낸 screencast 프레임의 수이고, 표 3의 프레임 간격은 같은 동안 페이지에서 `requestAnimationFrame` 콜백 사이를 잰 값이라 두 개수는 다릅니다. 결과 파일에는 프레임을 받은 시간의 길이를 적지 않았습니다.
- 브라우저는 Playwright로 띄운 Chrome이고, 측정 서버는 로컬에 두었습니다.

잰 빌드는 모두 다섯 개로, 행을 모두 그리는 가상화 전 빌드 하나와 미리 그릴 거리만 0px, 160px, 325px, 650px로 바꾼 가상화 빌드 네 개입니다. 가상화 전과 325px 빌드는 세션 녹화 도구(사용자의 화면 동작을 DOM 변화로 기록해 다시 보여 주는 분석 도구)를 넣지 않은 프로덕션 빌드이고, 나머지 세 빌드는 325px 빌드에서 미리 그릴 거리 상수만 바꿨습니다.

목록 응답은 폴더 28개, 문서 1,939개인 시험용 응답을 썼습니다. 11월 5일에 운영에서 저장한 응답이 지워져서, 폴더별 문서 수와 요약이 있는 행 8개의 위치를 저장한 응답과 같게 하고 제목과 폴더 이름만 지어 다시 만들었습니다. 11월 12일에 다시 만든 응답으로 가상화 전 빌드를 그리면 화면 요소 17,696개, `main` 스크롤 높이 128,317px였는데, 스크롤 높이는 11월 5일 값과 같았고 요소 수는 11월 5일 기록과 조금 달랐으며, 응답을 다시 만들 때 운영 서버에는 요청을 보내지 않았습니다.

## 325px는 어떻게 정했을까

휠 한 번에 150px와 300px씩 돌렸을 때 빈 칸 프레임이 하나도 없던 값 가운데, DOM에 두는 행이 적은 325px를 골랐습니다.

<Figure caption="표 1. 휠 스크롤 중 받은 프레임과 빈 칸 프레임 (2026년 11월 12일, CPU 4배 느림, 괄호 안은 CPU 제한 없음)" captionSide="top">

| 미리 그릴 거리 | 휠 한 번 150px | 휠 한 번 300px |
| ---: | --- | --- |
| 0px | 400프레임 중 221개 (392프레임 중 220개) | 재지 않음 |
| 160px | 403프레임 중 0개 (404프레임 중 0개) | 396프레임 중 216개 (402프레임 중 224개) |
| 325px | 404프레임 중 0개 (406프레임 중 0개) | 410프레임 중 0개 (391프레임 중 0개) |
| 650px | 401프레임 중 0개 (404프레임 중 0개) | 408프레임 중 0개 (427프레임 중 0개) |

</Figure>

빈 칸은 휠 한 번의 거리가 미리 그릴 거리보다 긴 두 조건(0px에 150px 휠, 160px에 300px 휠)에서 생겼고, 휠을 돌리는 동안 받은 프레임의 55–56%에 보였습니다. 프레임마다 센 자홍색 PNG 가로줄의 가장 큰 값은 150줄과 140줄로, 휠 거리에서 미리 그릴 거리를 뺀 150 − 0, 300 − 160과 수가 같았습니다. 다만 PNG 가로줄과 CSS px의 비율은 기록에 없어서, 줄 수와 px 값의 수가 같다는 점을 빈 칸 높이(px)를 잰 값으로 쓰지는 않았습니다. CPU를 4배 느리게 해도 빈 칸 프레임 수가 거의 같아서(221개와 220개, 216개와 224개), 빈 칸은 행을 그리는 시간이 길어서가 아니라 합성기 스레드의 프레임이 메인 스레드의 일보다 먼저 나가는 순서 때문에 생긴다고 볼 수 있습니다.

650px도 빈 칸이 없었지만, 미리 그릴 거리가 길수록 탭에 들어올 때 만드는 요소와 DOM에 두는 행이 함께 늘어납니다.

<Figure caption="표 2. 미리 그릴 거리마다 DOM에 둔 행과 화면 요소 (표 1과 같은 측정)" captionSide="top">

| 미리 그릴 거리 | 탭에 들어온 직후 | 22,500px 스크롤한 뒤 |
| ---: | --- | --- |
| 0px | 행 8개, 요소 309개 | 행 12개, 요소 346개 |
| 160px | 행 11개, 요소 336개 | 행 18개, 요소 400개 |
| 325px | 행 13개, 요소 354개 | 행 22개, 요소 436개 |
| 650px | 행 18개, 요소 399개 | 행 32개, 요소 526개 |

</Figure>

스크롤한 뒤의 행 수는 (보이는 높이 750px + 미리 그릴 거리 × 2) ÷ 65px 안팎이고, 탭에 들어온 직후에 더 적은 까닭은 첫 카드 위로는 넓힌 구간이 카드 밖이라 그릴 행이 없기 때문입니다. 325px는 650px보다 스크롤한 뒤의 행이 10개 적었습니다.

같은 계산으로 화면 위쪽 끝을 행 하나 길이(65px) 안에서 1px씩 바꾼 65곳을 모두 돌려 보면, 325px에서 350px 휠은 65곳 가운데 25곳에서 최대 25px, 400px 휠은 모든 곳에서 최대 75px가 빕니다. 그래서 휠 한 번에 325px보다 많이 스크롤하면 빈 칸이 생길 수 있다는 점을 측정 결과와 함께 상수 주석에 썼습니다.

```ts title="overscan.ts"
/**
 * 화면 위아래로 넓혀서 미리 그릴 거리(px).
 * …
 * 실제 빌드에서 휠 한 번에 300px씩 스크롤했을 때
 * 160px는 빈 칸이 보였고 325px는 보이지 않아서
 * 325px로 정했어요.
 * 휠 한 번에 이 거리보다 많이 스크롤하면
 * 빈 칸이 보일 수 있어요.
 */
export const OVERSCAN_PX = 325;
```

## 행을 더 그려도 스크롤 프레임 간격은 괜찮았을까

세션 녹화 도구가 없는 빌드에서는 325px 빌드의 프레임 간격이 가상화 전 빌드와 거의 같았고, 녹화 도구를 켠 빌드끼리 견주면 CPU 4배 느림의 99% 값이 가상화 전 빌드의 11.8–12.7ms에서 가상화 후 빌드의 15.5–19.5ms로 늘었습니다. 프레임 간격은 페이지에서 `requestAnimationFrame`이 연달아 불린 시간 차이이고, 99% 값은 간격을 짧은 순서로 늘어놓았을 때 99%째에 있는 값입니다. 11월 12일 측정에서 간격의 가운데값은 빌드마다 8.3ms 안팎이라, 99% 값과 가장 긴 간격은 보통 간격 8.3ms와 견줘 읽습니다. 측정 화면의 주사율은 결과 파일에 적지 않았습니다.

<Figure caption="표 3. 150px 휠로 150번 스크롤하는 동안의 프레임 간격 (표 1과 같은 측정, CPU 4배 느림, 세션 녹화 도구 없음)" captionSide="top">

| 빌드 | 가운데값 | 99% 값 | 가장 긴 간격 | 긴 작업(50ms 이상) |
| --- | ---: | ---: | ---: | ---: |
| 가상화 전 (행을 모두 그림) | 8.3ms | 11.5ms | 13ms | 0개 |
| 325px | 8.4ms | 12.3ms | 13ms | 0개 |

</Figure>

긴 작업은 [메인 스레드가 50ms 이상 쉬지 않고 바쁜 구간](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming)이고, 스크롤하며 행을 더하고 지워도 두 빌드 모두 긴 작업이 없었습니다.

세션 녹화 도구를 켠 개선 후 빌드를 CPU 4배 느림에서 300px 휠로 세 번 재 보면, 한 번은 425프레임 가운데 4개가 빈 칸 프레임이었고, 녹화 도구를 켠 측정들의 99% 값은 15.5–19.5ms였습니다. 팀 보고는 녹화 도구가 행을 그리고 지우는 DOM 변화까지 기록하기 때문으로 보았지만, 프로파일로 나눠 확인하지는 않았습니다.

## 휠 스크롤에서 아직 막지 못한 빈 칸은 무엇일까

휠 한 번에 325px보다 많이 스크롤하는 장치나 설정에서는 빈 칸이 한 프레임 보일 수 있고, 아래 경우는 재지 않았거나 다 막지 못했습니다.

- 스크롤바를 끌어 멀리 이동하는 동작은 재지 않았습니다. 그린 행이 화면을 덮지 못하면 scroll 이벤트 안에서 렌더링하게 해 두었지만([4편](/posts/virtual-list-back-navigation/)), 합성기 스레드가 먼저 만드는 프레임까지 막는지는 확인하지 않았습니다.
- 휠을 위로 돌리면 화면 위쪽 끝이 그린 첫 행보다 위로 올라가는지가 빈 칸을 정하는데, 측정은 휠을 아래로만 돌렸습니다.
- 세션 녹화 도구를 켠 빌드에서는 300px 휠에서도 빈 칸 프레임이 나온 적이 있습니다.

## 정리

- 휠 스크롤의 빈 칸은 합성기 스레드가 메인 스레드보다 먼저 스크롤한 프레임에서 생기고, 휠 한 번의 거리가 화면 아래로 그려 둔 거리보다 긴 만큼 보입니다.
- 미리 그릴 범위를 행 개수로 넓히면 화면 밖 카드의 첫 행을 그리지 않아서, 거리로 넓혀 가까운 카드도 미리 그리고 행 높이와 관계없이 같은 기준을 쓰게 했습니다.
- 빈 칸 프레임은 행이 덮지 않는 카드 영역을 자홍색으로 칠하고, CDP screencast로 받은 프레임에서 셌습니다.
- CPU를 4배 느리게 해도 빈 칸 프레임 수가 거의 같아서, 빈 칸은 그리는 속도보다 프레임이 나가는 순서와 관계가 있었습니다.
- 150px와 300px 휠에서 빈 칸이 없던 325px와 650px 가운데 DOM에 두는 행이 적은 325px를 골랐고, 녹화 도구가 없는 빌드에서는 스크롤 프레임 간격도 가상화 전과 거의 같았습니다.
