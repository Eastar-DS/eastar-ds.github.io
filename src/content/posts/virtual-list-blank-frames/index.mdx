[1편](/posts/virtualized-document-list/)에서 Knot 문서 목록에 리스트 가상화를 넣어, 문서 1,939개를 모두 그리던 화면을 보이는 행과 overscan 안의 행만 그리게 바꿨습니다. 문서 목록은 폴더마다 위에 폴더 이름이 있고, 그 아래 흰 카드 안에 문서가 한 줄씩 행으로 들어가는데요. 카드 높이는 행을 모두 그린 높이로 고정해 두고, 그리지 않은 행의 자리는 비워 둡니다.

그런데 보이는 행만 그리면 빠르게 스크롤할 때 화면이 잠깐 비어 보일 수 있습니다. 화면에 새로 들어온 곳에 행이 아직 없어서 카드 바탕만 보이는 건데요, 이 글에서는 이렇게 행 없이 카드 바탕만 보이는 부분을 「빈 칸」이라고 부를게요. 그래서 화면 위아래로 행을 더 그려 두는 여유분인 overscan을 두는데, 문제는 얼마나 더 그려 두느냐입니다. 너무 적으면 빈 칸이 보이고, 너무 많으면 가상화로 줄인 DOM이 다시 늘어나니까요.

휠 스크롤에서 빈 칸이 생기는 까닭은 Chrome이 화면을 그리는 순서에 있었습니다. 브라우저가 화면에 한 번 내보내는 그림 한 장을 프레임이라고 하는데요, Chrome은 휠로 스크롤한 프레임을 행을 다시 고르는 JavaScript보다 먼저 내보낼 수 있어요. 그래서 overscan을 0px, 160px, 325px, 650px로 바꾼 빌드를 만들고, 휠로 스크롤하는 동안 화면에 나간 프레임을 한 장씩 받아 빈 칸이 보인 프레임을 세어 봤습니다.

재 보니 휠 한 번의 거리가 overscan보다 길 때(0px에 150px 휠, 160px에 300px 휠)는 받은 프레임의 절반 넘게 빈 칸이 보였고, 325px와 650px에서는 150px 휠과 300px 휠 모두 한 장도 보이지 않았습니다. **그래서 빈 칸이 없던 두 값 가운데 DOM에 두는 행이 적은 325px로 정했습니다.**

## 휠로 스크롤하면 왜 화면이 비어 보일까

브라우저 안에서 화면을 만드는 일은 크게 두 스레드가 나눠 맡습니다[^threads].

- 메인 스레드는 JavaScript를 실행하고, 스타일과 레이아웃을 계산하고, 무엇을 어떻게 그릴지 기록합니다. React가 행을 그리는 일과, 스크롤할 때마다 그릴 범위를 다시 구하는 일도 여기서 돌아요.
- 합성기 스레드(compositor thread)는 메인 스레드가 넘겨준 내용을 픽셀로 바꾼 그림을 가지고, 위치를 옮기고 겹쳐서 화면에 내보낼 프레임을 만듭니다.

스크롤은 이미 그려 둔 그림의 위치만 옮기면 되니, 합성기 스레드가 메인 스레드를 기다리지 않고 혼자 처리할 수 있습니다. 합성기 스레드가 메인 스레드를 기다리는 건 입력 이벤트 리스너가 달린 영역에서 입력이 들어왔을 때인데요[^input]. 그 리스너가 스크롤을 막을 수도 있기 때문이에요. 문서 목록은 그릴 범위를 스크롤 영역(`main`)의 scroll 이벤트에서 다시 구합니다. scroll 이벤트는 스크롤이 일어난 뒤에 오는 알림이라 스크롤을 막을 수 없고[^scroll-event], 리스너도 `passive: true`로 달았어요. 합성기 스레드가 이 리스너를 기다릴 까닭이 없는 거죠.

문제는 합성기 스레드가 가진 그림에 DOM에 없는 행은 없다는 점입니다. 아직 그리지 않은 행은 픽셀로 바꿔 둔 그림에도 없으니까요. 휠 한 번에 스크롤하는 거리가 화면 아래로 그려 둔 거리보다 길면, 합성기 스레드가 먼저 내보낸 프레임에는 그 차이만큼 카드 바탕이 보입니다.

Knot에서 휠을 한 번 돌린 경우를 따라가 볼게요. 가장 큰 카드처럼 행이 994개 있고, 모두 요약 없는 행이라 행 하나가 구분선까지 65px인 카드입니다(행 높이와 구분선은 [2편](/posts/virtual-list-row-range/)에서 다뤘어요). 화면 위쪽 끝은 카드 맨 위에서 3,000px 아래에 있고, `main`의 보이는 높이는 750px, overscan은 160px라고 해 보겠습니다.

1. 휠을 돌리기 전 화면은 카드의 3,000–3,750px를 보여 줍니다. 그린 행은 43–60번 행 18개로, 2,794–3,964px를 덮고 있어요. 화면 아래로는 214px를 더 그려 두었습니다.
2. 휠을 아래로 한 번 돌려 300px를 스크롤합니다.
3. 합성기 스레드는 메인 스레드를 기다리지 않고, 가진 그림으로 3,300–4,050px를 보여 주는 프레임을 만들어요.
4. 그런데 그린 행은 3,964px에서 끝나서, 화면 아래쪽 86px(4,050 − 3,964)에는 행 없이 카드 바탕이 보입니다. 이게 빈 칸이에요.
5. 메인 스레드가 scroll 이벤트를 받아 그릴 범위를 48–64번 행으로 다시 구하고 React가 DOM에 반영하면, 다음 프레임부터는 행이 3,119–4,224px를 덮어 빈 칸이 사라집니다.

빈 칸의 높이는 휠 한 번의 거리에서 화면 아래로 그려 둔 거리를 뺀 값입니다. 위 예에서는 300 − 214 = 86px였죠. 그려 둔 거리가 overscan 160px보다 54px 긴 까닭은, overscan 끝에 조금이라도 걸친 행은 통째로 그리기 때문이에요. 그래서 그려 둔 거리는 overscan보다 짧아지지 않고, 길어지는 몫은 행 하나보다 짧습니다. 휠 한 번이 overscan보다 길지 않으면 어느 위치에서 스크롤해도 빈 칸이 생기지 않는다는 뜻이에요.

아래 데모가 같은 계산을 보여 줍니다. 처음 값은 위의 예와 같이 overscan 160px, 휠 한 번 300px예요. 데모의 「넓힌 구간」은 화면을 위아래로 overscan만큼 넓힌 구간이고, 여기에 걸친 행을 그립니다. 오른쪽 칸 아래쪽에 86px 빈 칸이 보일 텐데요, overscan을 325px로 올려 보시겠어요? 반대로 overscan을 325px에 둔 채 휠 한 번을 400px로 늘리면, 이번에는 56px가 다시 비어 보일 거예요.

## 빈 칸이 보인 프레임은 어떻게 셌을까

빈 칸은 합성기 스레드가 먼저 내보낸 프레임에만 잠깐 보이기 때문에, JavaScript로 DOM을 검사해서는 찾을 수 없습니다. 검사 코드도 메인 스레드에서 도는데, 메인 스레드가 일할 차례가 왔을 때는 이미 행을 다시 그린 뒤일 수 있으니까요. 그래서 화면에 실제로 나간 프레임을 한 장씩 받아서 봤습니다[^screencast].

받은 프레임에서 빈 칸을 쉽게 찾으려고, 측정할 때만 카드 바탕을 자홍색, 행 바탕을 흰색으로 칠하는 CSS를 넣었습니다. 측정 스크립트가 넣은 CSS를 읽기 쉽게 두 줄로 나누면 아래와 같아요.

```js title="check-2-4.mjs"
const CARD = "section[aria-labelledby] > ul";
const BLANK_CSS =
  `${CARD}{background:#ff00ff !important}` +
  `${CARD} > li{background:#ffffff !important}`;
```

카드(`ul`) 안에서 행(`li`)이 덮지 않은 곳만 자홍색으로 남으니, 프레임에 자홍색이 보이면 그 프레임에 빈 칸이 있었다는 뜻입니다. Knot 프런트엔드 코드에서 `#ff00ff` 같은 자홍색 값은 찾지 못했고, 행을 모두 그리는 가상화 전 빌드에서는 빈 칸이 보인 프레임이 한 장도 없었어요. 그러니 자홍색이 보였다면 가상화 때문에 생긴 빈 칸입니다.

overscan만 0px, 160px, 325px, 650px로 바꾼 빌드 네 개를 만들고, 휠을 한 번에 150px씩 또는 300px씩 150번 돌리며 프레임을 받았습니다. CPU를 4배 느리게 한 조건과 제한하지 않은 조건에서 따로 쟀어요. 프레임에서 자홍색을 어떻게 셌는지 같은 세부는 글 끝 「측정 조건 자세히 보기」에 적어 두었습니다.

## 얼마로 정했을까

overscan을 행 개수가 아니라 px로 정한 까닭은 [2편](/posts/virtual-list-row-range/)에서 다뤘는데요. 빈 칸이 생기는지도 휠 한 번에 몇 px를 움직이느냐로 정해지니, px로 정해 두면 요약 없는 행(64px)과 요약 있는 행(92px)을 같은 기준으로 따질 수 있습니다. 처음 값은 요약 없는 행 5개쯤인 325px로 잡았고, 재 보니 아래와 같았습니다.

| overscan | 휠 한 번 150px | 휠 한 번 300px |
| ---: | --- | --- |
| 0px | 400장 중 221장 (392장 중 220장) | 재지 않음 |
| 160px | 403장 중 0장 (404장 중 0장) | 396장 중 216장 (402장 중 224장) |
| 325px | 404장 중 0장 (406장 중 0장) | 410장 중 0장 (391장 중 0장) |
| 650px | 401장 중 0장 (404장 중 0장) | 408장 중 0장 (427장 중 0장) |

</Figure>

빈 칸은 휠 한 번의 거리가 overscan보다 긴 두 경우(0px에 150px 휠, 160px에 300px 휠)에서 보였고, 받은 프레임의 55–56%에 나왔습니다. 나머지 경우에는 한 장도 없었어요. 앞 절의 계산과 같은 결과예요.

그런데 CPU를 4배 느리게 해도 빈 칸이 보인 프레임 수는 거의 같았습니다(221장과 220장, 216장과 224장). 행을 그리는 시간이 길어서 빈 칸이 생긴 거라면, CPU가 느릴 때 빈 칸이 더 많이 보였어야 하겠죠? 빈 칸은 그리는 속도보다, 합성기 스레드의 프레임이 메인 스레드의 일보다 먼저 나가는 순서 때문에 생긴다고 볼 수 있습니다.

그럼 650px도 빈 칸이 없었는데 왜 325px를 골랐을까요? overscan이 길수록 DOM에 두는 행도 함께 늘어나기 때문입니다.

<Figure caption="표 2. overscan마다 DOM에 둔 행과 페이지의 HTML 요소 (표 1과 같은 측정)" captionSide="top">

| overscan | 목록을 연 직후 | 22,500px 스크롤한 뒤 |
| ---: | --- | --- |
| 0px | 행 8개, 요소 309개 | 행 12개, 요소 346개 |
| 160px | 행 11개, 요소 336개 | 행 18개, 요소 400개 |
| 325px | 행 13개, 요소 354개 | 행 22개, 요소 436개 |
| 650px | 행 18개, 요소 399개 | 행 32개, 요소 526개 |

</Figure>

스크롤한 뒤에 그린 행은 대략 (보이는 높이 750px + overscan × 2) ÷ 65px입니다. 목록을 연 직후에 더 적은 까닭은 첫 카드 위쪽에는 그릴 행이 없기 때문이에요. 325px는 650px보다 스크롤한 뒤 DOM에 둔 행이 10개 적었습니다.

325px에도 한계는 있습니다. 같은 계산으로 화면 위쪽 끝을 행 하나(65px) 안에서 1px씩 옮긴 65곳을 모두 돌려 보면, 휠 한 번이 350px일 때는 65곳 가운데 25곳에서 최대 25px, 400px일 때는 모든 곳에서 최대 75px가 빕니다. 그래서 이 점을 측정 결과와 함께 상수 주석에 남겼어요.

```ts title="overscan.ts"
/**
 * …
 * 실제 빌드에서 휠 한 번에 300px씩 스크롤했을 때
 * 160px는 빈 칸이 보였고 325px는 보이지 않아서
 * 325px로 정했어요.
 * 휠 한 번에 이 거리보다 많이 스크롤하면
 * 빈 칸이 보일 수 있어요.
 */
export const OVERSCAN_PX = 325;
```

## 행을 더 그려도 스크롤은 부드러웠을까

overscan을 늘리면 스크롤하며 행을 더하고 지우는 일도 늘어납니다. 그래서 스크롤하는 동안 프레임 사이의 간격이 길어지지 않았는지 가상화 전 빌드와 견줘 봤어요. 프레임 간격은 페이지가 화면을 다시 그릴 때마다 부르는 `requestAnimationFrame` 콜백 사이의 시간입니다[^raf].

<Figure caption="표 3. 150px 휠로 150번 스크롤하는 동안의 프레임 간격 (표 1과 같은 측정, CPU 4배 느리게)" captionSide="top">

| 빌드 | 가운데값 | 99% 값 | 가장 긴 간격 | 긴 작업(50ms 이상) |
| --- | ---: | ---: | ---: | ---: |
| 가상화 전 (행을 모두 그림) | 8.3ms | 11.5ms | 13ms | 0개 |
| 가상화 후 (overscan 325px) | 8.4ms | 12.3ms | 13ms | 0개 |

</Figure>

두 빌드의 값은 거의 같았습니다. 99% 값[^p99]이 11.5ms에서 12.3ms로 조금 늘었지만, 가장 긴 간격은 둘 다 13ms였어요. 메인 스레드가 50ms 이상 쉬지 못하는 긴 작업[^long-task]도 두 빌드 모두 없었습니다.

다만 세션 녹화 도구를 켠 빌드에서는 값이 달랐는데요. 세션 녹화 도구는 사용자의 화면 동작을 DOM 변화로 기록해 다시 보여 주는 분석 도구로, Knot 운영 환경에 켜져 있습니다. 이 도구를 켠 가상화 후 빌드를 300px 휠로 세 번 재 보니, 한 번은 425장 가운데 4장에 빈 칸이 보였습니다. 세 번의 99% 값도 17.7–19.5ms로, 같은 조건에서 도구를 켠 가상화 전 빌드(12.5–12.7ms)보다 길었어요. 행을 그리고 지우는 DOM 변화까지 녹화 도구가 기록하기 때문으로 보이지만, 프로파일로 나눠 확인하지는 않았습니다.

## 아직 막지 못한 빈 칸

- 휠 한 번에 325px보다 많이 스크롤하는 장치나 설정에서는 빈 칸이 한 프레임 보일 수 있습니다.
- 스크롤바를 끌어 멀리 옮기는 동작은 재지 않았습니다. 그린 행이 화면을 덮지 못하면 scroll 이벤트 안에서 바로 다시 그리게 해 두었지만([4편](/posts/virtual-list-back-navigation/)), 합성기 스레드가 먼저 내보내는 프레임까지 막는지는 확인하지 않았어요.
- 휠을 위로 돌리는 경우는 재지 않았습니다. 측정은 휠을 아래로만 돌렸어요.
- 세션 녹화 도구를 켠 빌드에서는 300px 휠에서도 빈 칸이 보인 프레임이 나온 적이 있습니다.

## 정리

- 휠 스크롤의 빈 칸은 Chrome의 합성기 스레드가 메인 스레드보다 먼저 스크롤한 프레임을 내보내서 생깁니다. 휠 한 번의 거리가 화면 아래로 그려 둔 거리보다 긴 만큼 비어 보여요.
- JavaScript로는 그 프레임을 볼 수 없어서, 카드 바탕을 자홍색으로 칠하고 화면에 나간 프레임을 받아 빈 칸이 보인 프레임을 셌습니다.
- CPU를 4배 느리게 해도 빈 칸이 보인 프레임 수가 거의 같아서, 빈 칸은 그리는 속도보다 프레임이 나가는 순서와 관계가 있었습니다.
- 150px와 300px 휠에서 빈 칸이 없던 325px와 650px 가운데, DOM에 두는 행이 적은 325px를 골랐습니다. 세션 녹화 도구가 없는 빌드에서는 스크롤할 때의 프레임 간격도 가상화 전과 거의 같았습니다.
