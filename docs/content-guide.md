이 블로그의 글을 쓰고 올릴 때 지키는 규칙입니다. 화면 기준값과 부품은 [design-system.md](./design-system.md), 계획은 [plan.md](./plan.md)에 있습니다.

## 1. 글 하나의 틀

- 글 하나는 폴더 하나입니다: `src/content/posts/{slug}/index.mdx`. 그림과 정지 그림도 같은 폴더에 둡니다.
- 폴더 이름(`slug`)이 그대로 주소가 됩니다: `/posts/{slug}/`.
- 데모 코드는 `src/modules/features/demo/{DemoName}/`에 두고 MDX에서 불러옵니다.
- frontmatter:

```yaml
---
title: "브라우저는 언제 화면을 다시 그릴까: 레이아웃과 페인트"
description: "스타일 하나를 바꿨을 뿐인데 화면이 버벅이는 이유를, 렌더링 단계를 직접 움직여 보며 정리합니다."
publishedAt: 2026-11-18
updatedAt: 2026-11-20 # 내용을 고쳤을 때만
projects: [knot] # 이어진 프로젝트가 있을 때만
draft: true # 이스타가 확인하기 전까지
category: 브라우저
series: # 시리즈 글일 때만
  id: browser-rendering
  name: 브라우저 렌더링
  order: 1
---
```

| 칸 | 꼭 | 쓰는 곳 | 규칙 |
|---|---|---|---|
| `title` | 예 | h1, `<title>`, og:title, RSS, 목록 | 2장 |
| `description` | 예 | 글 요약(글 머리), meta description, og:description, RSS, 목록 요약 | 2장 |
| `publishedAt` | 예 | 글 정보, BlogPosting `datePublished`, 목록 순서 | 9장 |
| `updatedAt` | 아니요 | 「고침」 표시, `dateModified`, 사이트맵 `lastmod` | 9장 |
| `category` | 예 | 글 정보 맨 앞, BreadcrumbList | 8장 |
| `series` | 아니요 | 영문 id, 이름, 순서. 시리즈 칩과 안내 상자, 시리즈 페이지, 이전과 다음 글 | 8장 |
| `projects` | 아니요 | 글 끝 「이 글과 이어진 프로젝트」(포트폴리오 구획으로 링크). `knot`, `sellerhome`, `bid` 가운데서 고르고, 없는 id면 빌드가 멈춤 | design-system 7.26 |
| `draft` | 아니요 | `true`면 초안. 배포 빌드의 글 목록, 글 페이지, RSS, 사이트맵, llms.txt, 공유 그림에서 빠짐. 공개한 편이 있는 시리즈의 편 목록에는 제목과 「준비 중」만 보임. 개발 서버에서는 본문도 보임 | 12장 |

## 2. 제목, 요약, 주소

### 2.1 제목 (`title`)

- 길이는 한글 25–32자로 쓰고 40자를 넘기지 않습니다.
- **핵심 낱말을 앞 20자 안에 둡니다.** 잘려도 무슨 글인지 알 수 있어야 합니다.
- 질문이나 「무엇: 어떻게」 꼴이 좋습니다. 예: 「브라우저는 언제 화면을 다시 그릴까: 레이아웃과 페인트」
- `<title>`은 「글 제목 · 이스타의 개발 노트」로 사이트 이름을 뒤에 붙입니다. og:title에는 붙이지 않습니다.
- 근거:
  - Google은 제목 글자 수를 정해 두지 않고, 검색 결과 폭에 맞춰 자릅니다([Google Search Central: Title links](https://developers.google.com/search/docs/appearance/title-link)).
  - 넓은 화면 검색 결과 제목은 약 600px에서 잘린다고 흔히 잽니다. 한글 한 글자는 영문 한 글자의 약 두 배 폭이라 30자 안팎이 한 번에 보이는 길이입니다.
  - 그래서 사이트 이름이 뒤에서 잘려도 글 제목은 남도록 32자 이하로 잡았습니다.

### 2.2 요약 (`description`)

- 길이는 한글 60–80자로 한두 문장을 쓰고 100자를 넘기지 않습니다.
- 글이 답하는 질문과 답의 방향을 씁니다. 「~을 정리합니다」만 쓰지 말고 무엇을 알게 되는지 씁니다.
- 제목을 되풀이하지 않습니다.
- 근거:
  - Google도 요약의 글자 수 제한을 두지 않고 화면 폭에 맞춰 자릅니다([Google Search Central: Snippets](https://developers.google.com/search/docs/appearance/snippet)).
  - 흔히 넓은 화면 약 920px, 휴대폰은 그보다 짧게 잘립니다. 한글로는 70–80자 안팎이라 핵심을 앞 60자 안에 둡니다.
  - 같은 글이 목록 요약과 RSS에도 쓰여서 한두 문장이 알맞습니다.

### 2.3 주소 (`slug`)

- 영어 소문자 낱말 3–5개를 하이픈으로 잇습니다. 예를 들어 `virtualized-document-list`처럼 씁니다.
- 한글, 날짜, 숫자 순번을 넣지 않습니다.
- **올린 뒤에는 바꾸지 않습니다.** 꼭 바꿔야 하면 옛 주소에서 새 주소로 넘기는 페이지를 남깁니다.

## 3. 글 구조

- **h1은 하나입니다.** frontmatter의 `title`이 h1이 됩니다. 본문에 `#`을 쓰지 않습니다.
- **본문 제목은 `##`(h2)와 `###`(h3)까지만** 씁니다. `####`가 필요하면 글을 나누거나 목록으로 바꿉니다.
- h2는 글 하나에 3–7개가 알맞습니다. h2가 셋 이상이면 목차가 생깁니다.
- 제목은 그 절이 답하는 질문이나 내용을 그대로 씁니다. 「들어가며」, 「본론」 같은 제목은 쓰지 않습니다.
- **답을 먼저 씁니다.**
  - 글 첫 문단 2–3문장에 글 전체의 결론을 씁니다.
  - h2마다 첫 문장에 그 절의 답을 씁니다. 그다음 이유와 예를 씁니다.
  - 검색 결과와 AI 답변이 첫 문단을 그대로 가져가는 일이 많아서입니다.
- 문단 하나는 3–5문장, 한 문장에 한 뜻을 씁니다.
- 순서가 있으면 번호 목록, 없으면 점 목록, 비교는 표를 씁니다.
- 표에는 설명을 붙입니다. 마크다운 표에는 `<caption>`을 넣을 수 없으므로 `<Figure caption="표 1. 바꾼 속성에 따라 다시 하는 단계" captionSide="top">`으로 감쌉니다.
- 끝에 「정리」 절을 두고 핵심 3–5개를 목록으로 씁니다.
- 글 길이는 읽는 시간 5–12분(한글 약 3,000–7,000자)을 기준으로 합니다. 더 길면 시리즈로 나눕니다.
- 쉬운 말로 씁니다. 전문 용어는 처음 나올 때 한 번 풀어 쓰고, 뒤에서는 같은 낱말을 씁니다.

## 4. 한글 표기

### 4.1 띄어쓰기와 숫자

- 한글 맞춤법을 따르고, 맞춤법 검사기로 한 번 봅니다.
- 아라비아 숫자 뒤의 단위는 붙여 씁니다: 8분, 3편, 2026년 11월 18일, 40자. 한글 맞춤법 제43항의 「숫자와 어울려 쓰이는 경우 붙여 쓸 수 있다」를 따릅니다.
- 단위 기호도 붙여 씁니다: 680px, 1.5초, 200ms, 40%, 30KB.
- 수의 범위는 짧은 줄표 「–」(U+2013)로 붙여 씁니다: 38–47자, 2026.09–2026.11.
- 마크다운 처리기가 한 줄의 물결표 두 개를 취소선으로 그리고 스크린 리더가 「물결」로 읽으므로, 수의 범위에는 물결표를 쓰지 않습니다.
- 큰 수는 세 자리마다 쉼표를 찍습니다: 3,000자.
- 날짜는 본문에서 「2026년 11월 18일」, 좁은 자리에서 「2026.11.18」로 씁니다.

### 4.2 문장 부호

| 부호 | 쓰는 곳 | 예 |
|---|---|---|
| 「」 | 화면에 보이는 문구, 단추 이름, 글 · 절 제목, 짧은 인용 | 「복사됨」으로 바뀝니다 |
| 『』 | 책 이름 | 『리팩터링』 |
| `백틱` | 코드 이름, 속성, 파일 이름, 명령 | `offsetWidth`, `resize.ts` |
| · (가운뎃점) | 화면의 정보 줄(글 머리, 글 목록)에서 짧은 정보의 나열. 본문 문장에는 쓰지 않고 「와 · 과」나 쉼표로 잇습니다(writing-style) | 분류 · 날짜 · 읽는 시간 |
| : (쌍점) | 제목의 앞뒤 나누기, 목록 이름 뒤 | 레이아웃과 페인트: 무엇이 다를까 |
| … | 말줄임 | |

- 큰따옴표 `""`는 코드 문자열 말고는 쓰지 않습니다.
- 굵게(`**`)는 문단 하나에 한 번 이하, 핵심 낱말에만 씁니다. 기울임꼴은 쓰지 않습니다.
- 이모지는 쓰지 않습니다.
- 느낌표는 독자가 놀라야 하는 곳처럼 정말 강조할 곳에만, 글 하나에 세 곳 이하로 씁니다. 넘으면 게시 전 점검이 경고합니다.

### 4.3 외래어와 영어

- 굳은 외래어는 한글로 씁니다: 브라우저, 레이아웃, 페인트, 컴포넌트.
- 코드 이름과 제품 이름은 원래 글자 그대로 씁니다: React, TanStack Query, `useEffect`.
- 처음 나오는 전문 용어는 괄호에 영어를 한 번 함께 씁니다: 강제 동기 레이아웃(forced synchronous layout).

### 4.4 줄바꿈

- MDX에서 문단 하나는 한 줄로 씁니다. 문장 중간에 손으로 줄을 바꾸지 않습니다.
- `<br>`을 쓰지 않습니다. 화면의 줄바꿈은 CSS(`word-break: keep-all`)가 맡습니다.

## 5. 코드 칸

- **언어를 꼭 적습니다.** 예: ` ```ts `, ` ```css `, ` ```tsx `, ` ```bash `, ` ```text `(실행 결과).
- **파일이 있으면 이름을 적습니다.** ` ```ts title="resize.ts" ` → 코드 칸 머리에 파일 이름이 보입니다. 없으면 언어 이름이 보입니다.
- 한 줄은 60자 이하로 씁니다. 코드 글자가 15px(휴대폰 14px)이라 넓은 화면은 약 70자, 휴대폰은 약 37자부터 칸 안에서 가로로 밀립니다. 줄을 바꿔 주지 않습니다.
- 들여쓰기는 스페이스 2칸입니다.
- 짚어 줄 줄은 강조 줄로 표시합니다. ` ```ts title="resize.ts" {3,5-6} `처럼 메타에 줄 번호를 적고, 한 칸에 세 줄 이하로만 씁니다. 줄 번호는 20줄 넘는 칸에서만 저절로 켜집니다.
- 글자는 신경 쓰지 않고 씁니다. 글꼴은 사이트에 쓰인 글자만 담아 만드는데, `pnpm build`가 글에 새로 쓴 글자로 글꼴을 다시 만들고 빠진 글자가 없는지 검사합니다. 바뀐 글꼴 파일(`src/shared/styles/fonts/`)은 글과 함께 커밋합니다. 원본 글꼴에 없는 글자(한자, 그림 문자 등)를 쓰면 빌드가 실패해서 알려 줍니다.
- 한 칸은 25줄 이하로 씁니다. 길면 핵심만 남기고 「…」 주석으로 줄입니다.
- 셸 명령에는 `$` 프롬프트를 붙이지 않습니다(복사해서 바로 쓰게).
- 좋은 예와 나쁜 예는 칸을 나누고, 주석 첫 줄에 `// 나쁜 예`, `// 좋은 예`를 씁니다. 설명은 칸 밖 문단에 씁니다.
- 코드 칸 바로 앞 문단에서 이 코드가 무엇을 보여 주는지 한 문장으로 말합니다.
- 실행 결과를 그림으로 보여 주지 않습니다. 결과가 글자면 ` ```text ` 칸, 화면이면 그림이나 데모를 씁니다.
- 토큰, 비밀번호, 키, 개인 주소는 코드 칸에도 넣지 않습니다(11장).

## 6. 그림과 공유 미리보기 이미지

### 6.1 그림

- **대체 글(`alt`)을 꼭 씁니다.**
  - 그림이 전하는 내용을 한 문장으로 씁니다. 「스크린샷」, 「그림」 같은 말로 시작하지 않습니다.
  - 예: `alt="Performance 패널: 보라색 레이아웃 막대가 상자 수만큼 이어진다"`
  - 꾸밈 그림은 `alt=""`로 둡니다(이 블로그는 꾸밈 그림을 거의 쓰지 않습니다).
  - 도식처럼 내용이 많으면 alt는 짧게, 자세한 설명은 본문이나 그림 설명에 씁니다.
- **크기:** 원본 폭 1360px(본문 680px의 2배). 원본 파일은 1MB 이하.
- **형식:** 원본은 PNG(스크린샷 · 도식)나 JPEG(사진). Astro의 그림 처리가 AVIF · WebP로 바꾸고 `width` · `height`를 붙입니다.
- **파일 이름:** 영어 소문자와 하이픈. 예: `performance-panel-layout.png`
- 그림 설명(`figcaption`)은 「그림 1.」로 시작하고 무엇을 보여 주는지 씁니다.
- 움직이는 GIF는 쓰지 않습니다. 움직임이 필요하면 데모를 만들거나, 짧은 영상(`mp4`, 자동 재생 없이 조작 단추 표시)을 씁니다.
- 투명 바탕 도식은 어두운 화면에서 안 보일 수 있습니다. 두 벌을 만들거나 바탕을 칠한 칸에 넣습니다(design-system 9장).
- 스크린샷의 주소창, 알림, 이메일, 사람 이름, 다른 탭은 가립니다(11장).

### 6.2 공유 미리보기 이미지 (og:image)

- 크기 **1200×630px**(1.91:1), PNG, 300KB 이하. Facebook, LinkedIn, X, 카카오톡이 큰 카드로 보여 주는 비율입니다.
- 글마다 하나씩 둡니다. 기본은 빌드할 때 글 제목과 분류로 만든 그림(밝은 화면 색, Pretendard)이고, 직접 만든 그림이 있으면 글 폴더의 `og.png`를 씁니다.
- 글자는 가운데 1080×530px 안에 두고, 제목은 48px 이상으로 씁니다. 작은 카드에서 잘려도 읽히게 하기 위해서입니다.
- `og:image:alt`에 그림이 무엇인지 씁니다(보통 글 제목).

## 7. 아티팩트를 데모로 다시 만드는 규칙

Claude 앱에서 만든 아티팩트는 **재료**입니다. 기준은 블로그 디자인입니다. 아티팩트 코드를 그대로 붙이지 않고, 필요한 부분만 골라 블로그 부품으로 다시 만듭니다.

### 7.1 색과 모양

- **디자인 토큰만 씁니다.** 색은 `--color-*`, 글꼴은 `--font-sans` · `--font-mono`, 간격은 `--space-*`, 모서리는 `--radius-*`.
- 색을 더할 때는 데이터 색인 `--color-data-1`–`--color-data-4`(주황, 청록, 자주, 분홍)를 씁니다.
  - 범주는 넷까지. 더 많으면 묶거나 데모를 나눕니다.
  - 범주는 색과 함께 이름표나 모양(●▲■◆)으로도 나눕니다.
  - 본문에서 그 범주를 말하는 낱말에 같은 색을 써서 글과 데모를 잇습니다.
- 「지금 바뀐 것」, 「고른 것」은 `--color-accent`와 `--color-accent-soft`로 표시합니다. 좋음 · 나쁨은 `--color-good` · `--color-bad`입니다.
- 아티팩트에 흔한 것들을 지웁니다: Tailwind 색 클래스, 그라데이션, 그림자, 둥근 큰 카드, 이모지 장식, 아티팩트 안 제목과 설명 글(본문과 그림 설명이 맡습니다).

### 7.2 폭과 배치

- 데모는 「데모 틀」(`DemoFrame`) 안에만 둡니다. 폭은 본문 폭(680px) 이하입니다.
- 휴대폰(화면 390px, 데모 화면 안쪽 약 300px)에서 가로로 넘치지 않게, 가로로 늘어선 것은 세로로 쌓습니다. 시안 「A · 글 화면 · 휴대폰」의 데모가 본보기입니다.
- **데모 화면 높이가 바뀌지 않게 합니다.** 데모마다 고정 높이(`min-height`나 `aspect-ratio`)를 정하거나, 서버에서 첫 화면을 그려 JavaScript가 붙기 전후 높이를 같게 합니다. 아래 글이 밀리지 않게 하려는 것입니다(CLS 0).
- 글자는 caption(14px · 휴대폰 13px) 이상, 누르는 것은 40px 이상으로 만듭니다.

### 7.3 어두운 화면

- 토큰만 쓰면 저절로 바뀝니다.
- `canvas`나 SVG에 색을 직접 칠할 때는 `getComputedStyle`로 CSS 변수를 읽어 칠하고, 화면 밝기가 바뀌면(`data-theme` 바뀜 감지) 다시 그립니다.
- 두 화면 모두에서 직접 보고 올립니다.

### 7.4 JavaScript 없이도

- **앞뒤 글만 읽어도 뜻이 통하게 씁니다.** 데모는 글을 돕는 것이지 글을 대신하지 않습니다.
- 데모 설명(`caption`) 한 줄에 데모가 보여 주는 결론을 씁니다. 예: 「width를 바꾸면 네 단계를 모두 다시 하고, transform을 고르면 레이아웃과 페인트를 건너뜁니다.」
- 데모가 보여 주는 동작과 설명은 실제 브라우저 동작과 맞춥니다. 아티팩트의 설명을 그대로 믿지 말고 공식 문서나 DevTools로 확인합니다.
- **정지 그림을 만듭니다.** 데모의 대표 상태를 1360px 폭으로 찍어 글 폴더에 `demo-{이름}-fallback.png`로 두고 `alt`를 씁니다. JavaScript가 없을 때 데모 틀의 「JavaScript 없음」 상태로 보입니다.
- 서버에서 그린 첫 화면이 이미 뜻이 통하는 상태면 정지 그림 대신 그 화면을 씁니다.

### 7.5 무게

- **데모 하나의 자체 코드는 30KB(gzip) 이하**, 데모 있는 글의 페이지 JS 합계는 100KB 이하(React 런타임 포함)입니다.
- 바깥 라이브러리를 새로 넣지 않습니다. 꼭 필요하면 이스타에게 먼저 묻습니다.
- 화면에 들어올 때 불러옵니다(`client:visible`). 첫 화면 안에 있으면 `client:idle`.
- 움직임은 `transform`과 `opacity`로 만들고, `requestAnimationFrame` 하나로 돌립니다. 화면 밖으로 나가면 멈춥니다.

### 7.6 조작

- **조작 장치는 두세 개 이하입니다.** 보통 재생/멈춤, 처음으로, 슬라이더(또는 고르기 하나)입니다. 조작은 데모 틀의 조작 줄에만 둡니다.
- **키보드로 모두 쓸 수 있어야 합니다.** Tab으로 닿고, 단추는 Enter · Space, 슬라이더는 화살표 · Home · End.
- 모든 조작에 이름을 붙입니다: 단추 `aria-label`, 슬라이더 `aria-label`과 `aria-valuetext`.
- 단계가 바뀌면 조작 줄의 상태 글(예: 「멈춤 · 2 / 4단계」)을 바꾸고 `aria-live="polite"`로 읽어 줍니다.
- 끌기(drag)만으로 되는 조작을 만들지 않습니다. 같은 일을 단추나 슬라이더로도 할 수 있게 합니다.

### 7.7 움직임 줄이기

- **자동 재생하지 않습니다.** 사용자가 재생을 눌러야 움직입니다.
- `prefers-reduced-motion: reduce`면 단계 사이를 움직이지 않고 바로 바꿉니다. 슬라이더와 단계 단추는 그대로 씁니다.
- 번쩍임(1초에 3번 넘게 밝기가 바뀌는 것)은 만들지 않습니다.

### 7.8 데모를 올리기 전 확인

- [ ] 토큰과 데이터 색만 썼다 (색 값을 직접 쓴 곳이 없다)
- [ ] 휴대폰 390px에서 가로로 넘치지 않는다
- [ ] 어두운 화면에서 보인다
- [ ] JavaScript를 끄고 글이 통하고, 정지 그림과 alt가 있다
- [ ] 키보드만으로 조작할 수 있고 포커스가 보인다
- [ ] 움직임 줄이기를 켜면 자동으로 움직이지 않는다
- [ ] 조작 장치가 세 개 이하다
- [ ] 데모 자체 코드 30KB 이하, 페이지 JS 100KB 이하
- [ ] 데모 화면 높이가 JavaScript 전후로 같아 CLS가 0이다
- [ ] 데모의 동작과 설명이 실제 브라우저 동작과 맞다
- [ ] 아티팩트의 대화 내용이나 개인 정보가 남아 있지 않다

## 8. 시리즈와 분류

### 8.1 분류 (`category`)

- 글 하나에 분류 하나만 둡니다. 태그는 두지 않습니다.
- 정한 분류: **브라우저 · CSS · JavaScript · React · 접근성 · 도구**
- 새 분류가 필요하면 이스타와 정하고 이 목록에 먼저 더합니다. 분류 이름은 바꾸지 않습니다.

### 8.2 시리즈 (`series`)

- 같은 주제를 이어서 읽어야 이해되는 글을 묶습니다. 세 편 이상 쓸 계획일 때만 만듭니다.
- `id`는 영문 소문자 낱말을 하이픈으로 이은 고유 주소 이름이며 `/series/{id}/`에 씁니다. `id`와 `name`은 한 번 정하면 바꾸지 않습니다. `order`는 1부터 빈 번호 없이 씁니다.
- 시리즈 글의 첫 문단 위 안내 상자에서 이름과 「5편 중 2편」, 접는 편 목록을 보입니다. 본문 첫 문단에는 안내를 반복하지 않으며, 이전과 다음 글은 시리즈 순서로 잇습니다. 배포 빌드에서 초안 편은 링크 없이 「준비 중」으로 보이고 공개한 편이 있는 시리즈만 페이지를 만듭니다(design-system 7.30과 7.31).
- 한 시리즈의 글은 따로 읽어도 첫 문단만으로 무엇을 다루는지 알 수 있게 씁니다.

## 9. 게시일과 수정일

- `publishedAt`: 처음 공개한 날(한국 시간). 바꾸지 않습니다.
- `updatedAt`: **내용이 바뀐 고침만** 적습니다. 오타, 문장 다듬기, 링크 고침은 적지 않습니다.
  - 적으면 글 머리에 「11월 20일 고침」이 보이고, BlogPosting의 `dateModified`와 사이트맵 `lastmod`가 바뀝니다.
  - 내용이 크게 바뀌었으면 글 끝 「고친 내용」에 날짜와 한 줄을 남깁니다. 예: 「2026년 11월 20일: Chrome 140의 바뀐 동작을 더했습니다.」
- 틀린 내용을 고쳤으면 고친 줄을 지우지 말고 「고친 내용」에 무엇이 틀렸는지 적습니다.

## 10. 게시 전 확인 목록 (SEO · AEO)

글마다 아래를 확인합니다. 사실 대조 상태는 게시 전에 로컬에서 확인하며, GitHub Actions의 배포 점검은 저장소 밖 대조표를 읽을 수 없어 이 항목을 건너뜁니다.

### 10.1 제목과 요약

- [ ] `title` 25–32자, 핵심 낱말이 앞 20자 안에 있다
- [ ] `description` 60–80자, 무엇을 알게 되는지 쓴다, 제목을 되풀이하지 않는다
- [ ] `slug`가 영어 소문자-하이픈 3–5낱말이고, 이미 쓰는 주소와 겹치지 않는다
- [ ] `category`가 정한 목록 안에 있다

### 10.2 구조

- [ ] 본문에 `#`(h1)이 없고, `##` · `###`만 쓴다
- [ ] 첫 문단 2–3문장에 결론이 있다
- [ ] h2마다 첫 문장이 그 절의 답이다
- [ ] 끝에 「정리」가 있다

### 10.3 AEO (AI 답변에 인용되기 쉽게)

- [ ] 중요한 개념을 정의 문장으로 한 번 쓴다(예: 「목록 가상화는 ... 방법을 말합니다」). writing-style의 금지 표현은 피한다
- [ ] 묻는 꼴의 h2가 하나 이상 있다(사람들이 실제로 검색할 질문)
- [ ] 비교는 표, 순서는 번호 목록으로 썼다
- [ ] 숫자와 버전, 확인한 날짜를 적었다(예: 「Chrome 140 기준, 2026년 11월 확인」)
- [ ] 출처 링크를 본문에 걸었다
- [ ] 사실 대조(`fact-check-post`)를 마쳤고, 대조표에 다름과 출처에 없음이 없다

### 10.4 그림과 데모

- [ ] 모든 그림에 alt와 그림 설명이 있다
- [ ] 공유 미리보기 이미지(1200×630)가 있다
- [ ] 데모가 있으면 7.8을 모두 통과했다

### 10.5 링크

- [ ] 이 블로그의 다른 글 링크가 있으면 걸었다(같은 시리즈, 앞선 개념)
- [ ] 링크 글이 갈 곳을 말한다(「여기」 없음)
- [ ] 깨진 링크가 없다

### 10.6 기술 확인

- [ ] `pnpm build`가 통과한다
- [ ] 미리보기에서 BlogPosting(작성자, 발행일, 수정일)과 BreadcrumbList가 나온다
- [ ] canonical, og:title · og:description · og:image가 맞다
- [ ] RSS, 사이트맵, llms.txt에 글이 들어갔다
- [ ] Lighthouse 휴대폰: 성능 95 이상, 접근성 · 권장사항 · SEO 100
- [ ] 넓은 화면 · 휴대폰 · 어두운 화면에서 직접 봤다

### 10.7 올린 뒤

- [ ] Google Search Console과 네이버 서치어드바이저에서 사이트맵이 다시 읽혔는지 본다(새 글이 많을 때는 주소 검사 요청)
- [ ] 공유 미리보기를 카카오톡이나 X 카드 검사로 한 번 본다

## 11. 세컨드 브레인 기록과 개인 정보

- **세컨드 브레인의 기록(회의 글, 대화, 개인 정보)을 글에 옮기지 않습니다.** 세컨드 브레인에서는 글감과 순서만 가져오고, 글 내용은 공개 자료와 직접 해 본 결과로 새로 씁니다.
- 회사 안의 일, 동료 · 고객의 이름, 비공개 저장소의 코드, 내부 주소와 화면은 쓰지 않습니다. 예시가 필요하면 새로 만든 예시를 씁니다.
- Claude 아티팩트를 만든 대화 내용은 옮기지 않습니다. 아티팩트에서는 데모의 생각과 모양만 가져옵니다.
- 토큰, 비밀번호, 키, 개인 이메일, 전화번호, 집 주소는 글, 코드 칸, 그림, 커밋 어디에도 넣지 않습니다. 이미 넣었으면 지우는 것만으로는 부족합니다. 키를 새로 발급하고 기록에서도 지웁니다.
- 스크린샷은 올리기 전에 주소창, 알림, 다른 탭, 계정 이름, 메일을 확인하고 가립니다.
- 공개되면 곤란한 초안은 저장소에 넣지 않습니다(저장소가 공개라서 초안 커밋도 공개됩니다).
- 반대 방향은 괜찮습니다. 올린 글은 세컨드 브레인 기록으로 넣습니다(plan.md).

## 12. 게시 절차

1. 글을 씁니다(이 문서의 규칙대로). 앞머리에 `draft: true`를 두고 시작합니다. 초안은 main에 올라가도 배포 사이트에 나오지 않습니다(2026-11-21).
2. `fact-check-post`로 사실을 대조하고 다름과 출처에 없음을 고칩니다. 글을 고쳤으면 다시 대조해 최신 대조표로 확인합니다.
3. 10장의 확인 목록을 돕니다. 초안이 아닌 글이나 초안 표시를 지우려는 글은 대조표가 없거나 낡았거나 다름 또는 출처에 없음이 있으면 실패입니다.
4. **이스타가 읽고 확인합니다.** 개발 서버에서는 초안도 보입니다. 게시는 늘 이스타가 확인한 뒤에 합니다.
5. 확인이 끝나면 `draft: true` 줄을 지우고 커밋해서 올립니다. GitHub Pages 배포가 끝나면 실제 주소에서 한 번 더 봅니다.
6. 10.7의 올린 뒤 확인을 합니다.
7. 올린 글을 세컨드 브레인 기록으로 넣습니다.
